# 01. 인증·인가

> 누가 로그인한 사람인지 확인하고(인증), 그 사람이 무엇을 할 수 있는지 정하는(인가) 규칙입니다.
> 관련 파일: [02-계정관리](02-계정관리.md), [03-코어-블로그-글](03-코어-블로그-글.md)
> 읽는 법과 ID 규칙은 [00-목차.md](00-목차.md)를 봅니다.

## 요구사항

### 회원 가입 (CF-01, CF-14) — 상태: 화면 `데모`, 이메일 인증 단계와 규칙은 아직 동작하지 않음

가입 화면 **한 곳에서 이메일 인증을 먼저 마치고**, 나머지 항목과 함께 가입합니다. 인증을 마치기 전에는 계정이 만들어지지 않습니다.

```
닉네임·이메일 입력 → [인증번호 받기] → 메일로 온 인증번호 입력 → [확인] → 이메일 인증 완료
→ 비밀번호·비밀번호 확인 입력 → [가입하기] → 가입 완료
```

| ID | 요구사항 | 상세 |
|---|---|---|
| CF-01-1 | 입력 항목 | 닉네임, 이메일, 인증번호, 비밀번호, 비밀번호 확인을 입력한다. **모두 필수**이고, **이메일 인증을 마치고 모든 칸이 규칙을 지켰을 때만** 가입 버튼이 눌린다. |
| CF-01-2 | 이메일 형식 | 이메일 형식(예: `a@b.com`)이어야 한다. 앞뒤 공백은 지우고, 대소문자는 구분하지 않는다. |
| CF-14-1 | 이메일 중복 | 이미 가입된 이메일로는 가입할 수 없다. **인증번호를 보내기 전에** 검사해서, 이미 가입된 이메일에는 메일을 보내지 않는다. |
| CF-01-3 | 닉네임 규칙 | **2~10자**, 한글·영문·숫자만 쓸 수 있다. 공백과 특수문자는 쓸 수 없다. 다른 회원과 같은 닉네임은 쓸 수 없다. (영문 대소문자는 같은 것으로 본다.) |
| CF-01-4 | **비밀번호 규칙** | **영문, 숫자, 특수문자를 각각 1개 이상 포함하고 8~10자**여야 한다. 공백은 쓸 수 없다. 쓸 수 있는 특수문자는 `! @ # $ % ^ & * ( ) _ + - =` 이다. |
| CF-01-5 | 비밀번호 확인 | 비밀번호와 확인 입력이 같아야 한다. 다르면 확인칸 아래에 알려 준다. |
| CF-01-6 | 입력 중 안내 | 비밀번호를 입력하는 동안, 칸 아래에 규칙(글자 수, 영문, 숫자, 특수문자)을 **충족했는지 바로** 보여 준다. |
| CF-01-7 | 오류 표시 | 규칙을 어긴 칸마다 이유를 칸 아래에 보여 주고, 맨 위의 어긴 칸으로 커서를 옮긴다. 다른 칸에 쓴 값은 지우지 않는다. 비밀번호 칸은 비운다. |
| CF-01-8 | **비밀번호 저장** | 저장하기 전에 **단방향 해시**로 바꾼다. 원문은 데이터베이스, 로그, 오류 메시지 어디에도 남기지 않으며 운영자도 알 수 없다. (NF-01) |
| CF-01-9 | 가입 완료 | 모든 조건을 만족해 가입하면 계정이 만들어지고 바로 쓸 수 있다. "가입이 완료되었습니다. 로그인해 주세요"를 보여 준 뒤 로그인 화면으로 이동한다. 이때 내 블로그가 만들어진다. (CF-03-2) |
| CF-01-10 | 중복 제출 방지 | 가입 버튼을 연속으로 눌러도 한 번만 처리한다. |

### 이메일 인증 (CF-01 하위) — 상태: 화면 없음

네이버, 구글 등 **어떤 이메일 주소든** 쓸 수 있고, 우리는 그 주소로 인증번호를 보냅니다. (네이버 계정으로 로그인하는 소셜 로그인과는 다릅니다.) **가입 전에 인증하므로, 인증하지 않은 계정은 만들어지지 않습니다.**

| ID | 요구사항 | 상세 |
|---|---|---|
| CF-01-11 | 인증번호 받기 | 닉네임과 이메일이 형식에 맞으면 `인증번호 받기` 버튼이 눌린다. 누르면 그 이메일 주소로 인증번호를 보낸다. |
| CF-01-12 | 인증번호 | **영문 대문자와 숫자로 된 6자리 무작위 문자열**이다. (헷갈리는 `O`, `0`, `I`, `1`은 제외) 메일에는 서비스 이름, 인증번호, 유효 시간, "본인이 요청하지 않았다면 이 메일을 무시해 주세요"가 들어간다. |
| CF-01-13 | 입력과 확인 | 메일로 받은 인증번호를 입력하고 `확인`을 누른다. 맞으면 "이메일 인증이 완료되었습니다"를 보여 주고, 이메일 칸은 고칠 수 없게 잠근다. 틀리면 "인증번호가 올바르지 않습니다"를 보여 준다. |
| CF-01-14 | 유효 시간 | **10분**이다. 지나면 "인증번호가 만료되었습니다. 인증번호를 다시 받아 주세요"를 보여 준다. |
| CF-01-15 | 1회용 | 인증번호는 **맞게 입력하는 순간 사라져서** 다시 쓸 수 없다. 새로 받으면 이전 번호는 쓸 수 없다. |
| CF-01-16 | 다시 받기 | `인증번호 다시 받기`를 누를 수 있다. **1분에 한 번, 하루 5번**까지이다. |
| CF-01-17 | 틀린 횟수 | 인증번호를 **연속 5회** 틀리면 그 번호는 더 쓸 수 없고 새로 받아야 한다. |
| CF-01-18 | 발송 실패 | "메일을 보내지 못했습니다. 잠시 뒤 다시 시도해 주세요"를 보여 준다. 다시 받기를 누를 수 있다. |
| CF-01-19 | 이메일 바꾸기 | 인증을 마친 뒤 이메일을 바꾸려면 `이메일 변경`을 눌러야 하고, 그러면 **인증이 취소**되어 다시 받아야 한다. |
| CF-01-20 | 가입할 때 확인 | `가입하기`를 누르면 **서버가 그 이메일의 인증이 아직 유효한지 다시 확인**한다. 인증 후 **30분 안에** 가입해야 하며, 지나면 다시 인증한다. 화면을 건너뛰고 가입 요청만 보내도 거절한다. |
| CF-01-21 | 사이에 가입한 경우 | 인증하는 동안 다른 사람이 같은 이메일로 먼저 가입했다면, 가입할 때 CF-14-1에 따라 거절한다. |

### 로그인·로그아웃 (CF-02, CF-16) — 상태: 화면 `데모`, 규칙은 아직 동작하지 않음

| ID | 요구사항 | 상세 |
|---|---|---|
| CF-02-1 | 입력 | 이메일과 비밀번호를 입력한다. 둘 다 필수이다. |
| CF-02-2 | 성공 후 이동 | 로그인 전에 보던 화면으로 돌아간다. 로그인 화면에서 직접 왔다면 첫 화면으로 간다. |
| CF-02-3 | 실패 안내 | 이메일이 없거나 비밀번호가 틀려도 **같은 문구**를 보여 준다. 가입된 이메일인지는 알려 주지 않는다. |
| CF-02-4 | 로그인할 수 있는 계정 | 가입을 마친 계정은 바로 로그인할 수 있다. (인증을 마치지 않으면 계정이 만들어지지 않으므로 "인증 전 계정"은 없다.) |
| CF-02-5 | **5회 실패 잠금** | 같은 계정에서 **연속 5회** 로그인에 실패하면 그 계정을 잠근다. |
| CF-02-6 | 잠금 중 | 잠금 시간은 **10분**이다. 이 동안에는 비밀번호가 맞아도 로그인할 수 없고, 남은 시간을 안내한다. |
| CF-02-7 | 잠금 해제 | 시간이 지나면 자동으로 풀리고 실패 횟수가 0이 된다. 로그인에 성공해도 0이 된다. |
| CF-02-8 | 남은 횟수 | 몇 번 더 틀리면 잠기는지는 **알려 주지 않는다.** (계정이 있는지 짐작하지 못하게) |
| CF-02-9 | 없는 이메일 | 가입되지 않은 이메일은 잠금 대상이 아니지만, 화면에는 CF-02-3과 같은 문구만 보여 준다. |
| CF-02-10 | 로그인 유지 | **마지막으로 사용한 때부터 7일** 동안 다시 로그인하지 않아도 된다. 계속 쓰면 기간이 연장되고, 브라우저를 닫아도 유지된다. |
| CF-02-11 | 로그아웃 | 누르면 바로 로그인 전 상태가 된다. 로그인이 필요한 화면에 있었다면 첫 화면으로 이동한다. |
| CF-16-1 | 로그인 유도 | 로그인하지 않고 회원 전용 기능(글쓰기, 마이페이지, 댓글, 좋아요 등)을 누르면 로그인 창을 띄운다. 로그인하면 하려던 화면으로 돌아간다. |

### 비밀번호 찾기 (CF-25, 새 기능 제안) — 상태: 화면 없음

> 비밀번호를 잊은 사람이 **이메일 인증으로 본인을 확인**하고 새 비밀번호를 정하는 기능입니다. 팀 공통 문서(`요구사항-공통.md`)에는 없던 기능이라 새 ID `CF-25`를 붙였습니다.

| ID | 요구사항 | 상세 |
|---|---|---|
| CF-25-1 | 진입 | 로그인 창에 "비밀번호를 잊으셨나요?"를 둔다. 누르면 비밀번호 찾기 화면으로 간다. 이미 로그인한 상태에서는 보이지 않고, 비밀번호를 바꾸려면 마이페이지(CF-15)를 쓴다. |
| CF-25-2 | 이메일 입력 | 가입한 이메일을 입력하고 `인증번호 받기`를 누른다. 이메일 형식은 CF-01-2와 같다. |
| CF-25-3 | **같은 안내** | 가입된 이메일이든, 가입되지 않은 이메일이든, 탈퇴한 이메일이든 **화면에는 같은 안내**를 보여 준다. "입력하신 이메일로 안내를 보냈습니다. 10분 안에 인증번호를 입력해 주세요" **실제 메일은 가입된 이메일에만 보낸다.** 가입 여부는 알려 주지 않는다. (CF-02-3, NF-06) |
| CF-25-4 | 인증번호 | 형식, 유효 시간, 1회용, 다시 받기, 틀린 횟수가 모두 가입 때와 **같다.** (CF-01-12, 14 ~ 17) 메일에는 "비밀번호 찾기"라는 용도와 "본인이 요청하지 않았다면 이 메일을 무시해 주세요"가 들어간다. |
| CF-25-5 | 인증 확인 | 번호가 맞으면 "이메일 인증이 완료되었습니다"를 보여 주고 새 비밀번호 입력칸을 연다. 이메일 칸은 고칠 수 없게 잠근다. 인증 후 **30분 안에** 변경해야 하고, `변경하기`를 누르면 **서버가 인증이 아직 유효한지 다시 확인**한다. (CF-01-13, 20) |
| CF-25-6 | 새 비밀번호 | 새 비밀번호와 확인을 입력한다. 모두 필수이고 규칙은 CF-01-4와 같다. |
| CF-25-7 | 변경 후 | "비밀번호를 변경했습니다. 새 비밀번호로 로그인해 주세요"를 보여 주고 로그인 화면으로 보낸다. **자동으로 로그인하지 않는다.** |
| CF-25-8 | 기존 로그인 | 그 회원이 로그인해 둔 **모든 기기의 로그인을 끊는다.** (CF-15-15는 지금 쓰는 기기를 유지하지만, 여기서는 로그인한 상태가 아니므로 전부 끊는다.) |
| CF-25-9 | 잠금 해제 | 로그인 연속 실패 횟수와 잠금을 푼다. (CF-02-5 ~ 7) |
| CF-25-10 | 변경 알림 메일 | 비밀번호가 바뀌면 가입 이메일로 알려 준다. (선택. CF-15-16과 같다) |

### 관련 비기능 (보안)

| ID | 분류 | 요구사항 |
|---|---|---|
| NF-01 | 보안 | **비밀번호는 원문으로 저장하지 않는다.** 되돌릴 수 없는 해시로 저장하고, 로그와 오류 메시지에도 남기지 않는다. |
| NF-02 | 보안 | 글·댓글의 수정·삭제 권한은 **서버에서 검사**한다. 화면에서 버튼을 숨기는 것만으로는 부족하다. |
| NF-04 | 보안 | 로그인, 가입, 비밀번호 변경, 비밀번호 찾기는 **암호화된 연결(HTTPS)**로 한다. (배포 시) |
| NF-05 | 보안 | 인증번호와 같은 값은 추측할 수 없는 무작위 값이어야 하고, 한 번만 쓸 수 있으며, 일정 시간이 지나면 사라진다. |
| NF-06 | 보안 | 오류 메시지는 계정이 있는지, 시스템 내부가 어떤지 드러내지 않는다. |
| NF-10 | 보안 | 로그인 정보(세션)는 화면의 스크립트로 읽을 수 없어야 하고, 암호화된 연결에서만 전송한다. |
| NF-11 | 보안 | 다른 사이트에서 몰래 보낸 요청으로 글 작성·삭제, 비밀번호 변경 같은 동작이 실행되지 않게 한다. |
| NF-12 | 보안 | 로그인할 때마다 로그인 식별값을 **새로 발급**한다. (남이 미리 알아 둔 값으로 로그인 상태를 가로채지 못하게) |

### 안내 문구

화면에 보여 줄 문구 예시입니다. 말투는 "~합니다 / ~해 주세요"로 통일합니다.

| 상황 | 문구 |
|---|---|
| 이메일 형식 오류 | "이메일 형식이 올바르지 않습니다" |
| 이메일 중복 | "이미 가입된 이메일입니다" |

- **로그인 잠금 횟수**를 Redis로 옮길지: 인증번호에 이미 Redis를 쓰므로 만료를 자동으로 처리할 수 있습니다. 지금은 DB 칸으로 적었습니다.
- **메일 발송 수단**: 어떤 메일 서비스로 보낼지 정해야 합니다. 개발 중에는 실제 메일 대신 화면이나 로그에 인증번호를 보여 주는 방법도 있습니다. 이 항목은 "외부 서비스는 쓰지 않는다"는 규칙의 예외입니다.
- **비밀번호 찾기의 새 비밀번호가 이전과 같아도 되는지**(CF-25-6): 잊어버린 사람에게 굳이 막을 이유가 적어 지금은 허용하는 쪽으로 봅니다.

### 인증과 세션

#### 쉬운 설명: 로그인 상태를 어떻게 기억할까? (비전공자용)

**왜 이런 방법이 필요한가**
웹사이트는 요청을 받을 때마다 상대를 **"처음 보는 사람"**으로 취급합니다. 로그인했어도 다음 화면을 열면 서버는 아까 그 사람인지 기억하지 못합니다. 그래서 **"이 사람은 아까 로그인한 그 사람입니다"를 증명하는 방법**이 필요합니다. 크게 두 가지가 있습니다.

**① 세션 방식 = 접수처의 명부 + 번호표**
- 로그인하면 서버(접수처)가 **명부에 내 이름을 적고**, 나에게는 **번호표(세션 번호)**만 줍니다.
- 이후 요청마다 번호표를 보여 주면, 서버가 **명부를 보고** "철수님이네요" 하고 알아봅니다.
- 내 정보는 **서버의 명부**에 있고, 내 손에는 의미 없는 번호만 있습니다.
- 로그아웃하거나 문제가 생기면 서버가 **명부에서 그 줄을 지웁니다. 그 순간 번호표는 쓸모없어집니다.**

**② 토큰(JWT) 방식 = 도장이 찍힌 입장권**
- 로그인하면 서버가 **"철수, 7일 동안 유효"라고 적고 도장을 찍은 입장권(토큰)**을 줍니다.
- 이후 요청마다 입장권을 보여 주면, 서버는 **도장만 확인**하고 통과시킵니다. 명부를 볼 필요가 없습니다.
- 내 정보가 **입장권 안에** 들어 있고, 서버는 기억하지 않습니다.
- 대신 **이미 나눠 준 입장권은 서버가 회수하기 어렵습니다.** 유효기간이 끝날 때까지는 도장이 진짜이기 때문입니다.

```
[세션]  로그인 ──▶ 서버가 명부에 기록 ──▶ 번호표(세션 번호) 전달
        이후 요청: 번호표 제시 ──▶ 서버가 명부에서 확인 ──▶ 통과
        로그아웃: 서버가 명부에서 지움 ──▶ 번호표 즉시 무효

[토큰]  로그인 ──▶ 서버가 입장권(토큰) 발급, 기억은 안 함
        이후 요청: 입장권 제시 ──▶ 서버가 도장만 확인 ──▶ 통과
        로그아웃: 서버가 할 수 있는 일이 없음 ──▶ 입장권은 유효기간까지 살아 있음
```

**한눈에 비교**

| 궁금한 것 | 세션 | 토큰(JWT) |
|---|---|---|
| 내 정보는 어디에 있나? | 서버의 명부 | 입장권(내 손) |
| 로그아웃하면 바로 못 쓰게 되나? | **네. 서버가 명부에서 지움** | 유효기간까지 살아 있음 (막으려면 별도 장치가 필요) |
| 비밀번호를 바꾸면 다른 기기를 끊을 수 있나? | **쉬움.** 그 사람의 명부 줄을 모두 지우면 됨 | 어려움 |
| 만들기 쉬운가? | **쉬움.** Spring의 기본 기능으로 대부분 해결 | 보통~어려움. 발급, 확인, 갱신을 직접 구성 |
| 서버가 여러 대, 서비스가 여러 개일 때 | 명부를 공유해야 해서 번거로움 | **편함.** 도장만 확인하면 됨 |
| 모바일 앱 등 다른 종류의 화면 | 다소 불편 | **편함** |

**우리 프로젝트에 세션이 맞는 이유**
우리가 이미 정한 요구사항과 직접 연결됩니다.

| 우리 요구사항 | 세션이면 | 토큰이면 |
|---|---|---|
| 로그아웃하면 **바로 끊김** (CF-02-11) | 명부에서 지우면 끝 | 입장권을 회수할 방법을 따로 만들어야 함 |
| 비밀번호를 바꾸면 **다른 기기도 끊김** (CF-15-15) | 그 사람의 명부 줄만 지우면 끝 | 어려움 |
| 마지막 사용 후 **7일 유지** (CF-02-10) | 명부의 유효기간만 늘리면 됨 | 짧은 입장권 + 오래가는 재발급권을 **두 종류** 관리해야 함 |
| **서버 1대**로 시작 | 명부를 한 곳에 두면 됨 | 토큰의 큰 장점(여러 서버가 명부 없이 확인)을 쓸 일이 없음 |
| **2주, 혼자** 구현 | 가장 단순함 | 만들 것이 많음 |

토큰으로 위 요구사항을 모두 지키려면, 결국 **"끊어야 할 입장권 목록"을 서버가 다시 기억**해야 합니다. 즉 **토큰의 장점(서버가 기억하지 않아도 됨)을 쓰려다 결국 명부를 만드는 셈**이라서, 처음부터 명부(세션)를 쓰는 편이 단순합니다.

**토큰이 더 좋은 경우도 있습니다 (공정하게)**
- 서버가 여러 대로 나뉘거나, 기능별로 서버를 쪼갠 구조(MSA)일 때
- 모바일 앱이나 다른 회사의 서비스와 같이 쓸 때
- 로그인 확인을 여러 서비스가 각자 해야 할 때

우리는 이 중 어느 것에도 해당하지 않습니다. (단일 서버로 확정)

**자주 묻는 질문**
- **토큰이 더 최신 기술이고 좋은 것 아닌가요?**
  최신이냐 아니냐가 아니라 **쓰임새가 다릅니다.** 서버가 하나이고 "바로 끊기"가 중요한 서비스에는 세션이 더 맞습니다.
- **세션은 서버가 힘들지 않나요?**
  동시에 접속하는 사람이 수만 명이 되면 고민해야 하지만, 우리 규모에서는 문제가 없습니다. 명부는 **DB에 저장**해서 서버를 다시 켜도 로그인이 유지됩니다.
- **둘 중 어느 쪽이 더 안전한가요?**
  어느 쪽이든 **훔치면 위험**합니다. 세션은 훔친 뒤 **서버가 바로 지울 수 있다**는 점이 강점이고, 토큰은 서버가 기억하지 않아 편한 대신 회수가 어렵습니다. 어느 쪽이든 안전하게 쓰는 설정이 필요합니다.
- **번호표(세션 번호)를 누가 훔치면요?**
  번호표를 담는 쿠키에 보호 설정을 합니다. 스크립트가 읽지 못하게 하고(`HttpOnly`), 암호화된 연결에서만 보내고(`Secure`/HTTPS), 다른 사이트가 몰래 쓰지 못하게 합니다(`SameSite`, CSRF 방어). 의심되면 서버가 명부에서 지웁니다. (아래 표의 쿠키 속성, CSRF 방어 참고)

**한 줄 결론**
> 우리 서비스는 **서버가 하나이고, "로그아웃하면 바로 끊김"과 "다른 기기 끊기"가 요구사항에 있어서**, 서버가 명부를 들고 있는 **세션 방식**이 가장 단순하고 안전하게 맞습니다. 토큰(JWT)은 서버가 여러 개로 나뉘거나 모바일 앱을 붙일 때 다시 검토합니다.

**우리가 정한 방식 (기술 표)**

| 저장 | CF-01-8, NF-01 | **BCrypt 해시** (Spring Security `BCryptPasswordEncoder`, 강도 10~12). 원문은 저장하지 않는다 | 되돌릴 수 없고, 같은 비밀번호도 매번 다른 값이 나온다 | 가안 |
| 규칙 검사 | CF-01-4 | 서버에서 정규식으로 검사하고, 화면에서도 같은 규칙으로 안내한다. 정규식: `^(?=.*[A-Za-z])(?=.*\d)(?=.*[!@#$%^&*()_+\-=])[A-Za-z\d!@#$%^&*()_+\-=]{8,10}$` | 화면 검사만으로는 우회할 수 있다 | 가안 |
| 같은 비밀번호 확인 | CF-15-12 | 새 비밀번호를 현재 해시와 비교해서 같으면 거절한다 | | 가안 |
| 길이 한도 | CF-01-4 | BCrypt는 입력 72바이트까지만 쓰므로, 최대 길이를 늘려도 20자 안팎은 문제없다 | 8~10자 제한은 보안상 재검토 대상이다 (이 파일의 '정하지 못한 것' 참고) | 참고 |

### 이메일 인증 (가입 전에 인증)

| 영역 | 연결 ID | 구현 방식 | 이유 | 상태 |
|---|---|---|---|---|
| 흐름 | CF-01-11 ~ 13, 20 | 가입 화면에서 인증번호 받기 → 입력 → 확인을 마친 뒤, 나머지 항목과 함께 `가입하기`를 보낸다. **계정은 마지막에 한 번만 만든다** | 인증하지 않은 계정이 생기지 않는다 | **확정** |
| 발송 | CF-01-11 | **Spring Mail (SMTP)** | 외부 서비스 규칙의 예외 | 가안 |
| 비동기 발송 | CF-01-11, 18 | 메일은 별도 작업으로 보낸다 (`@Async`). 실패하면 CF-01-18 문구를 보여 준다 | 응답이 느려지지 않는다 | 가안 |
| SMTP 서버 | CF-01-11 | **Gmail(앱 비밀번호) 또는 네이버(메일 설정에서 SMTP 사용을 켬)** 중 하나. 개인 계정이라 하루 발송 한도가 있다 | | **미정** |
| 개발 중 발송 | CF-01-11 | 실제 발송 대신 서버 로그에 인증번호를 출력한다 (또는 로컬 테스트용 메일 서버) | 개발 중 메일 한도를 아낀다 | 가안 |
| 인증번호 생성 | CF-01-12, NF-05 | `SecureRandom`으로 6자리를 만든다 (영문 대문자 + 숫자, `O`, `0`, `I`, `1` 제외) | 추측하기 어렵고 읽기 쉽다 | 가안 |
| **인증번호 저장** | CF-01-14, 15 | **Redis**에 `이메일 → 인증번호`로 저장하고 **10분 만료 시간**을 건다. 맞게 입력하면 **즉시 삭제**한다 | 만료와 1회용을 자동으로 지킨다 | **확정** |
| 틀린 횟수 | CF-01-17 | Redis 카운터로 센다. 5회가 되면 그 인증번호를 삭제한다 | 무작위 대입 방지 | 가안 |
| 다시 받기 제한 | CF-01-16 | Redis 키 두 개로 구현한다. "1분" 키(만료 60초)가 있으면 거절하고, "하루" 카운터(만료 24시간)가 5가 되면 거절한다 | | 가안 |
| **인증 완료 표시** | CF-01-13, 20 | 인증번호는 맞으면 삭제되므로, **"이 이메일은 인증됨" 표시를 Redis에 30분만** 남긴다. 가입이 끝나면 삭제한다 | 가입할 때 서버가 인증 사실을 다시 확인하려면 남아 있어야 한다 | 가안 |
| 가입 시점 확인 | CF-01-20 | 가입 요청이 오면 서버가 위 표시가 있는지 확인하고, 없거나 이메일이 다르면 거절한다 | 화면을 건너뛴 요청 방지 | 가안 |
| 이메일 중복 검사 | CF-14-1, CF-01-21 | 인증번호를 보내기 전에 DB에서 확인하고, 가입 시점에도 한 번 더 확인한다. DB의 이메일 칸에는 **중복 불가 제약**을 둔다 | 그 사이에 다른 사람이 가입하는 경우를 막는다 | 가안 |
| Redis에 연결 불가 | CF-01-11 | 인증번호를 보낼 수 없으므로 "잠시 뒤 다시 시도해 주세요"를 보여 준다 | | 가안 |

### 비밀번호 찾기

| 영역 | 연결 ID | 구현 방식 | 이유 | 상태 |
|---|---|---|---|---|
| 흐름 | CF-25-1 ~ 7 | 이메일 인증(가입 전에 인증)과 **같은 흐름, 같은 코드**를 쓴다. 인증번호 받기 → 입력·확인 → 새 비밀번호 입력 → 변경하기 | 새로 만들 것이 적고 **DB에 새 표가 필요 없다** | 가안 |
| 용도 구분 | CF-25-4 | Redis 키에 **용도(가입 / 비밀번호 찾기)**를 붙여 구분한다. 같은 이메일로 가입 중인 인증번호나 인증됨 표시와 섞이지 않는다 | 서로의 인증을 가져다 쓸 수 없게 한다 | 가안 |
| 계정 유무 숨기기 | CF-25-3, NF-06 | 가입된 이메일일 때만 메일을 보내되 **응답과 화면은 똑같이** 만든다. 다시 받기 제한(1분·하루)과 틀린 횟수도 **가입 여부와 상관없이 똑같이** 올린다 | 응답이나 제한 문구의 차이로 가입 여부를 알아내지 못하게 | 가안 |
| 가입 안 된 이메일 | CF-25-3, 5 | 인증번호를 저장하지 않는다. 번호를 입력하면 "인증번호가 올바르지 않습니다"가 나온다 | 화면 흐름은 가입된 이메일과 같게 유지 | 가안 |
| 변경 처리 | CF-25-6 ~ 9 | **한 번의 트랜잭션**으로 회원 표의 해시된 비밀번호를 새 값으로 바꾸고, 연속 실패 횟수와 잠금 해제 시각을 초기화한다 (BCrypt) | 일부만 바뀌는 일을 막는다 | 가안 |
| 모든 기기 로그아웃 | CF-25-8 | 변경 직후 그 회원의 세션을 **전부 삭제**한다 (Spring Session) | 남이 로그인해 둔 상태를 끊는다 | 가안 |

| 알림 메일 | CF-25-10 | 가입 때처럼 `@Async` 로 SMTP 발송한다 | | 가안 (선택) |
| DB 변경 | — | **새 표 없음.** 기존 회원 표의 칸만 쓴다 | | 가안 |
