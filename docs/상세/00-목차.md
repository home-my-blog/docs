# 공통 요구사항 — 상세 (내 기준)

> 2026-10-02 기준입니다. `요구사항-공통.md`의 공통 기능(CF-xx)을 기준으로, **내가 쓸 상세 규칙**까지 적은 개인용 문서입니다. 팀 합의가 필요 없고 자유롭게 고칩니다.
> 한 파일이 너무 길어서 **기능 묶음별 7개 파일**로 나누었습니다. 각 파일은 `쉬운 설명 → 요구사항 → 구현 방식` 순서입니다.
> 내 개인 기능(주제 분류, 커뮤니티, 실시간 인기 검색어 등)은 `요구사항.md`에 있습니다.

## 읽는 법

- **ID**: `CF-05`는 기능, `CF-05-3`은 그 기능의 세부 규칙입니다. 번호는 `요구사항-공통.md`와 같습니다. `BM-xx`는 블로그 관리 기능(새로 붙임), `NF-xx`는 비기능 요구사항입니다.
- **상태**: 각 파트의 제목 줄에 `화면 있음`, `데모`, `화면 없음` 중 하나를 적었습니다.
- **숫자**: 글자 수, 시간, 개수는 **기본값**입니다. 각 파일의 `기본값` 표에 모아 두었고, 고치면 그 표를 같이 고칩니다.
- **큰따옴표(" ")** 안은 화면에 보여 줄 안내 문구 예시입니다. 각 파일의 `안내 문구` 표에 모아 두었습니다.
- **구현 방식**은 각 파일 끝에 기술과 이유를 적고, 요구사항 ID와 연결했습니다. 상태는 확정 / 가안 / 미정으로 표시합니다.
- **요구사항은 "무엇을 할 수 있어야 하는가"만** 적습니다. 어떤 기술로 만들지는 `구현 방식`과 [기술스택-아키텍처.md](../기술스택-아키텍처.md)에만 적습니다.
- 기술은 요구사항을 지키기 위한 수단이므로, 요구사항이 바뀌면 `구현 방식`을 먼저 점검합니다.
- 처음 읽는다면 각 파일의 **`쉬운 설명`**부터 보세요. 용어가 낯설면 아래 `용어`를 봅니다.

## 용어

| 용어 | 뜻 |
|---|---|
| 회원 | 이메일 인증까지 마친 사용자 |
| 블로그 | 회원이 글을 담아 두는 공간. 이 문서에서 "공간"과 같은 말 |

| 블로그 주인 | 그 블로그를 가진 회원 |
| 공개 범위 | 글을 누가 볼 수 있는지 (공개 / 비공개) |
