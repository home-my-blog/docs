# 05. 홈과 찾기: 동작 원리

> 기능 설명은 [기능/05-홈과-찾기.md](../기능/05-홈과-찾기.md)에 있어요. 2026-10-13 코드(develop) 기준이에요.

## 큰 흐름

### 홈 화면 열기

1. 브라우저가 `/`를 열면 `HomePage`(`frontend/src/pages/HomePage.tsx`)가 React Query(서버 데이터를 받아 캐시해 두는 라이브러리)로 `GET /api/home`을 한 번 불러요.
2. 서버의 `HomeController.home`이 `PostQueryService`, `BlogCards`에 일을 나눠 맡겨 아래 값을 한 응답에 담아요.
   - `notices`: 공지 첫 페이지에서 3개
   - `weeklyPopular`: 최근 7일 공개 글 인기순 6개 (`popularPublic(7일 전, 6)`)
   - `popularPosts`: 전체 기간 공개 글 인기순 30개 (`popularPublic(null, 30)`, 추천 후보)
   - `popularDiaries`: 인기 다이어리 5개
   - `blogs`: 최근에 글을 쓴 블로그 6개
   - `featured`, `latestPosts`: 계산은 하지만 화면이 안 써요
3. 모든 값은 PostgreSQL에서 `JdbcClient`(SQL을 직접 쓰는 Spring의 DB 도구)로 읽어요. 인기 점수는 미리 저장해 둔 칸이 없고, 요청 때마다 SQL 안에서 계산해요.
4. 화면은 받은 값으로 공지 띠, 이번 주 인기 글, 추천 글, 인기 다이어리를 그려요. 추천 글은 이때 브라우저가 `popularPosts`와 localStorage의 읽은 기록으로 고르고, 서버에는 아무것도 보내지 않아요.
5. "분야별 글" 칸만 따로 `GET /api/posts?topic=&sort=&page=`를 불러요(`HomeController.feed` → `PostQueryService.publicFeed`). 실시간 인기 검색어 칸은 `GET /api/search/trending`을 5초마다 불러요.

### 검색하기

1. 머리 검색창(`SearchBox`)이나 검색 화면(`SearchPage`)이 `validateQuery`로 먼저 검사해요(앞뒤 빈칸 제거 뒤 2~50자). 맞으면 `/search?q=...&type=all|blog|post`로 이동해요.
2. `SearchPage`가 `GET /api/search?q=&type=&page=`를 불러요.
3. `SearchController.search` → `SearchService.search`가 `KeywordQuery.parse`로 검색어를 다듬고 단어별 LIKE 패턴을 만들어요. 2글자보다 짧으면 `QUERY_TOO_SHORT`(400) 오류를 내요.
4. 다듬은 검색어를 `search_logs` 표에 한 줄 넣어요(검색어, 시각).
5. `type`에 따라 `SearchService.blogs`(블로그)와 `PostQueryService.search`(글)를 불러요. 둘 다 단어마다 `ILIKE ... ESCAPE '\'` 조건을 만들어 `AND`로 이어요.
6. `{ query, type, total, blogs, posts }`를 돌려주고, 화면이 블로그 카드와 글 줄로 그려요.

## 자세히 보기

### 공개 글만 고르는 조건

홈·분야·태그·검색·인기 글·공지는 모두 `PostQueryService.PUBLIC_ONLY` 조건 하나를 붙여요. 글이 `PUBLIC`이고, 다이어리도 공개(`categories.visibility = 'PUBLIC'`)이고, 글쓴이가 탈퇴 신청한 회원이 아니어야 해요. 조건 문자열이 한 곳에만 있어서, 화면마다 공개 규칙이 어긋날 일이 없어요. 반대로 블로그 안 목록과 태그 모음은 보는 사람 기준인 `VISIBLE_TO`를 써요.

### 인기 점수 SQL

`PostQueryService.POPULARITY`는 SQL 조각이에요.

- `p.view_count`(글에 쌓인 전체 조회수)
- `+ 5 ×` 좋아요 수 (`post_likes`, 글쓴이 본인 제외)
- `+ 3 ×` 댓글 단 서로 다른 사람 수 (`count(DISTINCT cm.author_id)`, 본인 제외)
- `+ 4 ×` 책갈피 수 (`bookmarks`, 본인 제외)

이 조각을 `ORDER BY` 안에 넣어서 쓰고, 동점이면 `p.created_at DESC, p.id DESC`로 정해요. 쓰는 곳은 `popularPublic`(이번 주 인기 글, 추천 후보), `publicFeed`의 인기순, `blogPosts`의 인기순, `popularDiaries`(다이어리별 합계 `sum(...)`)예요. 행마다 하위 쿼리(쿼리 안의 쿼리)를 세 번 돌리는 방식이라, 글이 아주 많아지면 느려질 수 있어요. 지금 규모에서는 미리 계산해 저장하는 것보다 단순하고 늘 정확해요.

### 이번 주 인기 글과 분야별 글

`popularPublic(since, limit)`은 `since`가 있으면 `p.created_at >= since`를 붙여요. "이번 주"는 달력의 월~일이 아니라 **지금부터 7일 전**(`clock.nowOffset().minusDays(popularDays)`)이에요. `KoreanClock`은 한국 시간 기준 시계예요.

`publicFeed(topicId, sort, page)`는 분야 코드가 오면 `TopicService.byCode`로 번호를 찾고(없으면 `TOPIC_NOT_FOUND` 404), `sort=popular`이면 인기 점수, 아니면 최신순으로 정렬해요. 페이지는 `PageRequests.page`가 1부터 세고, 범위를 넘는 페이지는 마지막 페이지로 맞춰요. 화면의 `TopicFeed`는 탭·정렬·페이지를 `useSearchParams`로 주소창에 적어서 새로고침해도 유지돼요.

### 인기 다이어리

`PostQueryService.popularDiaries`는 `categories`(다이어리 표)와 `posts`를 `PUBLIC_ONLY` 조건으로 묶고 다이어리별로 `GROUP BY`해요. 그래서 공개 글이 하나도 없는 다이어리는 아예 후보가 안 돼요. 정렬은 다음 순서예요.

1. `SubscriptionService.DIARY_SUBSCRIBERS`: 그 다이어리의 `diary_subscriptions` 수(탈퇴 신청한 회원 제외). 블로그 구독(`subscriptions`)은 세지 않아요.
2. `sum(POPULARITY)`: 그 다이어리 공개 글 인기 점수 합계
3. 공개 글 수, 마지막으로 다이어리 번호

화면의 `PopularDiaries`는 `useDiaryStickers`로 표지 스티커를 따로 받아 그려요.

### 블로그 둘러보기와 블로그 카드

`BlogCards`(`backend/.../home/BlogCards.java`)는 블로그 카드에 필요한 값(이름, 소개, 주인 닉네임과 첫 글자, 분야, 공개 글 수, 마지막 공개 글 날짜)을 한 SQL로 읽어요. `recent(topicId, limit)`는 `last_post_at DESC NULLS LAST`로 정렬해서 글이 없는 블로그는 맨 뒤로 가요. 탈퇴 신청한 회원의 블로그는 `m.deleted_at IS NULL`로 빼요. `cards(ids)`는 검색처럼 번호 목록이 먼저 정해진 경우에 그 순서대로 카드를 만들어 줘요.

### 공지사항

`HomeController.noticePage`가 `myblog.notice.owner-email` 값을 앞뒤 빈칸 제거·소문자로 바꿔요. 회원 이메일도 가입 때 `EmailNormalizer`가 소문자로 저장하니까 대소문자 차이로 놓치지 않아요. 값이 비어 있으면 일부러 아무 회원과도 맞지 않는 `"-"`로 찾아서 빈 목록을 돌려줘요.

`PostQueryService.notices`는 `PUBLIC_ONLY`에 두 조건을 더해요. 다이어리 이름이 `myblog.notice.category-name`(기본 "공지")과 같고, 글쓴이가 그 이메일의 회원이어야 해요. 결과는 최신순 10개씩이에요. `GET /api/notices?page=`가 공지사항 화면용이고, 홈은 같은 함수의 첫 페이지에서 3개만 잘라 써요.

운영에서는 GitHub 저장소 변수 `NOTICE_OWNER_EMAIL`을 `.github/workflows/deploy.yml`이 넘기고, `deploy/deploy.sh`가 값이 있을 때만 서버 env 파일에 적어요.

### 추천 글: readHistory.ts

`frontend/src/lib/readHistory.ts`가 모두 맡아요.

- **기록**: `PostDetailPage`가 글을 받은 뒤 내 글이 아니면(`!post.isAuthor`) `recordRead({ id, blogId, categoryName })`를 불러요. localStorage 키 `sagak.reads.v1`에 배열로 저장해요. 같은 글을 다시 읽으면 예전 줄을 지우고 맨 앞에 넣고, 50개를 넘으면 뒤를 잘라요.
- **끄기**: `setTrackingOff(true)`는 `sagak.reads.off = '1'`을 적고 기록 키를 지워요. 꺼져 있으면 `recordRead`가 바로 돌아가요.
- **고르기**: `recommend(pool, 4, 내 블로그 번호)`가 읽은 블로그 번호 모음과 다이어리 이름 모음을 만든 뒤, 읽은 글과 내 블로그 글을 빼요. 점수는 읽은 블로그면 3, 같은 이름 다이어리면 2를 더해요. 블로그를 몇 번 읽었는지 세긴 하지만 점수에는 "읽은 적 있다"만 써요. 점수가 같으면 원래 후보 순서(인기 순위)를 지켜요. 이유 문구도 여기서 정해요.
- localStorage를 못 쓰는 브라우저에서는 모든 읽기·쓰기를 `try/catch`로 감싸서 오류 없이 빈 기록처럼 동작해요.

`readHistory.test.ts`에 이 규칙의 테스트가 있어요.

### 광고 슬라이드

`AdSlider`(`frontend/src/components/AdSlider.tsx`)는 `window.setInterval`로 `AD_INTERVAL_MS`(5000ms)마다 다음 장으로 넘겨요. 멈춤 여부는 `useRef`(다시 그리지 않고 값만 기억하는 상자)에 두고, 마우스 진입·초점·터치 때 켜요. 슬라이드 내용은 `frontend/src/lib/ads.ts`의 배열이라 서버와 상관없어요. `prefers-reduced-motion`이면 타이머를 아예 만들지 않아요.

### 분야 화면

`GET /api/topics/{code}` → `HomeController.topic`이 분야 정보, 블로그 수(`BlogCards.count`), 공개 글 수(`countPublicInTopic`), 블로그 최대 100개(`BlogCards.recent`), 최신 공개 글 9개(`latestPublicInTopic`)를 모아요. 글은 `posts.topic_id`, 블로그는 `blogs.topic_id`로 걸러요. `BlogCards.count`는 `blogs` 표를 그대로 세서 탈퇴 신청한 회원 블로그도 들어가요. 분야 9개는 `topics` 표(V11 마이그레이션)에 있고 `GET /api/topics`가 `sort_order` 순서로 돌려줘요.

### 태그별 글과 태그 모음

- `GET /api/tags/{name}/posts` → `PostController.tagPosts`가 이름의 앞뒤 빈칸과 앞의 `#`을 떼고, `TagService.key`로 소문자 키를 만들어 `PostQueryService.tagPosts`를 불러요. `post_tags`와 `tags.name_key`로 글을 찾고 `PUBLIC_ONLY`, 최신순, 10개씩이에요. 응답의 `tag`는 다듬은 이름 그대로예요.
- `GET /api/blogs/{blogId}/tags` → `PostQueryService.blogTags`는 `VISIBLE_TO`(보는 사람 기준) 조건으로 태그별 글 수를 세고 `count DESC, name` 순으로 12개를 줘요. 화면(`BlogShell`)은 태그를 누르면 `?tag=이름`으로 블로그 글 목록(`GET /api/blogs/{id}/posts?tag=`)을 걸러요.

### 검색어 다듬기와 이스케이프

`KeywordQuery.parse`가 하는 일이에요.

1. `strip()`, `\s+`를 빈칸 하나로, `toLowerCase`.
2. 길이는 글자 수(code point)로 세요. 2보다 짧으면 오류, 50보다 길면 앞 50자로 자르고 다시 빈칸을 정리해요.
3. 빈칸으로 나눠 단어마다 `escape`로 `\`→`\\`, `%`→`\%`, `_`→`\_`를 바꾼 뒤 `%단어%`로 감싸요.

이스케이프(특수 글자를 보통 글자로 바꾸는 것)를 하지 않으면 `%`나 `_`가 LIKE의 "아무 글자" 뜻으로 해석돼서 엉뚱한 결과가 나와요. SQL에는 `ESCAPE '\'`를 붙여 역슬래시가 이스케이프 글자임을 알려 줘요. 값은 `:w0`, `:w1` 같은 이름 붙은 매개변수로 넘겨서 SQL 주입도 막아요.

글 검색 조건은 단어마다 `(제목 OR 본문 OR 다이어리 이름 OR 블로그 이름 OR 분야 이름)`이고, 이 묶음을 단어 수만큼 `AND`로 이어요. 블로그 검색은 `(블로그 이름 OR 주인 닉네임 OR 소개 OR 분야 이름 OR EXISTS(그 블로그 다이어리 이름))`이에요. `ILIKE`는 대소문자를 가리지 않는 LIKE예요. 블로그 결과는 번호만 먼저 `b.id DESC`로 페이지만큼 뽑고, `BlogCards.cards`로 카드를 채워요.

`type=all`이면 블로그와 글 둘 다 1페이지만 계산하고, `blog`나 `post`면 그쪽만 요청한 페이지로 계산하고 다른 쪽은 빈 결과를 넣어요.

### pg_trgm 색인

`V1__core_schema.sql`이 `pg_trgm` 확장(글을 세 글자 조각으로 나눠 색인하는 PostgreSQL 기능)을 만들고, 글 제목과 본문에 `gin_trgm_ops` GIN 색인(`idx_posts_title_trgm`, `idx_posts_body_trgm`)을 만들어요. 이 색인은 `ILIKE '%단어%'`처럼 가운데 일치 검색도 도울 수 있어요. 확장을 만들 권한이 없는 DB에서는 경고만 남기고 색인 없이 넘어가요(검색은 그대로 동작하고 느려질 뿐이에요). 블로그 이름·닉네임·다이어리 이름에는 이런 색인이 없어요. 실제로 색인을 쓸지는 PostgreSQL 실행 계획이 정하는데, 다른 칸과 `OR`로 묶여 있어 표를 다 읽는 쪽을 고를 수도 있어요.

### 검색 기록과 정리

`search_logs`는 `id`, `keyword`(최대 50자), `searched_at` 세 칸뿐이고 `searched_at`에 색인이 있어요. 회원 번호는 없어요. `SearchService.search`는 검사를 통과한 요청마다 한 줄 넣어요. 화면에서 페이지·범위를 바꾸면 요청이 새로 가므로 그만큼 더 기록돼요.

`SearchService.purgeOldLogs`는 `@Scheduled(cron = "0 30 4 * * *", zone = "Asia/Seoul")`로 매일 새벽 4시 30분에 `myblog.search.log-retention`(30일)보다 오래된 줄을 지워요.

### 실시간 인기 검색어: TrendingService

`TrendingService.refresh`는 `@Scheduled(fixedRateString = "${myblog.trending.interval}")`로 5초마다 돌아요. `synchronized`라 한 번에 하나만 돌아요.

1. **조회 모으기**: 글 조회가 세질 때 `ViewRecorder.record`가 `TrendingService.recordView(postId)`를 불러요. 시각과 글 번호를 메모리의 `ConcurrentLinkedDeque`(여러 스레드가 함께 써도 안전한 양쪽 끝 큐)에 넣어요. `refresh`는 먼저 24시간보다 오래된 것을 앞에서부터 버려요.
2. **검색 수**: `search_logs`에서 최근 24시간을 검색어별로 `count(*)`.
3. **조회 수**: 큐에서 글별 조회 수를 세고, 그 글들 중 `PUBLIC_ONLY`인 것의 소문자 제목을 읽어요.
4. **댓글 수**: 최근 24시간에 공개 글에 달린 댓글마다 그 글의 소문자 제목을 읽어요(댓글 하나가 1개).
5. **점수**: 검색어마다 단어를 빈칸으로 나눠, 제목이 모든 단어를 포함하는(`containsAll`) 글의 조회 수와 댓글 수를 더해요. `검색 수 × 3 + 조회 × 1 + 댓글 × 5`.
6. **순위**: 점수 내림차순, 같으면 검색어 가나다순으로 10개.
7. **변화 표시**: 직전 계산의 순위표(`previousRanks`)와 비교해 `NEW`/`UP`/`DOWN`/`SAME`과 칸 수(`delta`)를 붙여요. 10위 밖으로 나갔다 들어오면 다시 `NEW`예요.
8. 결과를 `AtomicReference<Snapshot>`(값을 통째로 안전하게 바꿔 끼우는 상자)에 넣어요. `GET /api/search/trending`은 이 값을 그대로 돌려줘서 DB에 가지 않아요.

화면의 `useTrending`(`frontend/src/api/queries.ts`)은 `/api/config`의 `trendingIntervalSeconds`(5)마다 다시 불러요. `TrendingList`는 `useLayoutEffect`에서 줄마다 이전 위치와 새 위치를 비교해 `element.animate`로 450ms 동안 미끄러지게 해요(FLIP 기법). 순위 변화는 서버가 계산한 값을 그대로 써요.

### 알려진 한계

- 조회 큐와 직전 순위는 서버 메모리라, 배포(블루-그린으로 새 서버로 전환)하면 새 서버는 빈 상태에서 시작해요. 첫 계산에서 모든 단어가 `NEW`가 되고 그 전 조회는 빠져요.
- `ViewRecorder`는 Redis로 30분 중복 조회를 거르는데, Redis가 꺼지면 조회를 세지 않아서 `recordView`도 불리지 않아요.
- 서버가 두 대 이상 동시에 일을 받는다면 서버마다 다른 순위를 갖게 돼요. 지금은 nginx가 한 번에 한 서버로만 보내서 문제가 안 돼요.

## 왜 이렇게 만들었나

- **검색에 pg_trgm + ILIKE**: `specs/001-blog-core/research.md` 7장에 따르면, 한국어는 PostgreSQL 전문 검색(`tsvector`)에 형태소 분석기가 없어서 쓰지 않았고, Elasticsearch는 기술 스택에서 뺐어요. 트라이그램 색인이면 한국어 부분 일치도 색인을 탈 수 있어요. 확장을 만들 권한이 없는 DB에서도 서버가 켜지도록 V1에서 예외를 잡아 넘어가게 했어요(CHANGELOG에 기록).
- **단어 AND, 이스케이프**: 같은 문서의 결정이에요. 검색어를 빈칸으로 나눠 각 단어 `ILIKE`를 `AND`로 묶고, `%`·`_`·`\`는 이스케이프해요.
- **인기 검색어를 메모리에, 5초마다**: research.md 8장에서 서버가 1대라 메모리(`AtomicReference`)로 충분하고, 서버를 다시 켜도 첫 계산에서 복구된다고 정했어요. Redis Sorted Set은 서버가 여러 대일 때, WebSocket 푸시는 쓰지 않기로 했어요. 화면은 5초마다 가져가요(폴링).
- **1시간에서 24시간으로**: 처음에는 최근 1시간이었는데, CHANGELOG v1.6.1에서 "사람이 적을 때도 순위가 금방 비지 않게" 24시간으로 바꿨어요.
- **추천을 브라우저에서**: `readHistory.ts` 주석대로, 읽은 기록은 이 브라우저에만 남고 서버로 보내지 않아요. 서버는 인기 글 후보만 주고, 개인 기록은 사용자가 지우거나 끌 수 있어요.
- **댓글은 사람 수로**: `POPULARITY` 주석대로 한 사람의 댓글 여러 개를 한 명으로 세서, 댓글 도배로 점수를 올릴 수 없게 했어요.

## 공부 키워드

- `pg_trgm` / trigram index: 세 글자 조각으로 부분 일치 검색을 빠르게 하는 PostgreSQL 확장
- GIN index: 값 하나에 여러 조각이 있는 데이터를 색인하는 PostgreSQL 색인 종류
- `ILIKE` / `LIKE ESCAPE`: 대소문자 무시 패턴 검색과 특수 글자 이스케이프
- SQL 하위 쿼리(correlated subquery): 행마다 다시 도는 쿼리 안의 쿼리
- Spring `@Scheduled` (`fixedRate`, `cron`, `zone`): 정해진 주기·시각에 메서드 실행
- `AtomicReference`, `ConcurrentLinkedDeque`: 여러 스레드가 안전하게 함께 쓰는 자바 도구
- 슬라이딩 윈도우(sliding window): "최근 24시간"처럼 계속 움직이는 기간으로 세기
- React Query `refetchInterval`: 일정 간격으로 서버 데이터를 다시 받는 폴링
- localStorage: 브라우저에 사이트별로 남는 작은 저장소
- FLIP 애니메이션: 이전 위치와 새 위치 차이로 목록 이동을 부드럽게 보여 주는 기법
