# 08. 운영과 배포: 동작 원리

> 기능 설명은 [기능/08-운영과-배포.md](../기능/08-운영과-배포.md)에 있어요. 2026-10-13 코드(develop) 기준이에요.

## 큰 흐름

### 흐름 1. 코드가 사이트에 올라가기까지

1. 기능 브랜치에서 PR을 올리면 `.github/workflows/ci.yml`이 `pull_request` 이벤트로 돌아요. backend와 frontend 두 작업(job)이 따로따로 동시에 돌아요.
2. develop을 main으로 합치면 `.github/workflows/deploy.yml`이 `push`(main) 이벤트로 시작해요.
3. deploy의 첫 작업 `ci`는 `uses: ./.github/workflows/ci.yml`로 같은 검사를 다시 불러요(`workflow_call`). 두 번째 작업 `deploy`는 `needs: ci`라서 검사가 통과해야만 시작해요.
4. `docker build -t myblog:<커밋 sha> .`로 이미지를 만들고 `docker save ... | gzip`으로 `myblog-image.tar.gz` 파일에 담아요.
5. `appleboy/scp-action`이 SSH 아이디·비밀번호로 서버에 접속해 이미지 파일과 `deploy/deploy.sh`를 `~/myblog-deploy`에 올려요.
6. `appleboy/ssh-action`이 서버에서 `./deploy/deploy.sh <이미지 파일> <sha>`를 실행해요. DB 정보 Secrets와 `NOTICE_OWNER_EMAIL` 변수는 `envs`로 환경변수가 되어 스크립트에 넘어가요.
7. `deploy.sh`가 블루-그린으로 새 서버를 띄우고 nginx를 돌려요(흐름 2). 끝나면 이미지 압축 파일을 지워요.

### 흐름 2. deploy.sh 한 번이 하는 일

1. `docker load`로 이미지를 불러오고, 네트워크 `myblog-net`이 없으면 만들어요.
2. `myblog-redis` 컨테이너가 있으면 `start`, 없으면 `redis:7`로 새로 띄워요(`--restart unless-stopped`).
3. `~/myblog-data/app.env`를 다시 써요. 그리고 nginx 설정 `~/myblog-data/proxy/conf.d/default.conf`에서 `myblog-blue`나 `myblog-green` 글자를 찾아 지금 색(ACTIVE)을 알아내요. blue면 새 색(NEXT)은 green, 아니면 blue예요.
4. NEXT 이름의 컨테이너를 지우고 새 이미지로 띄워요. 바깥 포트는 열지 않고 `myblog-net` 안에서만 보여요.
5. 3초 간격으로 최대 60번, 같은 네트워크에 nginx 이미지를 잠깐 띄워 `wget http://<NEXT>:8390/api/topics`를 보내요. 성공하면 다음 단계로 가요.
6. 실패하면(60번 다 실패했거나 새 컨테이너가 도중에 죽음) 새 서버 로그 80줄을 찍고 새 서버만 지운 뒤 `exit 1`. nginx는 건드리지 않았으니 사이트는 옛 서버 그대로예요.
7. 성공하면 nginx 설정을 백업(`.bak`)하고 `proxy_pass http://<NEXT>:8390`으로 다시 써요. `nginx -t`로 문법을 검사하고 `nginx -s reload`로 다시 읽어요.
8. 옛 서버가 있으면 2초 기다린 뒤 `docker stop -t 35`로 끄고 지워요. Spring은 graceful shutdown으로 하던 요청을 마치고 내려가요.
9. `docker image prune -f`로 안 쓰는 이미지를 지워요.

## 자세히 보기

### 브랜치 전략: 간소화한 Git Flow
- main은 "지금 사이트에 있는 코드", develop은 "다음 배포에 들어갈 것을 모으는 곳"이에요. 기능은 `feature/*` 브랜치에서 만들어 develop으로 PR을 보내요.
- `deploy.yml`의 트리거가 `push: branches: [main]`뿐이라, develop에 아무리 합쳐도 배포되지 않아요. main에 들어가는 것이 곧 배포 버튼이에요.
- 원래 Git Flow의 hotfix는 main에서 갈라 고친 뒤 main과 develop 두 곳에 합치는 브랜치예요. 이 저장소에는 hotfix 규칙이나 hotfix 브랜치가 없고, 고치는 것도 `fix/session-cookie`처럼 브랜치를 따서 develop을 거쳐 main으로 갔어요.

### CI: 테스트에 진짜 DB와 Redis를 쓰는 이유
- backend 작업은 GitHub Actions의 `services`로 `postgres:16`(DB 이름 `myblog_test`, 비밀번호 postgres)과 `redis:7`을 띄워요. `--health-cmd`(`pg_isready`, `redis-cli ping`)로 준비될 때까지 기다린 뒤 테스트를 시작해요.
- 테스트는 `@ActiveProfiles("test")`(`support/IntegrationTest`)로 `application-test.yml`을 더 읽어요. DB는 `TEST_DB_URL` 기본 `jdbc:postgresql://localhost:5432/myblog_test`, Redis는 1번 DB를 써서 개발용 0번과 섞이지 않아요.
- 테스트 설정은 `SessionAutoConfiguration`을 빼요. 대부분의 테스트는 가짜 세션(MockHttpSession)을 쓰고, Redis 세션은 `RedisSessionIT`에서 따로 확인해요.
- frontend 작업의 `npm run build`는 `tsc --noEmit -p . && vite build`예요. 타입 검사를 한 번 더 하고 실제 빌드가 되는지 봐요.

### CD: concurrency로 배포 줄 세우기
- `deploy.yml`에 `concurrency: group: deploy, cancel-in-progress: false`가 있어요. 같은 group의 실행은 한 번에 하나만 돌아요.
- `cancel-in-progress: false`라서 돌던 배포를 중간에 끊지 않아요. 새 실행은 앞 배포가 끝날 때까지 기다려요. 배포를 도중에 끊으면 블루-그린 전환이 반쯤 된 채로 남을 수 있어서예요. (GitHub의 concurrency는 기다리는 실행을 하나만 두기 때문에, 그 사이에 여러 번 합치면 기다리던 것 중 앞의 것은 취소되고 마지막 것만 남아요.)
- 이미지 태그는 커밋 sha예요. 서버에서 `myblog:<sha>`로 어느 커밋이 떠 있는지 알 수 있어요.

### Dockerfile: 화면과 서버를 상자 하나에
- 1단계 `node:22-alpine`에서 `npm ci`, `npm run build`로 화면을 빌드해요.
- 2단계 `eclipse-temurin:21-jdk`에서 화면 결과 `dist/`를 `src/main/resources/static/`에 복사하고 `./gradlew bootJar -x test`로 jar를 만들어요. 테스트는 CI에서 이미 돌렸으니 건너뛰어요.
- 3단계 `eclipse-temurin:21-jre`에 jar만 담아요. `TZ=Asia/Seoul`, `SERVER_PORT=8390`, `MYBLOG_IMAGE_DISK_PATH=/data/images`를 환경변수로 박아 둬요.
- 그래서 Spring이 `/api`도 화면 파일도 함께 내려줘요. nginx는 받은 요청을 앱으로 넘기기만 해요.

### deploy.sh: 왜 그 순서인가
- **새 서버를 먼저 띄우고 확인한 뒤에 nginx를 돌려요.** 순서를 거꾸로 하면 새 서버가 고장 났을 때 사이트가 꺼져요. 지금 순서에서는 실패해도 옛 서버가 계속 손님을 받아요.
- **지금 색은 nginx 설정 파일로 알아요.** 따로 상태 파일을 두지 않고, 실제로 손님을 보내는 곳이 적힌 `default.conf`를 믿어요. 파일이 없으면(처음) ACTIVE는 비고 NEXT는 blue예요.
- **확인을 nginx 이미지의 wget으로 해요.** 새 서버는 바깥 포트가 없어서 서버 주인 컴퓨터에서 `curl localhost`로는 닿지 않아요. 같은 네트워크에 일회용 컨테이너(`--rm`)를 띄워 컨테이너 이름으로 불러요.
- **`/api/topics`를 확인 주소로 써요.** 로그인 없이 DB에서 분야 목록을 읽어 오는 요청이라, 응답이 오면 서버가 켜졌고 DB 연결과 Flyway까지 끝났다는 뜻이에요.
- **새 컨테이너가 죽으면 바로 멈춰요.** 기다리는 중에 `docker inspect`로 `State.Running`을 보고, false면 60번을 다 채우지 않고 실패로 가요.
- **nginx 설정은 검사 후 적용해요.** `nginx -t`가 실패하면 `.bak`으로 되돌리고 새 서버를 지워요. `nginx -s reload`는 nginx를 끄지 않고 설정만 다시 읽어서, 이미 연결된 요청은 옛 서버로 마저 가고 새 요청부터 새 서버로 가요.
- **처음 한 번(nginx가 없을 때)만 끊겨요.** 예전에는 `myblog` 컨테이너가 8390을 직접 잡고 있었어요. 이 컨테이너를 지우고 `myblog-proxy`를 `-p 8390:8390`, 설정 폴더를 읽기 전용(`:ro`)으로 띄우는 1~2초 동안만 끊겨요.
- **옛 서버는 2초 뒤에 꺼요.** reload 직후 아직 옛 서버로 가던 요청이 들어갈 틈을 줘요. `docker stop -t 35`는 SIGTERM을 보내고 35초까지 기다렸다가 그래도 안 꺼지면 강제로 꺼요.
- **graceful shutdown**: `application.yml`의 `server.shutdown: graceful` 덕분에 Spring은 SIGTERM을 받으면 새 요청은 안 받고 하던 요청을 끝낸 뒤 꺼져요. Spring의 기본 대기 시간(30초)이 docker의 35초보다 짧게 맞물려요.
- **docker 권한**: `docker info`가 안 되면 `sudo -n docker info`를 시도해요. `-n`은 비밀번호를 묻지 않는다는 뜻이라, 비밀번호 없는 sudo가 아니면 바로 안내 문구와 함께 멈춰요.
- **DB가 같은 서버에 있을 때**: `DB_ADDRESS`가 `localhost`나 `127.0.0.1`이면 컨테이너 안에서는 자기 자신을 가리키게 돼요. 그래서 `host.docker.internal`로 바꾸고 `--add-host=host.docker.internal:host-gateway`를 붙여요. 운영 DB는 외부 서버라 이 경로는 쓰이지 않아요.

### app.env: 운영 설정이 앱에 들어가는 길
- `deploy.sh`가 `umask 077`(주인만 읽기·쓰기)로 `app.env`를 써요. 들어가는 값은 `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `SPRING_FLYWAY_SCHEMAS`, `REDIS_HOST=myblog-redis`, `REDIS_PORT=6379`, 그리고 값이 있을 때만 `NOTICE_OWNER_EMAIL`이에요.
- `DB_URL`은 `jdbc:postgresql://<주소>:<포트>/<DB>?currentSchema=<스키마>,public`이에요. 내 스키마를 먼저 찾고 없으면 public을 찾아요. Flyway도 `SPRING_FLYWAY_SCHEMAS`로 내 스키마에 표를 만들어요.
- 앱 컨테이너는 `--env-file`로 이 파일을 읽어요. Spring은 `DB_URL` 같은 환경변수를 `application.yml`의 `${DB_URL:...}` 자리에 넣어요.
- 메일 관련 값(`MYBLOG_MAIL_MODE`, `SMTP_*`, `MAIL_FROM`)과 `SESSION_SECURE_COOKIE`는 이 목록에 없어요. 그래서 운영은 기본값인 log 모드, Secure 없는 쿠키로 돌아요.

### 설정 읽는 순서: 프로필 없이 하나로
- `application.yml`의 `spring.config.import: optional:file:../.env[.properties],optional:file:./.env[.properties]`가 `.env`를 properties 파일처럼 읽어요. `backend`에서 실행하면 `../.env`(저장소 루트)를, 루트에서 실행하면 `./.env`를 찾아요. `optional:`이라 없어도 오류가 나지 않아요.
- 값을 쓰는 곳은 `${환경변수:기본값}` 꼴이에요. 예를 들어 `myblog.mail.mode: ${MYBLOG_MAIL_MODE:log}`. 환경변수나 `.env`에 있으면 그 값, 없으면 기본값이에요.
- 그 밖의 숫자 규칙은 `myblog.*` 아래에 기본값으로 있고, `MyBlogProperties`(`@ConfigurationPropertiesScan`)가 읽어요.
- `SERVER_PORT`처럼 yml에 없는 값도 Spring의 느슨한 이름 맞추기(relaxed binding)로 `server.port`가 돼요. Dockerfile이 이것으로 8390을 줘요.

### 로컬 개발: Vite 프록시
- `frontend/vite.config.ts`는 개발 서버를 5173에 띄우고, `/api`로 시작하는 요청을 `MYBLOG_API_TARGET`(기본 `http://localhost:8080`)으로 넘겨요. `changeOrigin: false`라서 Host 헤더를 바꾸지 않아요.
- 브라우저 입장에서는 화면과 API가 같은 주소(5173)라 쿠키와 CSRF 토큰이 운영과 똑같이 동작해요. 운영도 Spring이 화면과 API를 같은 주소로 내려줘요.
- `docker-compose.yml`에는 `db`(postgres:16, 사용자·DB 이름 myblog, 비밀번호는 `.env`의 `DB_PASSWORD`), `redis`(redis:7), `minio`가 있어요. minio는 `profiles: ["minio"]`라서 `--profile minio`를 줘야만 떠요. 서버와 화면은 컨테이너에 넣지 않아요.

### 시간 맞춰 도는 일 4개
`MyBlogApplication`의 `@EnableScheduling`이 `@Scheduled`가 붙은 메서드를 찾아 돌려요.

| 메서드 | 언제 | 하는 일 |
|---|---|---|
| `TrendingService.refresh` | `fixedRateString = ${myblog.trending.interval}` (5초) | 24시간 안의 검색 기록(DB)과 조회 기록(메모리)으로 점수를 계산해 메모리의 순위를 바꿔요 |
| `ImageService.cleanOrphans` | `fixedDelay = 3_600_000, initialDelay = 60_000` | 글·대표 사진·임시저장 어디에도 안 쓰인 채 24시간 지난 사진을 DB에서 지우고, 커밋 뒤 파일도 지워요 |
| `SearchService.purgeOldLogs` | `cron = "0 30 4 * * *"`, Asia/Seoul | `search_logs`에서 30일 지난 줄을 지워요 |
| `WithdrawalCleaner.scheduled` | `cron = "0 40 4 * * *"`, Asia/Seoul | 탈퇴 30일 지난 회원을 한 명씩 각자 트랜잭션으로 익명화해요 |

- `fixedRate`는 시작 시각 기준 간격, `fixedDelay`는 앞 실행이 끝난 뒤부터의 간격이에요.
- 배포 중 블루와 그린이 잠깐 같이 떠 있으면 두 서버 모두 이 일을 돌려요. 따로 잠금(ShedLock 같은)은 없어요. 서버가 평소 한 대라서 따로 두지 않았어요(`TrendingService` 주석의 "서버 1대").

### RedisGuard: required와 optional
- `common/RedisGuard`에는 메서드가 두 개 있어요. 둘 다 Redis 호출을 감싸고 `DataAccessException`(Redis 연결 실패 등)을 잡아요.
- `required`: 경고 로그를 남기고 `ApiException(SERVICE_UNAVAILABLE)`을 던져요. 응답은 503 "잠시 뒤 다시 시도해 주세요"예요. `EmailVerificationService`의 인증번호 보내기·확인하기·확인됐는지 보기에 써요.
- `optional`: 경고 로그를 남기고 빈 값(`Optional.empty()`)을 돌려줘요. 부르는 쪽이 `orElse`로 기본값을 정해요.
  - `ViewRecorder`의 조회수 중복 막기와 방문자 세기는 `orElse(false)`라서, Redis가 없으면 새 조회로 치지 않아요(숫자가 안 늘어요).
  - `CommentService`의 댓글 5초 막기와 `EmailVerificationService.preventDuplicate`(5초 중복 제출 막기)는 `orElse(true)`라서, Redis가 없으면 그냥 통과시켜요.
  - 인증 끝난 표시 지우기(`consume`)도 optional이에요.
- Redis 연결 제한 시간은 `spring.data.redis.timeout: 1s`라서, 꺼져 있어도 요청이 1초 넘게 붙잡히지 않아요.
- 세션은 RedisGuard를 거치지 않아요. Spring Session이 요청마다 Redis에서 세션을 읽기 때문에, Redis가 꺼지면 세션을 쓰는 요청이 오류가 나요. 로그인 없이 읽는 글은 세션이 필요 없어서 돼요.

### Flyway: 번호 붙은 SQL만으로 DB 바꾸기
- `spring.flyway.enabled: true`. 서버가 켜질 때 Flyway가 `db/migration`의 `V숫자__이름.sql`을 번호 순서로 보고, DB의 기록 표(`flyway_schema_history`)에 없는 것만 실행해요.
- 실행한 파일의 체크섬(내용 지문)도 기록해요. 이미 실행한 파일을 고치면 지문이 달라져 검증에서 서버가 안 켜져요. 그래서 고치지 않고 새 번호를 더해요. 예: "미분류" 다이어리 이름을 "일기장"으로 바꾼 것도 V20으로 새로 더했어요.
- 지금 V1~V20 중 V14·V15가 비어 있어요. 운영 DB에 V16이 먼저 적용된 뒤 V14·V15가 들어오자, 기본 설정은 이미 지난 번호를 허용하지 않아 검증이 실패했어요. 두 파일은 운영에 적용된 적이 없어서 V17·V18로 이름만 바꿨어요(커밋 "구독 마이그레이션 번호를 V16 뒤로 옮겨 배포 실패를 고친다").
- V1은 `pg_trgm` 확장을 만들 권한이 없으면 `RAISE NOTICE`만 하고 넘어가요. Crowfoot DB처럼 스키마 안에서만 권한이 있는 곳에서도 배포가 되게 하려고요.
- 블루-그린과의 관계: 새 서버가 뜨면서 Flyway를 돌리는 순간에도 옛 서버는 같은 DB로 손님을 받아요. 컬럼을 지우면 옛 서버의 SQL이 깨져요. 그래서 "새 코드가 옛 컬럼을 안 쓰게 배포 → 다음 배포에서 컬럼 삭제"로 두 번에 나눠요.

### 메일 모드: 빈 하나만 고르기
- `MailSender` 인터페이스에 구현이 둘 있어요. `LogMailSender`는 `@ConditionalOnProperty(name = "myblog.mail.mode", havingValue = "log", matchIfMissing = true)`, `SmtpMailSender`는 `havingValue = "smtp"`예요. 설정값에 따라 하나만 만들어져요.
- `LogMailSender.send`는 `[메일] to=... subject=...`와 본문을 로그에 찍고, `isAvailable`은 항상 true예요.
- `SmtpMailSender.isAvailable`은 `testConnection`으로 SMTP 서버에 붙어 보고, 실패하면 인증번호 보내기가 `MAIL_SEND_FAILED`(503)가 돼요. `send`는 `@Async("mailExecutor")`라 따로 스레드(`AsyncConfig`, 2~4개, 대기 100개)에서 보내고, 실패는 로그만 남겨요.
- 운영이 log인 이유는 `deploy.sh`가 쓰는 `app.env`에 `MYBLOG_MAIL_MODE`가 없어서 `matchIfMissing`·기본값 log가 쓰이기 때문이에요.

### status.yml: 세 곳에서 보기
- **서버 안**: ssh로 들어가 `docker ps -a --filter name=myblog`, `curl localhost:8390/api/topics`(nginx를 거친 응답), `default.conf`에서 active 색, 그 컨테이너 로그 20줄. active를 못 찾으면 예전 이름 `myblog`의 로그를 봐요.
- **바깥**: GitHub 러너에서 `http://<SSH_ADDRESS>:8390/api/topics`. 서버 안은 되는데 바깥이 안 되면 방화벽·포트 문제예요.
- **공개 주소**: 입력한 URL로 `/`, `/api/topics`, `/api/search?q=a`. 도메인 연결과 화면 파일까지 확인해요.

### release.yml: CHANGELOG를 Release로
- `push`(main) 중 `paths: [CHANGELOG.md]`가 바뀐 경우에만 돌아요. `contents: write` 권한과 `fetch-depth: 0`(커밋 전체)을 써요.
- 파이썬이 `^## (v\d+\.\d+\.\d+)[ \t]*(.*)$` 정규식으로 버전·제목·본문을 나누고, `gh release list`로 이미 있는 태그를 빼요.
- 오래된 버전부터 만들어서 맨 위 버전이 마지막에 `--latest=true`가 돼요. `<!-- commit: ... -->`가 있으면 그 커밋에, 없으면 HEAD에 태그를 붙여요. 주석은 노트에서 지우고 `###` 제목은 `##`로 한 단계 올려요.

| 비밀값(SSH, DB) | GitHub Secrets | 사람이 지울 때 |
| `NOTICE_OWNER_EMAIL` | GitHub Variables → 서버 `~/myblog-data/app.env` | 배포 때마다 다시 써요 |
| 앱 설정 | 서버 디스크 `~/myblog-data/app.env` | 배포 때마다 다시 써요 |
| 지금 일하는 색 | 서버 디스크 `~/myblog-data/proxy/conf.d/default.conf` | 배포 때마다 다시 써요 |
| 회원 사진 | 서버 디스크 `~/myblog-data/images` (컨테이너 `/data/images`) | 정리 작업이 지울 때 |

| 로그인 세션 | Redis `myblog:session` 키 (`myblog-redis` 컨테이너) | 7일 안 쓰면, 또는 Redis 컨테이너를 새로 만들 때 |
| 인증번호, 조회 중복, 댓글 5초 | Redis 키 | 각자 TTL(10분, 30분, 5초 등) |
| 인기 검색어 순위, 최근 조회 기록 | 서버 메모리 (`TrendingService`) | 서버를 바꿀 때(배포) |
| 배포용 이미지 압축 파일 | 서버 `~/myblog-deploy/myblog-image.tar.gz` | 배포 끝나면 바로 |
| 로컬 비밀값 | 내 컴퓨터 `.env` (Git에 안 올림) | 내가 지울 때 |
| 로컬 DB 데이터 | 도커 볼륨 `db-data` | `docker compose down -v` 할 때 |

## 왜 이렇게 만들었나

- **블루-그린 + Redis 세션**: 예전에는 옛 서버를 끄고 새 서버를 켜서 몇 초씩 끊겼고, 세션이 서버 메모리에 있어 배포할 때마다 모든 회원이 로그아웃됐어요. 새 버전이 안 뜨면 사이트가 꺼진 채로 남기도 했어요. 세션을 Redis로 옮기고 nginx 뒤에 두 서버를 번갈아 두었어요. README에 따르면 0.2초마다 요청을 보내며 배포해 봤을 때 끊김이 0번이었고, 일부러 고장 낸 버전을 배포해도 옛 서버가 사이트를 지켰어요. 대가는 "DB 변경 두 번에 나누기"예요. (README 기술적 의사결정 2)
- **Git Flow 간소화**: 자잘한 수정을 하나씩 배포하면 배포가 너무 잦고 느려서, develop에 모았다가 한 번에 main으로 보내요. (README 기술적 의사결정 7)
- **비밀값은 Secrets에**: 저장소가 공개라서 비밀번호를 코드에 둘 수 없어요.
- **Redis를 required/optional로 나눔**: 인증번호는 Redis 없이 할 방법이 없지만, 조회수 중복 막기는 잠깐 틀려도 큰일이 아니에요. 덜 중요한 기능 때문에 글 읽기까지 막히지 않게 했어요. (README 기술적 의사결정 3)
- **화면과 서버를 이미지 하나로**: 배포 단위가 하나라 버전이 어긋날 일이 없고, 같은 주소라 쿠키를 그대로 써요. (research.md §14)
- **Flyway 번호 파일**: 어느 서버(로컬, CI, 운영)에서든 같은 순서로 같은 구조가 만들어져요.
- **메일 log 모드 기본값**: 개발 중에 진짜 메일 없이도 가입을 끝까지 해 볼 수 있어요. 운영에 SMTP를 넣는 일은 아직 하지 않았어요.

## 공부 키워드

- **Git Flow**: main/develop/feature/hotfix로 나누는 브랜치 전략
- **GitHub Actions workflow_call, concurrency**: 워크플로 재사용과 동시 실행 막기
- **블루-그린 배포(Blue-Green Deployment)**: 두 벌을 번갈아 쓰는 무중단 배포
- **nginx reverse proxy, nginx -s reload**: 요청 넘기기와 끊김 없는 설정 다시 읽기
- **Spring Boot graceful shutdown, SIGTERM**: 하던 요청 끝내고 꺼지기
- **Docker multi-stage build**: 빌드용과 실행용 이미지를 나누기
- **Docker network, --env-file, volume**: 컨테이너끼리 이름으로 부르기, 설정 넣기, 데이터 남기기
- **Flyway migration, checksum, outOfOrder**: DB 구조 버전 관리
- **Expand and Contract 패턴**: 컬럼 변경을 두 번에 나누는 방법
- **Spring @Scheduled (cron, fixedRate, fixedDelay)**: 시간 맞춰 도는 일
