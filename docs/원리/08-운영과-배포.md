# 08. 운영과 배포: 동작 원리

> 기능 설명은 [기능/08-운영과-배포.md](../기능/08-운영과-배포.md)에 있어요. 2026-10-16 코드(develop, v1.10.2 + 다음 버전 CI 변경) 기준이에요.

## 큰 흐름

### 흐름 1. 코드가 사이트에 올라가기까지

1. 기능 브랜치에서 PR을 올리면 `.github/workflows/ci.yml`이 `pull_request` 이벤트로 돌아요. backend와 frontend 두 작업(job)이 따로따로 동시에 돌아요. PR이 develop에 합쳐지면 `push`(develop) 이벤트로 한 번 더 돌아요(v1.10.1).
2. develop을 main으로 합치면 `.github/workflows/deploy.yml`이 `push`(main) 이벤트로 시작해요.
3. deploy의 첫 작업 `ci`는 `uses: ./.github/workflows/ci.yml`로 같은 검사를 다시 불러요(`workflow_call`). 두 번째 작업 `deploy`는 `needs: ci`라서 검사가 통과해야만 시작해요.
4. `docker build -t myblog:<커밋 sha> .`로 이미지를 만들고 `docker save ... | gzip`으로 `myblog-image.tar.gz` 파일에 담아요.
5. `appleboy/scp-action`이 SSH 아이디·비밀번호로 서버에 접속해 이미지 파일과 `deploy/deploy.sh`를 `~/myblog-deploy`에 올려요.
6. `appleboy/ssh-action`이 서버에서 `./deploy/deploy.sh <이미지 파일> <sha>`를 실행해요. DB 정보 Secrets, 선택 Secrets(`SMTP_*`, `MAIL_FROM`, `KAKAO_*`, `GOOGLE_*`)와 변수(`NOTICE_OWNER_EMAIL`, `SITE_URL`)는 `envs`로 환경변수가 되어 스크립트에 넘어가요.
7. `deploy.sh`가 블루-그린으로 새 서버를 띄우고 nginx를 돌려요(흐름 2). 끝나면 이미지 압축 파일을 지워요.
8. 마지막 단계 "배포 후 실제 사이트 확인"이 러너에서 `SITE_URL`(비면 `https://sagak.java21.net`)로 `curl`을 보내요(다음 버전). 아래 "스모크 테스트"를 보세요.

### 흐름 2. deploy.sh 한 번이 하는 일

1. `docker load`로 이미지를 불러오고, 네트워크 `myblog-net`이 없으면 만들어요.
2. `myblog-redis` 컨테이너가 있으면 `start`, 없으면 `redis:7`로 새로 띄워요(`--restart unless-stopped`).
3. `~/myblog-data/app.env`를 다시 써요. 그리고 nginx 설정 `~/myblog-data/proxy/conf.d/default.conf`에서 `myblog-blue`나 `myblog-green` 글자를 찾아 지금 색(ACTIVE)을 알아내요. blue면 새 색(NEXT)은 green, 아니면 blue예요.
4. NEXT 이름의 컨테이너를 지우고 새 이미지로 띄워요. 바깥 포트는 열지 않고 `myblog-net` 안에서만 보여요.
5. 3초 간격으로 최대 60번, 같은 네트워크에 nginx 이미지를 잠깐 띄워 `wget http://<NEXT>:8390/api/topics`를 보내요. 성공하면 다음 단계로 가요.
6. 실패하면(60번 다 실패했거나 새 컨테이너가 도중에 죽음) 새 서버 로그 80줄을 찍고 새 서버만 지운 뒤 `exit 1`. nginx는 건드리지 않았으니 사이트는 옛 서버 그대로예요.
7. 성공하면 nginx 설정을 백업(`.bak`)하고 `proxy_pass http://<NEXT>:8390`으로 다시 써요. 같은 `location`에 `add_header Strict-Transport-Security "max-age=31536000" always`도 적어요(v1.10.1). `nginx -t`로 문법을 검사하고 `nginx -s reload`로 다시 읽어요.
   - 이어서 `myblog-proxy`가 지금 8390을 받는 주소(`docker inspect`의 `PortBindings` HostIp)가 `PROXY_BIND`와 다르면 컨테이너를 지우고 새 주소로 다시 띄워요(v1.10.1). 새 주소로 못 띄우면 예전 주소로 다시 띄워요.
8. 옛 서버가 있으면 2초 기다린 뒤 `docker stop -t 35`로 끄고 지워요. Spring은 graceful shutdown으로 하던 요청을 마치고 내려가요.
9. `docker image prune -f`로 안 쓰는 이미지를 지워요.

## 자세히 보기

### 브랜치 전략: 간소화한 Git Flow
- main은 "지금 사이트에 있는 코드", develop은 "다음 배포에 들어갈 것을 모으는 곳"이에요. 기능은 `feature/*` 브랜치에서 만들어 develop으로 PR을 보내요.
- `deploy.yml`의 트리거가 `push: branches: [main]`뿐이라, develop에 아무리 합쳐도 배포되지 않아요. main에 들어가는 것이 곧 배포 버튼이에요.
- 원래 Git Flow의 hotfix는 main에서 갈라 고친 뒤 main과 develop 두 곳에 합치는 브랜치예요. 이 저장소에는 hotfix 규칙이나 hotfix 브랜치가 없고, 고치는 것도 `fix/session-cookie`처럼 브랜치를 따서 develop을 거쳐 main으로 갔어요.

### CI: 테스트에 진짜 DB와 Redis를 쓰는 이유
- backend 작업은 GitHub Actions의 `services`로 `postgres:16`(DB 이름 `myblog_test`, 비밀번호 postgres)과 `redis:7`을 띄워요. `--health-cmd`(`pg_isready`, `redis-cli ping`)로 준비될 때까지 기다린 뒤 테스트를 시작해요.
- 테스트는 `@ActiveProfiles("test")`(`support/IntegrationTest`)로 `application-test.yml`을 더 읽어요. DB는 `TEST_DB_URL` 기본 `jdbc:postgresql://localhost:5432/myblog_test`, Redis는 1번 DB를 써서 개발용 0번과 섞이지 않아요.
- 테스트 설정은 `SessionAutoConfiguration`을 빼요. 대부분의 테스트는 가짜 세션(MockHttpSession)을 쓰고, Redis 세션은 `RedisSessionIT`에서 따로 확인해요.
- frontend 작업의 `npm run build`는 `tsc --noEmit -p . && vite build`예요. 타입 검사를 한 번 더 하고 실제 빌드가 되는지 봐요.

### 품질 게이트: SonarQube Cloud (v1.10.0)
- backend 작업에서 `./gradlew test`가 끝나면 JaCoCo가 서버 테스트 커버리지를 `backend/build/reports/jacoco/test/jacocoTestReport.xml`로 남겨요(`build.gradle.kts`의 `finalizedBy(jacocoTestReport)`).
- 이어서 Node를 깔고 `frontend`에서 `npm ci --ignore-scripts && npm run test:coverage`를 돌려 화면 커버리지를 `frontend/coverage/lcov.info`로 남겨요(vitest v8).
- 마지막으로 `SonarSource/sonarqube-scan-action`이 코드와 두 보고서를 SonarQube Cloud(조직 `home-my-blog`, 프로젝트 `home-my-blog_myblog`)로 보내요. 설정은 저장소 맨 위 `sonar-project.properties`에 있어요.
- `sonar.qualitygate.wait=true`라서 분석이 끝날 때까지 기다렸다가 **품질 게이트가 실패하면 backend 작업도 실패**해요. 기준은 "Sonar way"로, 이번 PR에서 바뀐 코드(new code)에 대해 버그 0 · 보안 취약점 0 · 커버리지 80% 이상 · 중복 3% 이하예요.
- develop과 main에는 규칙("머지 전 검사 필수")이 걸려 있어요. backend, frontend, SonarCloud Code Analysis 세 검사가 모두 초록이어야 병합 버튼이 눌리고, 브랜치 삭제와 강제 푸시는 막혀요.
- 스캔 action은 태그가 아니라 커밋 sha로 고정했어요. 태그는 나중에 다른 코드로 옮길 수 있어서, Sonar가 보안 문제로 짚었어요. `npm ci`의 `--ignore-scripts`도 같은 이유(설치 중 남의 스크립트 실행 막기)로 붙였어요. v1.10.1부터는 `Dockerfile`의 `npm ci`에도 붙였어요.
- `push`(develop)에도 도는 이유(v1.10.1): SonarQube Cloud 첫 화면은 develop 분석을 보여 줘요. PR 분석만 있으면 develop에는 커버리지가 비어 보여서, 합친 뒤의 develop도 분석해요.
- v1.10.2에서 남은 이슈를 정리해 신뢰성 · 보안 · 유지보수성 모두 A, 해결 안 된 이슈 0개가 됐어요. 화면 테스트를 241개 더해 전체 커버리지는 약 90%예요(`CHANGELOG.md`).
- 토큰은 GitHub Secrets의 `SONAR_TOKEN`이에요. 없으면(포크 PR 등) Sonar 단계만 건너뛰어요(`if: env.SONAR_TOKEN != ''`). `deploy.yml`은 `ci.yml`을 다시 불러 쓰므로 `secrets: inherit`로 토큰을 넘겨요.
- SonarQube Cloud의 "자동 분석(Automatic Analysis)"은 꺼야 해요. 켜 두면 CI 분석과 겹쳐서 CI 쪽 분석이 실패해요.

### 실패한 테스트 보고서 남기기 (다음 버전)
- 두 작업 끝에 `if: failure()`인 `actions/upload-artifact`(커밋 sha로 고정) 단계가 있어요. 실패했을 때만 돌아요.
- backend는 `backend/build/reports/tests/test`(HTML), `backend/build/test-results/test`(XML), `frontend/coverage`를 `backend-test-reports`로 올려요.
- frontend는 `npm test`에 `--reporter=junit --outputFile.junit=test-results/junit.xml`을 더해 JUnit XML을 만들고, 실패하면 `frontend/test-results`를 `frontend-test-reports`로 올려요.
- `retention-days: 14`, `if-no-files-found: ignore`(보고서가 생기기 전 단계에서 실패해도 이 단계는 오류를 내지 않음)예요.

### 테스트 층과 E2E (다음 버전)
- 코드 저장소의 `TESTING.md`가 테스트 전략을 정해요. 2026-10-15 기준 단위 · 컴포넌트 317개(서버 25 + 화면 292), 통합 88개(서버, 실제 DB · Redis), 종단 7개예요. 아래가 넓고 위가 좁은 피라미드를 지켜요.
- 서버는 통합이 단위보다 많아요. 서버 로직이 대부분 "권한 확인 + SQL"이라 실제 DB로 봐야 의미가 있어서예요.
- 종단 테스트는 `frontend/e2e/*.spec.ts` 세 파일(`signup-write`, `comment-like`, `search`)이고, `frontend/playwright.config.ts`가 설정해요.
  - `baseURL`은 `E2E_BASE_URL`(기본 `http://localhost:8080`, 화면을 함께 내보내는 서버)이에요.
  - `fullyParallel: false`, CI에서는 `retries: 1`, 실패하면 trace와 스크린샷을 남겨요(`retain-on-failure`, `only-on-failure`). 브라우저는 Desktop Chrome(Chromium) 하나예요.
  - 서버를 `MYBLOG_MAIL_MODE=log`로 띄워야 가입 인증번호(`devCode`)가 화면에 나와서 테스트가 가입을 끝낼 수 있어요.
- `.github/workflows/e2e.yml`
  - 트리거: `push`(develop, main), 경로가 `frontend/e2e/**`, `frontend/playwright.config.ts`, `.github/workflows/e2e.yml`인 `pull_request`, `workflow_dispatch`. `concurrency: e2e-<ref>`, `cancel-in-progress: true`라 같은 브랜치의 앞 실행은 취소돼요.
  - `services`로 `postgres:16`(DB `myblog_e2e`)과 `redis:7`을 띄우고, `docker build -t myblog:e2e .`로 운영과 같은 이미지를 만들어 `--network host`, `SERVER_PORT=8080`, `MYBLOG_MAIL_MODE=log`로 띄워요. `/api/topics`가 응답할 때까지 3초 간격 60번 기다려요.
  - `npm ci --ignore-scripts` → `npx playwright install --with-deps chromium` → `npm run e2e`(`playwright test`). 실패하면 `docker logs --tail 200`과 `playwright-report`, `test-results`를 Artifacts `e2e-report`(14일)로 남겨요.
  - 작업 제한 시간은 30분이에요. `ci.yml`과 따로 도는 워크플로라 브랜치 규칙의 필수 검사에는 들어 있지 않아요.
- AI(Claude Code)는 저장소 맨 위 `CLAUDE.md`를 읽어요. "테스트를 먼저 정하고, 실패하면 테스트가 아니라 구현을 고친다", "품질 게이트를 넘어야 병합", "develop · main에 직접 push하지 않는다", "비밀값은 코드에 넣지 않는다"가 들어 있어요.

### Dependabot (다음 버전)
- `.github/dependabot.yml`에 세 가지가 있어요. 모두 `target-branch: develop`, 시간대 `Asia/Seoul`이에요.

| 대상 | 폴더 | 주기 | 묶음 |
|---|---|---|---|
| `gradle` | `/backend` | 매주 월요일, 열린 PR 5개까지 | `backend-minor` (minor · patch) |
| `npm` | `/frontend` | 매주 월요일, 열린 PR 5개까지 | `frontend-minor` (minor · patch) |
| `github-actions` | `/` | 매달 | `actions` (전부) |

- major 올림은 묶지 않아서 하나씩 PR로 와요. PR은 다른 PR과 똑같이 CI와 품질 게이트를 통과해야 합칠 수 있어요.

### CD: concurrency로 배포 줄 세우기
- `deploy.yml`에 `concurrency: group: deploy, cancel-in-progress: false`가 있어요. 같은 group의 실행은 한 번에 하나만 돌아요.
- `cancel-in-progress: false`라서 돌던 배포를 중간에 끊지 않아요. 새 실행은 앞 배포가 끝날 때까지 기다려요. 배포를 도중에 끊으면 블루-그린 전환이 반쯤 된 채로 남을 수 있어서예요. (GitHub의 concurrency는 기다리는 실행을 하나만 두기 때문에, 그 사이에 여러 번 합치면 기다리던 것 중 앞의 것은 취소되고 마지막 것만 남아요.)
- 이미지 태그는 커밋 sha예요. 서버에서 `myblog:<sha>`로 어느 커밋이 떠 있는지 알 수 있어요.

### 스모크 테스트: 배포 뒤 실제 주소로 확인 (다음 버전)
- `deploy.yml`의 마지막 단계예요. `deploy.sh`의 확인(`/api/topics`)은 서버 안 도커 네트워크에서 하므로, 서버 nginx · 인증서 · `myblog-proxy` 바인딩 문제는 잡지 못해요. 그래서 바깥(GitHub 러너)에서 실제 주소로 한 번 더 봐요.
- `check` 함수가 `curl --max-time 10`으로 `/`, `/api/topics`, `/api/home`을 차례로 불러요. 200이 아니면 5초 쉬고 다시, 5번까지 해 봐요. 그래도 아니면 `::error::`를 찍고 실패해요.
- 마지막으로 `curl -sI "$SITE/"`의 헤더에 `strict-transport-security`가 있는지 봐요(대소문자 무시). 없으면 실패해요.
- 이 단계가 실패해도 서버는 이미 새 버전으로 바뀐 뒤예요. 되돌리지는 않고, deploy 작업을 빨간 X로 남겨 사람이 보게 해요.

### Dockerfile: 화면과 서버를 상자 하나에
- 1단계 `node:22-alpine`에서 `npm ci --ignore-scripts`(v1.10.1), `npm run build`로 화면을 빌드해요.
- 2단계 `eclipse-temurin:21-jdk`에서 화면 결과 `dist/`를 `src/main/resources/static/`에 복사하고 `./gradlew bootJar -x test`로 jar를 만들어요. 테스트는 CI에서 이미 돌렸으니 건너뛰어요.
- 3단계 `eclipse-temurin:21-jre`에 jar만 담아요. `TZ=Asia/Seoul`, `SERVER_PORT=8390`, `MYBLOG_IMAGE_DISK_PATH=/data/images`를 환경변수로 박아 둬요.
- 그래서 Spring이 `/api`도 화면 파일도 함께 내려줘요. nginx는 받은 요청을 앱으로 넘기기만 해요.

### deploy.sh: 왜 그 순서인가
- **새 서버를 먼저 띄우고 확인한 뒤에 nginx를 돌려요.** 순서를 거꾸로 하면 새 서버가 고장 났을 때 사이트가 꺼져요. 지금 순서에서는 실패해도 옛 서버가 계속 손님을 받아요.
- **지금 색은 nginx 설정 파일로 알아요.** 따로 상태 파일을 두지 않고, 실제로 손님을 보내는 곳이 적힌 `default.conf`를 믿어요. 파일이 없으면(처음) ACTIVE는 비고 NEXT는 blue예요.
- **확인을 nginx 이미지의 wget으로 해요.** 새 서버는 바깥 포트가 없어서 서버 주인 컴퓨터에서 `curl localhost`로는 닿지 않아요. 같은 네트워크에 일회용 컨테이너(`--rm`)를 띄워 컨테이너 이름으로 불러요.
- **`/api/topics`를 확인 주소로 써요.** 로그인 없이 DB에서 분야 목록을 읽어 오는 요청이라, 응답이 오면 서버가 켜졌고 DB 연결과 Flyway까지 끝났다는 뜻이에요.
- **새 컨테이너가 죽으면 바로 멈춰요.** 기다리는 중에 `docker inspect`로 `State.Running`을 보고, false면 60번을 다 채우지 않고 실패로 가요.
- **nginx 설정은 검사 후 적용해요.** `nginx -t`가 실패하면 `.bak`으로 되돌리고 새 서버를 지워요. `nginx -s reload`는 nginx를 끄지 않고 설정만 다시 읽어서, 이미 연결된 요청은 옛 서버로 마저 가고 새 요청부터 새 서버로 가요.
- **처음 한 번(nginx가 없을 때)만 끊겨요.** 예전에는 `myblog` 컨테이너가 8390을 직접 잡고 있었어요. 이 컨테이너를 지우고 `myblog-proxy`를 `-p 127.0.0.1:8390:8390`(v1.10.1 전에는 `-p 8390:8390`), 설정 폴더를 읽기 전용(`:ro`)으로 띄우는 1~2초 동안만 끊겨요.
- **8390은 서버 안에서만 받아요(v1.10.1).** `PROXY_BIND`(기본 `127.0.0.1`)로 `-p` 앞 주소를 정해요. 내부망 IP를 주면 그 내부망에서만, `all`이면 빈 값이 되어 모든 주소(공인 IP 포함)에서 받아요. 서버 nginx(HTTPS, Certbot, 학원 서버 관리자 관리)가 `https://sagak.java21.net`을 `127.0.0.1:8390`으로 넘겨 주는 것을 status 워크플로로 확인하고 바꿨어요.
- **바인딩이 바뀌면 그때만 nginx를 다시 띄워요.** 도커는 실행 중인 컨테이너의 포트 주소를 바꿀 수 없어요. 그래서 `reload` 뒤에 지금 주소와 `PROXY_BIND`를 비교해, 다를 때만 `myblog-proxy`를 지우고 다시 띄워요(1~2초 끊김). 실패하면 예전 주소로 다시 띄워 사이트를 살려 둬요.
- **HSTS(v1.10.1)**: `myblog-proxy`가 응답마다 `Strict-Transport-Security: max-age=31536000`(1년)을 붙이고, 서버 nginx가 이것을 HTTPS로 그대로 전달해요. 브라우저는 한 번 받은 뒤 1년 동안 이 사이트를 http로 열지 않아요. `always`라 오류 응답에도 붙어요.
- **옛 서버는 2초 뒤에 꺼요.** reload 직후 아직 옛 서버로 가던 요청이 들어갈 틈을 줘요. `docker stop -t 35`는 SIGTERM을 보내고 35초까지 기다렸다가 그래도 안 꺼지면 강제로 꺼요.
- **graceful shutdown**: `application.yml`의 `server.shutdown: graceful` 덕분에 Spring은 SIGTERM을 받으면 새 요청은 안 받고 하던 요청을 끝낸 뒤 꺼져요. Spring의 기본 대기 시간(30초)이 docker의 35초보다 짧게 맞물려요.
- **docker 권한**: `docker info`가 안 되면 `sudo -n docker info`를 시도해요. `-n`은 비밀번호를 묻지 않는다는 뜻이라, 비밀번호 없는 sudo가 아니면 바로 안내 문구와 함께 멈춰요.
- **DB가 같은 서버에 있을 때**: `DB_ADDRESS`가 `localhost`나 `127.0.0.1`이면 컨테이너 안에서는 자기 자신을 가리키게 돼요. 그래서 `host.docker.internal`로 바꾸고 `--add-host=host.docker.internal:host-gateway`를 붙여요. 운영 DB는 외부 서버라 이 경로는 쓰이지 않아요.

### app.env: 운영 설정이 앱에 들어가는 길
- `deploy.sh`가 `umask 077`(주인만 읽기·쓰기)로 `app.env`를 써요. 늘 들어가는 값은 `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `SPRING_FLYWAY_SCHEMAS`, `REDIS_HOST=myblog-redis`, `REDIS_PORT=6379`, `SESSION_SECURE_COOKIE=true`, `SITE_URL`(비면 `https://sagak.java21.net`)이에요.
- 값이 있을 때만 더하는 묶음이 넷이에요.

| 조건 | 더하는 값 |
|---|---|
| `NOTICE_OWNER_EMAIL`이 있음 | `NOTICE_OWNER_EMAIL` |
| `SMTP_HOST`가 있음 | `MYBLOG_MAIL_MODE=smtp`, `SMTP_HOST`, `SMTP_PORT`(비면 587), `SMTP_USERNAME`, `SMTP_PASSWORD`, `MAIL_FROM`(있을 때만) |
| `KAKAO_CLIENT_ID`가 있음 | `KAKAO_CLIENT_ID`, `KAKAO_CLIENT_SECRET` |
| `GOOGLE_CLIENT_ID`가 있음 | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` |

- 값이 없으면 그 줄을 아예 적지 않아서 `application.yml`의 기본값(메일 log, 소셜 로그인 꺼짐)이 그대로 쓰여요.
- `DB_URL`은 `jdbc:postgresql://<주소>:<포트>/<DB>?currentSchema=<스키마>,public`이에요. 내 스키마를 먼저 찾고 없으면 public을 찾아요. Flyway도 `SPRING_FLYWAY_SCHEMAS`로 내 스키마에 표를 만들어요.
- 앱 컨테이너는 `--env-file`로 이 파일을 읽어요. Spring은 `DB_URL` 같은 환경변수를 `application.yml`의 `${DB_URL:...}` 자리에 넣어요.
- v1.7.1 전에는 메일 값과 `SESSION_SECURE_COOKIE`가 이 파일에 없어서, 운영이 늘 log 모드에 Secure 없는 쿠키로 돌았어요. 지금은 쿠키는 늘 Secure이고, 메일은 Secret `SMTP_HOST`로 정해져요.

### 소셜 로그인 키와 SITE_URL
- `application.yml`의 `myblog.oauth`가 `KAKAO_CLIENT_ID`, `KAKAO_CLIENT_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`을 읽어요. 기본값은 모두 빈 값이에요.
- `SocialClientRegistrations`가 client id가 있는 제공자만 등록하고, 하나도 없으면 `SecurityConfig`가 `oauth2Login`을 켜지 않아요. 그래서 키 없는 CI와 로컬에서도 서버가 그대로 떠요.
- `myblog.oauth.redirect-base: ${SITE_URL:{baseUrl}}`. 돌아올 주소는 `<redirect-base>/login/oauth2/code/{kakao|google}`예요. 운영 앱은 nginx가 넘긴 http 요청을 받고(nginx는 `Host`만 넘기고 `X-Forwarded-Proto`는 넘기지 않아요), 요청 주소로 만들면 `https://sagak.java21.net`이 되지 않아요. 그래서 `deploy.sh`가 `SITE_URL`을 늘 적어 둬요.
- `SITE_URL`은 GitHub 저장소 변수(Variables)라서 비밀이 아니에요. 키 4개는 Secrets예요.

### 설정 읽는 순서: 프로필 없이 하나로
- `application.yml`의 `spring.config.import: optional:file:../.env[.properties],optional:file:./.env[.properties]`가 `.env`를 properties 파일처럼 읽어요. `backend`에서 실행하면 `../.env`(저장소 루트)를, 루트에서 실행하면 `./.env`를 찾아요. `optional:`이라 없어도 오류가 나지 않아요.
- 값을 쓰는 곳은 `${환경변수:기본값}` 꼴이에요. 예를 들어 `myblog.mail.mode: ${MYBLOG_MAIL_MODE:log}`. 환경변수나 `.env`에 있으면 그 값, 없으면 기본값이에요.
- 그 밖의 숫자 규칙은 `myblog.*` 아래에 기본값으로 있고, `MyBlogProperties`(`@ConfigurationPropertiesScan`)가 읽어요.
- `SERVER_PORT`처럼 yml에 없는 값도 Spring의 느슨한 이름 맞추기(relaxed binding)로 `server.port`가 돼요. Dockerfile이 이것으로 8390을 줘요.

### 로컬 개발: Vite 프록시
- `frontend/vite.config.ts`는 개발 서버를 5173에 띄우고, `/api`로 시작하는 요청과 소셜 로그인 주소(`/oauth2`, `/login/oauth2`)를 `MYBLOG_API_TARGET`(기본 `http://localhost:8080`)으로 넘겨요. `changeOrigin: false`라서 Host 헤더를 바꾸지 않아요. 그래서 개발 중 소셜 로그인의 돌아올 주소가 `http://localhost:5173/login/oauth2/code/...`가 돼요.
- 브라우저 입장에서는 화면과 API가 같은 주소(5173)라 쿠키와 CSRF 토큰이 운영과 똑같이 동작해요. 운영도 Spring이 화면과 API를 같은 주소로 내려줘요.
- `docker-compose.yml`에는 `db`(postgres:16, 사용자·DB 이름 myblog, 비밀번호는 `.env`의 `DB_PASSWORD`), `redis`(redis:7), `minio`가 있어요. minio는 `profiles: ["minio"]`라서 `--profile minio`를 줘야만 떠요. 서버와 화면은 컨테이너에 넣지 않아요.

### 시간 맞춰 도는 일 4개
`MyBlogApplication`의 `@EnableScheduling`이 `@Scheduled`가 붙은 메서드를 찾아 돌려요.

| 메서드 | 언제 | 하는 일 |
|---|---|---|
| `TrendingService.refresh` | `fixedRateString = ${myblog.trending.interval}` (5초) | 24시간 안의 검색 기록(DB)과 조회 기록(메모리)으로 점수를 계산해 메모리의 순위를 바꿔요 |
| `ImageService.cleanOrphans` | `fixedDelay = 3_600_000, initialDelay = 60_000` | 글·대표 사진·임시저장 어디에도 안 쓰인 채 24시간 지난 사진을 DB에서 지우고, 커밋 뒤 파일도 지워요 |
| `SearchService.purgeOldLogs` | `cron = "0 30 4 * * *"`, Asia/Seoul | `search_logs`에서 30일 지난 줄을 지워요 |
| `WithdrawalCleaner.scheduled` | `cron = "0 40 4 * * *"`, Asia/Seoul | 탈퇴 30일 지난 회원을 한 명씩 각자 트랜잭션으로 익명화해요 |

- `fixedRate`는 시작 시각 기준 간격, `fixedDelay`는 앞 실행이 끝난 뒤부터의 간격이에요.
- 배포 중 블루와 그린이 잠깐 같이 떠 있으면 두 서버 모두 이 일을 돌려요. 따로 잠금(ShedLock 같은)은 없어요. 서버가 평소 한 대라서 따로 두지 않았어요(`TrendingService` 주석의 "서버 1대").

### RedisGuard: required와 optional
- `common/RedisGuard`에는 메서드가 두 개 있어요. 둘 다 Redis 호출을 감싸고 `DataAccessException`(Redis 연결 실패 등)을 잡아요.
- `required`: 경고 로그를 남기고 `ApiException(SERVICE_UNAVAILABLE)`을 던져요. 응답은 503 "잠시 뒤 다시 시도해 주세요"예요. `EmailVerificationService`의 인증번호 보내기·확인하기·확인됐는지 보기에 써요.
- `optional`: 경고 로그를 남기고 빈 값(`Optional.empty()`)을 돌려줘요. 부르는 쪽이 `orElse`로 기본값을 정해요.
  - `ViewRecorder`의 조회수 중복 막기와 방문자 세기는 `orElse(false)`라서, Redis가 없으면 새 조회로 치지 않아요(숫자가 안 늘어요).
  - `CommentService`의 댓글 5초 막기와 `EmailVerificationService.preventDuplicate`(5초 중복 제출 막기)는 `orElse(true)`라서, Redis가 없으면 그냥 통과시켜요.
  - 인증 끝난 표시 지우기(`consume`)도 optional이에요.
- Redis 연결 제한 시간은 `spring.data.redis.timeout: 1s`라서, 꺼져 있어도 요청이 1초 넘게 붙잡히지 않아요.
- 세션은 RedisGuard를 거치지 않아요. Spring Session이 요청마다 Redis에서 세션을 읽기 때문에, Redis가 꺼지면 세션을 쓰는 요청이 오류가 나요. 로그인 없이 읽는 글은 세션이 필요 없어서 돼요.

### Flyway: 번호 붙은 SQL만으로 DB 바꾸기
- `spring.flyway.enabled: true`. 서버가 켜질 때 Flyway가 `db/migration`의 `V숫자__이름.sql`을 번호 순서로 보고, DB의 기록 표(`flyway_schema_history`)에 없는 것만 실행해요.
- 실행한 파일의 체크섬(내용 지문)도 기록해요. 이미 실행한 파일을 고치면 지문이 달라져 검증에서 서버가 안 켜져요. 그래서 고치지 않고 새 번호를 더해요. 예: "미분류" 다이어리 이름을 "일기장"으로 바꾼 것도 V20으로 새로 더했어요.
- 지금 V1~V24 중 V14·V15가 비어 있어요. V21은 소셜 로그인 연결 표 `member_social_accounts`를 만들고(v1.8.0), V22는 `members.password_set`(비밀번호 설정 여부)을 더해요(v1.8.1). V23(소셜 가입 회원의 `password_set`을 false로)과 V24(이메일 가입 회원에게 자동으로 붙은 소셜 연결 지우기)는 데이터만 바꿔서 표 구조는 V22와 같아요(v1.9.0). 다음 파일은 V25예요. 운영 DB에 V16이 먼저 적용된 뒤 V14·V15가 들어오자, 기본 설정은 이미 지난 번호를 허용하지 않아 검증이 실패했어요. 두 파일은 운영에 적용된 적이 없어서 V17·V18로 이름만 바꿨어요(커밋 "구독 마이그레이션 번호를 V16 뒤로 옮겨 배포 실패를 고친다").
- V1은 `pg_trgm` 확장을 만들 권한이 없으면 `RAISE NOTICE`만 하고 넘어가요. Crowfoot DB처럼 스키마 안에서만 권한이 있는 곳에서도 배포가 되게 하려고요.
- 블루-그린과의 관계: 새 서버가 뜨면서 Flyway를 돌리는 순간에도 옛 서버는 같은 DB로 손님을 받아요. 컬럼을 지우면 옛 서버의 SQL이 깨져요. 그래서 "새 코드가 옛 컬럼을 안 쓰게 배포 → 다음 배포에서 컬럼 삭제"로 두 번에 나눠요.

### 메일 모드: 빈 하나만 고르기
- `MailSender` 인터페이스에 구현이 둘 있어요. `LogMailSender`는 `@ConditionalOnProperty(name = "myblog.mail.mode", havingValue = "log", matchIfMissing = true)`, `SmtpMailSender`는 `havingValue = "smtp"`예요. 설정값에 따라 하나만 만들어져요.
- `LogMailSender.send`는 `[메일] to=... subject=...`와 본문을 로그에 찍고, `isAvailable`은 항상 true예요.
- `SmtpMailSender.isAvailable`은 `testConnection`으로 SMTP 서버에 붙어 보고, 실패하면 인증번호 보내기가 `MAIL_SEND_FAILED`(503)가 돼요. `send`는 `@Async("mailExecutor")`라 따로 스레드(`AsyncConfig`, 2~4개, 대기 100개)에서 보내고, 실패는 로그만 남겨요.
- 운영은 Secret `SMTP_HOST`가 있을 때만 `deploy.sh`가 `MYBLOG_MAIL_MODE=smtp`를 적어요. 없으면 `app.env`에 `MYBLOG_MAIL_MODE`가 없어서 `matchIfMissing`·기본값 log가 쓰여요.
- `log` 모드에서 화면에 번호를 보여 주는 것(`devCode`)은 가입 인증번호뿐이에요. 비밀번호 찾기 번호는 로그에만 남아요(v1.7.1, 원리 01 참고).

### status.yml: 세 곳에서 보기
- **서버 안**: ssh로 들어가 `docker ps -a --filter name=myblog`, `curl localhost:8390/api/topics`(nginx를 거친 응답), `default.conf`에서 active 색, 그 컨테이너 로그 20줄. active를 못 찾으면 예전 이름 `myblog`의 로그를 봐요.
- **바깥**: GitHub 러너에서 `http://<SSH_ADDRESS>:8390/api/topics`(`--max-time 10`). v1.10.1부터 8390은 `127.0.0.1`에만 열려 있어서 여기는 `timeout`이 나와야 정상이에요. 응답 코드가 나오면 8390이 바깥에 열렸다는 뜻이에요. 서버 안 확인(`curl localhost:8390`)은 같은 서버 안이라 그대로 돼요.
- **공개 주소**: 입력한 URL로 `/`, `/api/topics`, `/api/search?q=a`. 도메인 연결과 화면 파일까지 확인해요.

### release.yml: CHANGELOG를 Release로
- `push`(main) 중 `paths: [CHANGELOG.md]`가 바뀐 경우에만 돌아요. `contents: write` 권한과 `fetch-depth: 0`(커밋 전체)을 써요.
- 파이썬이 `^## (v\d+\.\d+\.\d+)[ \t]*(.*)$` 정규식으로 버전·제목·본문을 나누고, `gh release list`로 이미 있는 태그를 빼요.
- 오래된 버전부터 만들어서 맨 위 버전이 마지막에 `--latest=true`가 돼요. `<!-- commit: ... -->`가 있으면 그 커밋에, 없으면 HEAD에 태그를 붙여요. 주석은 노트에서 지우고 `###` 제목은 `##`로 한 단계 올려요.

## 왜 이렇게 만들었나

- **블루-그린 + Redis 세션**: 예전에는 옛 서버를 끄고 새 서버를 켜서 몇 초씩 끊겼고, 세션이 서버 메모리에 있어 배포할 때마다 모든 회원이 로그아웃됐어요. 새 버전이 안 뜨면 사이트가 꺼진 채로 남기도 했어요. 세션을 Redis로 옮기고 nginx 뒤에 두 서버를 번갈아 두었어요. README에 따르면 0.2초마다 요청을 보내며 배포해 봤을 때 끊김이 0번이었고, 일부러 고장 낸 버전을 배포해도 옛 서버가 사이트를 지켰어요. 대가는 "DB 변경 두 번에 나누기"예요. (README 기술적 의사결정 2)
- **품질 게이트를 병합 조건으로**: 테스트가 통과해도 테스트가 없는 코드나 보안 문제는 걸러지지 않아요. 기준을 숫자로 정해 두고, 못 넘으면 병합 자체가 안 되게 브랜치 규칙으로 막았어요. 처음 켰을 때 action 고정과 `--ignore-scripts` 두 가지 보안 문제를 찾아 고쳤어요. (README 기술적 의사결정 9)
- **앱 포트를 서버 안으로**: 8390이 모든 주소에 열려 있으면 `http://공인IP:8390`으로 도메인과 HTTPS를 건너뛰고 들어올 수 있고, 그 길로 로그인하면 비밀번호가 암호화 없이 오가요. 서버 nginx가 같은 서버에서 넘겨 주니 8390은 바깥에 열 필요가 없어요. HSTS는 사용자가 http로 쳐도 브라우저가 https로 바꾸게 해요(v1.10.1).
- **배포 뒤 바깥에서 한 번 더**: 서버 안 확인만으로는 인증서 · 서버 nginx · 포트 바인딩 문제를 모르고 "배포 성공"이 될 수 있어요. 실제 손님과 같은 길로 확인해요(다음 버전).
- **E2E는 핵심 흐름만, 합친 뒤에**: 종단 테스트는 느리고 잘 깨져요. 대부분은 단위 · 통합 테스트가 맡고, E2E는 "사용자가 끝까지 할 수 있는지"만 7개로 봐요. PR마다 돌리면 느려서 develop · main에 들어온 뒤에 돌려요(다음 버전, `TESTING.md`).
- **Git Flow 간소화**: 자잘한 수정을 하나씩 배포하면 배포가 너무 잦고 느려서, develop에 모았다가 한 번에 main으로 보내요. (README 기술적 의사결정 7)
- **비밀값은 Secrets에**: 저장소가 공개라서 비밀번호를 코드에 둘 수 없어요.
- **Redis를 required/optional로 나눔**: 인증번호는 Redis 없이 할 방법이 없지만, 조회수 중복 막기는 잠깐 틀려도 큰일이 아니에요. 덜 중요한 기능 때문에 글 읽기까지 막히지 않게 했어요. (README 기술적 의사결정 3)
- **화면과 서버를 이미지 하나로**: 배포 단위가 하나라 버전이 어긋날 일이 없고, 같은 주소라 쿠키를 그대로 써요. (research.md §14)
- **Flyway 번호 파일**: 어느 서버(로컬, CI, 운영)에서든 같은 순서로 같은 구조가 만들어져요.
- **메일 log 모드 기본값**: 개발 중에 진짜 메일 없이도 가입을 끝까지 해 볼 수 있어요. 운영은 Secrets에 SMTP 값을 넣으면 코드 수정 없이 실제 메일로 바뀌어요(v1.7.1).
- **운영 쿠키는 늘 Secure**: 운영 사이트는 HTTPS라서 쿠키를 HTTPS로만 보내도 문제가 없어요. 로컬은 http라서 기본값을 false로 두고, 운영만 `deploy.sh`에서 켜요(v1.7.1).
- **선택 기능은 키가 있으면 켜기**: 메일과 소셜 로그인은 키가 없어도 서버가 떠야 해요(CI, 로컬, 키를 아직 받지 않은 운영). 그래서 값이 있을 때만 `app.env`에 적고, 앱도 값이 없으면 그 기능만 꺼요.

## 공부 키워드

- **SonarQube, Quality Gate, JaCoCo, lcov**: 정적 분석과 병합 기준, 커버리지 보고서 형식
- **Playwright, E2E 테스트, 테스트 피라미드**: 브라우저로 끝까지 확인하기와 테스트 층 나누기
- **스모크 테스트(smoke test)**: 배포 직후 핵심 주소만 빠르게 확인하기
- **HSTS(Strict-Transport-Security)**: 브라우저가 https로만 접속하게 하기
- **Docker 포트 바인딩(-p 127.0.0.1:포트)**: 컨테이너 포트를 어느 주소에 열지 정하기
- **Dependabot**: 의존성 새 버전과 보안 패치를 PR로 받기
- **GitHub Actions artifact**: 실행 결과 파일 남기기
- **GitHub branch ruleset, required status checks**: 검사를 통과해야만 병합하게 막기
- **Git Flow**: main/develop/feature/hotfix로 나누는 브랜치 전략
- **GitHub Actions workflow_call, concurrency**: 워크플로 재사용과 동시 실행 막기
- **블루-그린 배포(Blue-Green Deployment)**: 두 벌을 번갈아 쓰는 무중단 배포
- **nginx reverse proxy, nginx -s reload**: 요청 넘기기와 끊김 없는 설정 다시 읽기
- **Spring Boot graceful shutdown, SIGTERM**: 하던 요청 끝내고 꺼지기
- **Docker multi-stage build**: 빌드용과 실행용 이미지를 나누기
- **Docker network, --env-file, volume**: 컨테이너끼리 이름으로 부르기, 설정 넣기, 데이터 남기기
- **Flyway migration, checksum, outOfOrder**: DB 구조 버전 관리
- **Expand and Contract 패턴**: 컬럼 변경을 두 번에 나누는 방법
- **Spring @Scheduled (cron, fixedRate, fixedDelay)**: 시간 맞춰 도는 일
- **GitHub Actions secrets와 vars**: 비밀값과 일반 설정값을 나눠 넣기
- **Cookie Secure 속성**: HTTPS에서만 쿠키 보내기
- **OAuth redirect URI**: 소셜 로그인 뒤 돌아올 주소를 제공자에 등록하는 이유
