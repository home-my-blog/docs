# 01. 회원과 로그인: 동작 원리

> 기능 설명은 [기능/01-회원과-로그인.md](../기능/01-회원과-로그인.md)에 있어요. 2026-10-14 코드(develop, v1.9.1) 기준이에요.

## 큰 흐름

### 가입: 인증번호를 받아서 회원이 되기까지

1. 브라우저가 앱을 처음 열 때 `GET /api/csrf`를 불러 `XSRF-TOKEN` 쿠키를 받아요(`frontend/src/api/client.ts`의 `refreshCsrf`).
2. "인증번호 받기"를 누르면 `POST /api/auth/verifications` `{purpose: "signup", email, nickname}`을 보내요.
3. `AuthController.sendCode`가 `EmailNormalizer.normalize`로 이메일을 정리하고, `SignupService.checkAvailable`로 이메일·닉네임이 비었는지 PostgreSQL `members` 표에서 확인해요.
4. `EmailVerificationService.send`가 Redis에서 다시 받기 간격과 하루 횟수를 검사하고, 6자리 번호를 만들어 Redis에 10분짜리로 넣은 뒤 `MailSender.send`로 보내요.
5. 응답은 `202 Accepted` `{expiresAt}`이에요. 메일 모드가 `log`이고 용도가 **가입**일 때만 `devCode`(번호)도 같이 실려서 화면(`useEmailVerification`)이 "임시 인증번호"로 보여 줘요. 비밀번호 찾기 번호는 모드와 관계없이 응답에 싣지 않아요(v1.7.1).
6. 번호를 넣으면 `POST /api/auth/verifications/confirm`. `EmailVerificationService.confirm`이 Redis의 번호와 비교하고, 맞으면 번호를 지우고 "인증됨" 표시(30분)를 남겨요.
7. "가입하기"를 누르면 `POST /api/auth/signup`. `SignupService.signup`이 규칙을 다시 검사하고, Redis의 "인증됨" 표시를 **서버가 한 번 더** 확인한 뒤 `members`에 한 줄 넣고 블로그를 만들어요. 마지막에 인증됨 표시를 지워요.
8. 응답은 `201` `{id}`. 화면은 로그인 탭으로 돌아가요.

### 로그인: 비밀번호 확인에서 쿠키까지

1. 브라우저가 `POST /api/auth/login` `{email, password}`를 보내요. 헤더에 `X-XSRF-TOKEN`이 붙어요.
2. `LoginService.login` → `authenticate`가 `members`에서 이메일로 회원을 찾아요. `refuseSocialAccount`가 `password_set`이 false인 회원(소셜 가입)이면 비밀번호를 보기 전에 `409 SOCIAL_ACCOUNT`로 멈춰요. 문구는 `Messages.socialAccount(제공자 이름)`("카카오로 가입한 계정입니다. 카카오로 로그인해 주세요")이고 `error.provider`에 `kakao`/`google`을 실어요(v1.9.0).
3. `verifyPassword`가 잠금을 먼저 보고, BCrypt로 비밀번호를 비교해요. 틀리면 `members.failed_login_count`를 올리고, 5번째면 `locked_until`을 10분 뒤로 적어요.
4. 맞으면 실패 횟수를 0으로 지우고, 탈퇴 신청한 회원이면 `409 ACCOUNT_WITHDRAWN`으로 멈춰요.
5. `startSession`이 세션 번호를 새로 바꾸고(세션 고정 방지), 회원별 세션 목록에 등록하고, "이 세션은 회원 7번" 같은 인증 정보를 세션에 저장해요. 세션은 Spring Session이 Redis(`myblog:session` 아래)에 써요.
6. 응답과 함께 `MYBLOG_SESSION` 쿠키(값은 세션 번호)가 브라우저에 가요.
7. 화면(`AuthProvider.completeLogin`)은 CSRF 토큰을 새로 받고, 캐시를 비운 뒤 `GET /api/auth/me`로 내 정보를 다시 불러요.

### 소셜 로그인: 카카오 · 구글에서 돌아와 회원이 되기까지 (v1.8.0)

1. 화면 `SocialLoginButtons`가 `GET /api/config`의 `socialLogin`(켜진 제공자 목록)을 보고 버튼을 그려요. 버튼은 링크 `/oauth2/authorization/{kakao|google}`예요.
2. 이 주소는 Spring Security `oauth2Login`이 받아요. 상태값(state)을 세션에 두고 제공자의 로그인 화면으로 보내요.
3. 제공자가 `SITE_URL/login/oauth2/code/{kakao|google}?code=...`로 돌려보내면, Spring Security가 code를 토큰으로 바꾸고 회원 정보(user-info)를 받아요.
4. 성공하면 `SocialLoginHandler.onAuthenticationSuccess`가 `SocialProfile.from`으로 필요한 값(제공자 회원 번호, 이메일, 이메일 인증 여부, 닉네임)만 꺼내 `SocialLoginService.complete`에 넘겨요.
5. `complete`가 갈 곳을 정해요(아래 "자세히 보기"). 로그인시킬 때는 비밀번호 로그인과 같은 `LoginService.startSession`을 써요.
6. 처음 보는 이메일이면 가입 대기 정보를 세션에 두고 `/social/signup`으로 보내요. 화면 `SocialSignupPage`가 `GET /api/auth/social/pending`으로 이메일과 추천 닉네임을 받아 보여 주고, 닉네임을 정하면 `POST /api/auth/social/signup` `{nickname}`을 보내요.
7. 가입이 끝나면 응답 `201` `{id, member}`와 함께 바로 로그인돼요. 로그인하지 못한 경우는 홈 `/?social=withdrawn|no-email|failed`로, 같은 이메일이 다른 방법으로 가입돼 있으면 `/?social=email-account|kakao-account|google-account`(v1.9.0)로, 비밀번호 없는 탈퇴 회원이면 `/?social=restore-confirm`(v1.9.2)으로 보내 복구할지 묻고, `SocialLoginNotice`가 안내를 띄운 뒤 주소에서 `social`을 지워요.

## 자세히 보기

### 이메일 정리와 입력 검사

- `EmailNormalizer.normalize`는 앞뒤 공백을 빼고 소문자로 바꾼 뒤 `^[^\s@]+@[^\s@]+\.[^\s@]+$` 모양인지, 254자 이하인지 봐요. 틀리면 `email` 칸 오류를 던져요.
- `NicknamePolicy.validate`는 `^[가-힣A-Za-z0-9]+$`와 글자 수(2~10, 코드 포인트로 셈)를 봐요. 겹침 검사는 `NicknamePolicy.key`(소문자로 바꾼 값)로 해요. DB에도 `nickname_key` 칸에 고유 제약(UNIQUE)이 있어요.
- `PasswordPolicy.isValid`는 한 글자씩 보면서 영문, 숫자, 허용 특수문자를 하나씩 찾아요. 그 밖의 글자가 하나라도 있으면 바로 거절해요.
- 이 프로젝트는 Bean Validation(`@Valid`)을 쓰지 않아요. 서비스 코드가 직접 검사하고 `ApiException.field(...)`로 어느 칸이 틀렸는지 돌려줘요. 화면(`lib/validation`)도 같은 규칙으로 먼저 막지만, 진짜 기준은 서버예요.

### 인증번호를 Redis에 어떻게 두나

`EmailVerificationService`는 키에 용도(`signup`/`reset`)와 이메일을 넣어요. 그래서 가입 인증으로 비밀번호를 바꿀 수 없어요.

| 키 | 값 | 수명 |
| --- | --- | --- |
| `verify:{용도}:{이메일}:code` | 번호 6자 | 10분 |
| `verify:{용도}:{이메일}:fails` | 틀린 횟수 | 10분(틀릴 때마다 다시 10분) |
| `verify:{용도}:{이메일}:cooldown` | `1` | 1분 |
| `verify:{용도}:{이메일}:daily:{yyyyMMdd}` | 오늘 보낸 수 | 처음 보낸 때부터 24시간 |
| `verify:{용도}:{이메일}:verified` | `1` | 30분 |
| `verify:{용도}:{이메일}:confirmed` | `1` | 24시간 |

`send`의 순서는 이래요.
1. 메일을 보내야 하는데 `mail.isAvailable()`이 false면 바로 `MAIL_SEND_FAILED`.
2. `cooldown` 키가 있으면 `RESEND_TOO_SOON`(429).
3. `daily` 값이 5 이상이면 `DAILY_LIMIT`(429). 날짜는 `KoreanClock`의 한국 날짜라서 자정이 지나면 새 키로 세요.
4. `cooldown`을 1분짜리로 넣고 `daily`를 1 올려요(처음이면 24시간 수명을 붙여요).
5. `fails`, `verified`, `confirmed`를 지워요. 새 번호를 받으면 예전 기록이 모두 무효가 되는 이유예요.
6. `VerificationCodeGenerator`가 `SecureRandom`으로 32글자 중에서 6자를 뽑아 `code`에 넣고, `MailTemplates`로 메일 내용을 만들어 보내요.

`confirm`은 입력을 공백 제거, 대문자로 바꾼 뒤 비교해요.
- `code`가 없으면: `fails`가 5 이상이면 `CODE_ATTEMPTS_EXCEEDED`, 아니면 `CODE_EXPIRED`.
- 다르면 `fails`를 1 올리고, 5가 되면 `code`를 지우고 `CODE_ATTEMPTS_EXCEEDED`, 아니면 `CODE_MISMATCH`.
- 맞으면 `code`와 `fails`를 지우고 `verified`(30분), `confirmed`(24시간)를 남겨요.

`requireVerified`는 가입·재설정 직전에 불려요. `verified`가 있으면 통과, 없는데 `confirmed`가 있으면 "시간이 지났다"(`VERIFICATION_EXPIRED`), 둘 다 없으면 "인증 먼저"(`NOT_VERIFIED`)로 나눠 알려 줘요. `confirmed`는 이 두 문구를 구분하려고만 있어요.

### 가입 끝내기와 겹침 처리

- `AuthController.signup`은 먼저 `preventDuplicate("signup", email)`을 불러요. Redis에 `submit:signup:{이메일}`을 5초짜리 `SETNX`(없을 때만 넣기)로 넣어 보고, 이미 있으면 `DUPLICATE_SUBMIT`(409)로 연타를 막아요. Redis가 없으면 이 검사는 건너뛰고 DB 고유 제약에 맡겨요.
- `checkAvailable`은 가입된 이메일이 `password_set` false(소셜 가입)이면 `EMAIL_TAKEN`의 문구를 `Messages.socialEmailTaken(제공자 이름)`("카카오로 가입한 이메일입니다. 카카오로 로그인해 주세요")으로 바꾸고 `provider`를 함께 실어요(v1.9.0). 인증번호 받기 단계에서 걸러져요.
- `SignupService.signup`은 검사 순서가 중요해요. 닉네임·이메일·비밀번호 규칙 → 인증됨 확인 → 다시 `checkAvailable`(인증하는 사이 다른 사람이 먼저 가입했을 수 있어서) → `members.insert`.
- 두 요청이 거의 동시에 들어와 DB 고유 제약에 걸리면 `DuplicateKeyException`이 나요. 이때 `checkAvailable`을 한 번 더 불러 "이미 가입된 이메일" 같은 알기 쉬운 오류로 바꿔요.
- `BlogService.createFor`가 "닉네임의 블로그"를 기본 분야(`myblog.blog.default-topic`, hobby)로 만들고 기본 다이어리를 넣어요. 모두 한 트랜잭션(`@Transactional`)이라 중간에 실패하면 회원도 블로그도 안 생겨요.

### 비밀번호 저장과 확인 (BCrypt)

- `SecurityConfig.passwordEncoder`가 `BCryptPasswordEncoder`를 만들어요. 가입·변경 때 `encoder.encode`로 해시를 만들어 `members.password_hash`에 넣어요.
- BCrypt는 해시마다 소금(salt, 무작위 값)을 섞고 일부러 느리게 계산해요. 같은 비밀번호라도 저장값이 다르고, 하나씩 대입해 보는 공격이 오래 걸려요.
- 로그인 때는 `encoder.matches(입력, 저장값)`으로 비교만 해요. 원래 비밀번호로 되돌리는 방법은 없어요.

### 없는 이메일도 같은 시간 쓰기 (더미 해시)

`LoginService`는 시작할 때 `dummyHash = encoder.encode("dummy-password-1!")`를 하나 만들어 둬요. 이메일로 회원을 못 찾으면 `encoder.matches(password, dummyHash)`를 일부러 한 번 돌리고 `LOGIN_FAILED`를 던져요. BCrypt 비교는 느리기 때문에, 이걸 안 하면 "없는 이메일은 빨리, 있는 이메일은 느리게" 실패해서 응답 시간만 재도 가입 여부를 알 수 있어요. 문구도 둘 다 "이메일 또는 비밀번호가 올바르지 않습니다"로 같아요.

### 5번 실패하면 10분 잠금

`LoginService.verifyPassword`가 맡아요.
1. `locked_until`이 지금보다 뒤면 비밀번호를 보지도 않고 `ACCOUNT_LOCKED`(423)를 던져요. 응답에 `unlockAt`(풀리는 시각)과 남은 분(올림)이 들어가요.
2. `locked_until`이 있지만 이미 지났으면 실패 횟수를 0부터 다시 세요.
3. 틀리면 횟수를 1 올려 `members.recordFailure`로 저장해요. 5번째면 횟수는 0, `locked_until`은 지금 + 10분으로 저장하고 `ACCOUNT_LOCKED`.
4. 맞으면 `authenticate`가 `clearFailures`로 횟수와 잠금을 지워요.

이 메서드에는 `@Transactional(propagation = REQUIRES_NEW, noRollbackFor = ApiException.class)`가 붙어 있어요. 실패하면 예외를 던지는데, 보통은 예외가 나면 DB 변경도 되돌려져요. 따로 새 트랜잭션을 열고 "이 예외에는 되돌리지 마"라고 해서 실패 횟수가 꼭 남게 했어요. 마이페이지의 비밀번호 변경·탈퇴도 같은 메서드를 써서 횟수가 합쳐져요.

### 세션 만들기와 세션 고정 방지

`LoginService.startSession`이 하는 일이에요.
1. `UsernamePasswordAuthenticationToken(회원번호, null, ROLE_MEMBER)`을 만들어요. 주체(principal)가 회원 번호(`Long`)라서 컨트롤러는 `@AuthenticationPrincipal Long memberId`로 바로 받아요.
2. `req.getSession(true)`로 세션을 확실히 만든 뒤 `sessionStrategy.onAuthentication`을 불러요. 이 전략은 `SecurityConfig.loginSessionStrategy`에 두 개가 묶여 있어요.
   - `ChangeSessionIdAuthenticationStrategy`: 세션 번호를 새로 바꿔요. 로그인 전에 누가 내 세션 번호를 알아 두었어도(세션 고정 공격) 로그인 뒤에는 쓸모가 없어져요.
   - `RegisterSessionAuthenticationStrategy`: 이 세션을 회원별 세션 목록(`SessionRegistry`)에 올려요.
3. `SecurityContext`에 인증 정보를 담고 `HttpSessionSecurityContextRepository.saveContext`로 세션에 저장해요.

Spring Security의 폼 로그인(`formLogin`), HTTP Basic, 기본 로그아웃은 모두 꺼 두고 컨트롤러에서 직접 처리해요. JSON으로 답하고 잠금·탈퇴 규칙을 직접 다루기 위해서예요.

### 세션은 Redis에 (Spring Session)

- `application.yml`의 `spring.session.redis.repository-type: indexed`, `namespace: myblog:session`으로 세션을 Redis에 둬요. 서버 메모리도 PostgreSQL도 아니에요.
- 세션 내용은 `myblog:session:sessions:{세션번호}` 같은 키에 들어가요. `indexed`라서 "회원 번호 → 그 회원의 세션들" 색인(index) 키도 같이 관리돼요.
- 서버(블루·그린 두 대)가 같은 Redis를 보니까, 배포로 서버가 바뀌어도 로그인이 유지돼요.
- 세션 수명은 `server.servlet.session.timeout`(= `myblog.session.timeout`, 7일)이에요. 마지막으로 쓴 때부터 7일 동안 안 쓰면 Redis가 지워요.

### 쿠키 7일, 쓸 때마다 연장

- 쿠키 설정은 `server.servlet.session.cookie.*`에 있어요. 이름 `MYBLOG_SESSION`, `HttpOnly`(자바스크립트로 못 읽음), `SameSite=Lax`, `Max-Age` 7일, `Secure`는 `SESSION_SECURE_COOKIE`(기본 false). 운영은 `deploy.sh`가 `app.env`에 `SESSION_SECURE_COOKIE=true`를 넣어서(v1.7.1) HTTPS로만 쿠키가 오가요. 로컬 개발은 http라서 false 그대로 써요.
- `SameSite=Lax`는 다른 사이트에서 넘어오는 링크 이동(GET)에는 쿠키를 보내요. 그래서 카카오 · 구글이 `/login/oauth2/code/...`로 돌려보낼 때도 세션(상태값 확인용)이 이어져요.
- 그런데 Spring Session은 세션 번호가 새로 생길 때만 쿠키를 다시 보내요. 그대로 두면 7일 뒤 쿠키가 사라져요.
- 그래서 `SessionCookieRefreshFilter`가 모든 요청이 끝난 뒤, 브라우저가 보낸 세션 번호가 유효하고 지금 세션과 같으면 같은 쿠키를 `Max-Age` 7일로 다시 내려 줘요. 쓸 때마다 7일이 새로 시작되는 이유예요.
- 이 필터는 세션 번호를 그대로 쿠키 값에 써요. Spring Session은 원래 base64로 바꿔 담기 때문에 둘이 어긋나면 다음 요청에서 세션을 못 찾아요. 그래서 `SecurityConfig.plainSessionCookie`(`DefaultCookieSerializerCustomizer`)로 base64를 꺼서 둘 다 번호 그대로 쓰게 맞췄어요.

### 다른 기기 로그아웃

- `SecurityConfig.sessionRegistry`는 Redis 세션 저장소(`FindByIndexNameSessionRepository`)가 있으면 `SpringSessionBackedSessionRegistry`를 써요. 회원 번호로 그 회원의 세션들을 Redis 색인에서 찾아요. (Redis 세션을 끈 테스트에서만 메모리용 `SessionRegistryImpl`을 써요.)
- `MemberSessionService.expireAll(memberId, exceptSessionId)`가 그 목록을 돌면서 `expireNow()`로 "만료됨" 표시를 붙여요. `exceptSessionId`가 있으면 그 세션(지금 기기)은 건너뛰어요.
  - 비밀번호 변경(`MyPageService.changePassword`): 지금 세션 번호를 넘겨서 다른 기기만 끊어요.
  - 비밀번호 찾기(`PasswordResetService.reset`), 탈퇴(`MyPageService.withdraw`, 소셜 탈퇴는 `SocialLoginService.completeWithdraw`): `null`을 넘겨서 모두 끊어요.
- 끊긴 기기가 다음 요청을 보내면 Spring Security의 동시 세션 필터가 만료 표시를 보고 로그아웃시키고, `expiredSessionStrategy`가 `401 UNAUTHENTICATED`를 써 줘요. 화면은 401을 보고 로그인 창을 띄워요.
- `maximumSessions(-1)`이라 동시에 로그인할 수 있는 기기 수에는 제한이 없어요. 이 설정은 세션 목록을 쓰기 위해 켠 거예요.

### CSRF: XSRF-TOKEN 쿠키 + X-XSRF-TOKEN 헤더

- CSRF(사이트 간 요청 위조)는 내가 로그인한 채로 나쁜 사이트에 갔을 때, 그 사이트가 몰래 사각으로 요청을 보내는 공격이에요. 브라우저가 쿠키를 자동으로 붙이니까 서버는 내가 보낸 줄 알아요.
- `SecurityConfig`는 `CookieCsrfTokenRepository.withHttpOnlyFalse()`로 무작위 토큰을 `XSRF-TOKEN` 쿠키에 담아 줘요. 화면 자바스크립트가 읽어야 하니까 HttpOnly가 아니에요.
- `CsrfTokenRequestAttributeHandler`의 요청 속성 이름을 `null`로 두어, 토큰을 미루지 않고 요청마다 쿠키로 내려 주게 했어요. SPA(한 페이지 앱)가 언제든 쿠키에서 토큰을 읽을 수 있게 하려는 설정이에요.
- `client.ts`의 `send`는 GET이 아닌 모든 요청에 쿠키 값을 `X-XSRF-TOKEN` 헤더로 옮겨 적어요. 다른 사이트는 사각의 쿠키를 읽을 수 없으니 이 헤더를 채울 수 없고, 서버는 헤더가 없거나 틀리면 403으로 거절해요.
- 로그인, 가입, 인증번호 요청도 POST라서 모두 이 헤더가 필요해요.
- 로그인·로그아웃 뒤에는 `refreshCsrf()`로 `GET /api/csrf`를 다시 불러 토큰을 새로 받아요. 그래도 403이 오면 `api()`가 토큰을 한 번 새로 받아 같은 요청을 한 번만 다시 보내요.

### 로그아웃

- 화면(`AuthProvider.doLogout`)이 `POST /api/auth/logout`을 보내요. 실패해도(이미 끊긴 세션 등) 화면은 로그아웃 상태로 바꿔요.
- `AuthController.logout`은 `session.invalidate()`로 세션을 지우고 `SecurityContextHolder.clearContext()`를 불러요. 응답은 204예요.
- 이 주소는 `SecurityConfig`에서 공개 목록에 없어서 로그인한 사람만 부를 수 있어요. 로그인 안 한 채로 부르면 401이 와요(화면은 무시해요).

### 비밀번호 찾기

1. `POST /api/auth/verifications` `{purpose: "reset", email}`. 컨트롤러(`AuthController.sendCode`)는 `members.findByEmail`로 탈퇴 신청 안 한 회원을 찾아 "번호 메일을 보낼지"만 정해요. 그 회원이 `password_set` false(소셜 가입)이면 번호는 보내지 않고(`sendMail=false`), `send`가 끝난 뒤 `MailTemplates.socialAccountNoPassword(제공자 이름)` 안내 메일(제목 "[사각] 비밀번호 찾기 안내")을 보내요(v1.9.0). 본문은 "이 이메일은 사각 카카오로 가입한 계정이라 비밀번호가 없습니다."로 시작해 로그인 창의 "카카오로 시작하기"를 누르라고 알려 줘요.
2. 회원이 아니거나 소셜 가입 회원이면 `send(..., sendMail=false)`: 번호는 만들지 않고 `code` 키를 지우지만, `cooldown`과 `daily`는 똑같이 올려요. 응답은 회원이든 아니든, 소셜 가입 회원이든 `{expiresAt}` 하나로 똑같아요. 그래서 응답으로 가입 여부를 알 수 없어요.
   - v1.7.1 전에는 `log` 모드에서 이 응답에도 `devCode`가 실렸어요. 회원이면 번호가 보이고 아니면 안 보여서 가입 여부가 드러났고, 무엇보다 남의 이메일로 번호를 받아 그 사람 비밀번호를 바꿀 수 있었어요. 지금은 `AuthController.sendCode`가 `purpose == SIGNUP`일 때만 `devCode`를 넣어요.
3. 확인은 가입과 같은 `confirm`이에요. 회원이 아니거나 소셜 가입 회원이면 `code`가 없어서 늘 `CODE_EXPIRED`가 돼요.
4. `POST /api/auth/password-reset` `{email, newPassword, newPasswordConfirm}`. 컨트롤러는 로그인한 사람이면 `403 FORBIDDEN`으로 막아요.
5. `PasswordResetService.reset`: 새 비밀번호 규칙 → `requireVerified(RESET)` → 인증됨 표시 지우기 → 탈퇴 신청 안 했고 `password_set`이 true인 회원이 있으면(v1.9.0) `updatePassword`(해시 바꾸고 실패 횟수·잠금도 지움) → `expireAll(id, null)` → "비밀번호가 변경되었습니다" 메일.

### 마이페이지

- `/api/me/**`는 `SecurityConfig`에서 로그인 필수예요. `MyPageController`가 주소를 받고 `MyPageService`가 일을 해요.
- `GET /api/me`: 이메일, 닉네임, 소개, 가입일, 내 블로그 번호, `passwordSet`(`members.passwordSet`), `socialAccounts`(`SocialAccountRepository.providersOf`가 연결한 순서로 돌려준 제공자를 소문자로, 예: `["kakao"]`). 화면 `MyPage`는 `passwordSet`이 false면 비밀번호 변경 칸을 그리지 않고, `socialAccounts`가 있으면 "연결된 계정" 줄에 "카카오 계정으로 로그인해요"처럼 보여 줘요(v1.8.1).
- `PATCH /api/me` `{nickname?, bio?}`: 보낸 칸만 바꿔요. 닉네임 겹침은 `existsByNicknameKey(key, 내 번호)`로 나를 빼고 봐요. 소개는 100자를 넘으면 거절해요. 블로그 이름은 건드리지 않아요.
- `PUT /api/me/password`: `password_set`이 false면 맨 먼저 `400 PASSWORD_NOT_SET`("소셜 로그인으로 가입한 계정은 비밀번호가 없습니다")으로 거절해요(v1.8.1). 그다음 현재 비밀번호를 `verifyPassword`로 확인(틀리면 `CURRENT_PASSWORD_MISMATCH`, 실패 횟수에 더해짐) → 새 비밀번호 규칙 → 지금 해시와 같으면 `SAME_AS_CURRENT` → 저장 → 다른 기기 로그아웃 → 알림 메일.

### 탈퇴와 30일 안 복구

- `DELETE /api/me` `{password, acknowledged}`: `acknowledged`가 true가 아니면 `ACKNOWLEDGE_REQUIRED`. `password_set`이 false(소셜 가입)면 `400 SOCIAL_WITHDRAW_ONLY`("소셜 로그인으로 가입한 계정은 가입한 소셜 계정으로 다시 확인하고 탈퇴합니다")로 거절해요(v1.9.1, 아래 "소셜 계정으로 확인하고 탈퇴"). 그 밖에는 비밀번호를 확인하고(틀리면 `CURRENT_PASSWORD_MISMATCH`, 실패 횟수에 더해짐), 확인이 끝나면 `members.markWithdrawn`으로 `deleted_at`만 찍어요(소프트 삭제, 실제로 지우지 않고 표시만 하기). 그리고 모든 세션을 끊고 지금 세션도 `invalidate`해요.
- `deleted_at`이 있는 회원(`Member.withdrawn()`)은 여러 조회 코드가 `deleted_at IS NULL` 조건으로 걸러요. 블로그·글 목록이나 검색에서 빠지고, 댓글은 `CommentService`가 작성자 번호를 비워서 "탈퇴한 사용자"로 보여요.
- 가입 때 `checkAvailable`은 탈퇴 신청한 이메일이면 `EMAIL_WITHDRAWN`을 돌려줘요. `existsByEmail`이 탈퇴 신청 회원도 세기 때문에 같은 이메일로는 못 들어와요.
- 로그인 때 비밀번호가 맞고 `withdrawn()`이면 `409 ACCOUNT_WITHDRAWN`과 `restorableUntil`(= `deleted_at` + 30일)을 돌려줘요. 화면 `LoginForm`이 `window.confirm`으로 물어보고, 그러겠다고 하면 같은 이메일·비밀번호로 `POST /api/auth/restore`를 보내요.
- `LoginService.restore`는 비밀번호를 다시 확인하고, 탈퇴 신청 회원이 아니면 `LOGIN_FAILED`로 거절해요. 맞으면 `members.restore`(`anonymized_at IS NULL`일 때만 `deleted_at`을 비움)를 하고 세션을 시작해요.
- 소셜 가입 회원(`password_set` false)은 이메일 로그인을 못 하니, 가입한 소셜 계정으로 들어오면 `SocialLoginService.logInOrRefuse`가 묻지 않고 같은 `members.restore`를 부른 뒤 로그인시켜요(v1.8.1, 위 "어디로 보낼지 정하기" 2번).

### 소셜 계정으로 확인하고 탈퇴 (v1.9.1)

소셜 가입 회원은 비밀번호가 없어서, 가입한 제공자에 다시 로그인하는 것으로 본인을 확인해요. v1.8.1의 "탈퇴합니다" 문구(`WITHDRAW_PHRASE`)와 `confirmText`는 없어졌어요.

1. 화면 `MyPage`가 `passwordSet` false면 비밀번호 칸 대신 안내 문구와 **{카카오|구글}로 확인하고 탈퇴하기** 버튼을 그려요. 확인란 체크와 `window.confirm`을 거친 뒤 `POST /api/me/withdraw/social` `{acknowledged: true}`를 보내요.
2. `MyPageController.withdrawBySocial` → `SocialLoginService.startWithdraw`: `acknowledged`가 아니면 `ACKNOWLEDGE_REQUIRED`, `password_set`이 true(또는 가입 제공자가 없음)면 `400 PASSWORD_WITHDRAW_ONLY`("비밀번호를 입력해 탈퇴해 주세요"). 통과하면 세션 속성 `myblog.socialWithdraw`에 `WithdrawIntent(memberId, provider, expiresAt = 지금 + 10분)`을 넣고 `{redirectUrl: "/oauth2/authorization/{provider}"}`를 돌려줘요.
3. 화면이 `window.location.assign(redirectUrl)`로 이동해요. `SecurityConfig.ReconfirmingAuthorizationRequestResolver`(직접 만든 `OAuth2AuthorizationRequestResolver`)가 기본 resolver를 감싸서, 세션에 `WithdrawIntent`가 있으면 인가 요청에 `prompt`를 더해요. 카카오는 `prompt=login`(다시 로그인), 구글은 `prompt=select_account`(계정을 다시 고르기)예요. 제공자에 이미 로그인돼 있어도 그냥 통과되지 않게 하려는 거예요.
4. 돌아오면 `SocialLoginService.complete`가 맨 먼저 `WithdrawIntent`를 보고(있으면 세션에서 지우고) `completeWithdraw`로 가요.
   - 회원이 없거나 이미 탈퇴 상태면 인증 정보를 지우고 `/?social=failed`.
   - 제공자가 같고, (제공자, 제공자 회원 번호)의 연결이 그 회원이고, 10분이 안 지났으면: `members.markWithdrawn` → `MemberSessionService.expireAll(id, null)`(모든 기기 로그아웃) → 인증 정보 지우기 → 세션 `invalidate` → `/?social=withdraw-done`("탈퇴 신청이 완료되었습니다").
   - 다른 계정이거나 시간이 지났으면 탈퇴하지 않고 `startSession`으로 원래 회원 로그인을 되돌려요. 제공자 로그인이 끝나면 Spring Security가 세션의 인증 정보를 소셜 토큰으로 바꿔 두기 때문이에요. → `/me?social=withdraw-mismatch`("가입한 계정과 다른 계정으로 확인해 탈퇴하지 않았습니다. 가입한 계정으로 다시 시도해 주세요").
5. 제공자 화면에서 취소하면 `SocialLoginHandler.onAuthenticationFailure` → `SocialLoginService.failed`가 `WithdrawIntent`를 보고, 지운 뒤 로그인은 그대로 두고 `/me?social=withdraw-cancelled`("탈퇴 확인을 취소해 탈퇴하지 않았습니다")로 보내요. 탈퇴 확인 중이 아니면 예전처럼 인증 정보를 지우고 `/?social=failed`예요.

`WithdrawIntent`는 `Pending`처럼 `Serializable` record예요. 세션(Redis)에만 있고, 확인이 끝나거나 취소되면 지워요.

### 탈퇴 정리 스케줄 (04:40 익명화)

- `WithdrawalCleaner.scheduled`에 `@Scheduled(cron = "0 40 4 * * *", zone = "Asia/Seoul")`이 붙어 있어 매일 한국 시간 새벽 4시 40분에 돌아요.
- `cleanUp`은 `deleted_at <= 지금 - 30일`이고 `anonymized_at IS NULL`인 회원 번호를 모아, 한 명마다 따로 트랜잭션(`TransactionTemplate`)을 열어 `anonymize`를 해요. 한 명이 실패해도 다른 사람 정리는 계속돼요.
- `anonymize`의 순서예요.
  1. 지울 사진의 저장 키를 먼저 모아요(내가 올린 것 + 내 글에 붙은 것).
  2. 글 → 블로그 → 내가 누른 좋아요 → 임시저장 → 내가 올린 사진 기록 순으로 지워요. 글을 먼저 지우는 건 다이어리(분류) 쪽 외래 키가 RESTRICT(참조하는 줄이 있으면 못 지움)라서예요.
  3. 회원 줄은 남기고 이메일을 `del_{12자}@deleted.invalid`, 닉네임을 겹치지 않는 `del{7자}`로, 비밀번호 해시를 `!{40자}`(BCrypt 형식이 아니라 어떤 비밀번호와도 안 맞음)로, 소개를 빈 값으로 바꾸고 `anonymized_at`을 찍어요.
  4. `images.deleteFilesAfterCommit`으로 사진 파일은 DB 반영(커밋)이 끝난 뒤에 지워요. DB가 실패했는데 파일만 사라지는 일을 막아요.
- `deleted_at`은 그대로 남아서 계속 "탈퇴한 사용자"로 보이고, 복구는 `anonymized_at` 조건 때문에 안 돼요.

### 권한: SecurityConfig 규칙

`SecurityConfig.filterChain`의 `authorizeHttpRequests`는 위에서부터 처음 맞는 규칙을 써요.

| 순서 | 주소 | 규칙 |
| --- | --- | --- |
| 1 | `/api/me/**`, `/api/manage/**` (모든 메서드) | 로그인 필요 |
| 2 | `GET /api/posts/*/edit` | 로그인 필요 |
| 3 | 그 밖의 `GET /api/**` | 누구나 |
| 4 | `/api/auth/verifications`, `/api/auth/verifications/**`, `/api/auth/signup`, `/api/auth/login`, `/api/auth/restore`, `/api/auth/password-reset`, `/api/auth/social/signup` | 누구나 |
| 5 | 그 밖의 `/api/**` (POST·PUT·PATCH·DELETE) | 로그인 필요 |
| 6 | API가 아닌 주소(화면 파일, 소셜 로그인 `/oauth2/authorization/*`, `/login/oauth2/code/*` 등) | 누구나 |

- 로그인이 필요한데 없으면 `authenticationEntryPoint`가 `401 UNAUTHENTICATED` JSON을 써요. `client.ts`가 401을 받으면 `myblog:unauthenticated` 이벤트를 보내고, `AuthProvider`가 듣고 로그인 창을 열어요. `useRequireLogin`은 하려던 동작을 기억했다가 로그인 뒤에 다시 실행해요.
- 이 표는 "로그인했나"만 봐요. "내 글인가", "내 블로그인가" 같은 주인 확인은 각 서비스 코드가 회원 번호를 비교해서 따로 해요.
- `GET /api/auth/social/pending`은 3번 규칙(GET은 누구나)으로 열려 있어요. 세션에 가입 대기 정보가 없으면 404예요.
- 소셜 로그인 키가 하나라도 있을 때만 `oauth2Login`을 켜요(`socialClients.isEmpty()` 검사). `loginPage("/")`로 Spring의 기본 로그인 화면(`/login`)은 만들지 않아요. 인가 요청은 `authorizationEndpoint`에 넣은 `ReconfirmingAuthorizationRequestResolver`가 만들어요. 평소에는 기본 resolver와 똑같고, 소셜 탈퇴 확인 중일 때만 `prompt`를 더해요(v1.9.1).
- `GET /api/auth/me`는 누구나 부를 수 있고, 로그인 안 했거나 탈퇴 신청 상태면 204(빈 응답)를 돌려줘요. 화면은 이걸로 로그인 여부를 알아요.

### 소셜 로그인 제공자 등록: SocialClientRegistrations

- `config/SocialClientRegistrations`는 `ClientRegistrationRepository`를 직접 구현해요. `myblog.oauth.kakao.client-id`, `myblog.oauth.google.client-id`가 비어 있지 않은 제공자만 목록에 넣어요.
- Spring의 `spring.security.oauth2.client.registration` 설정을 쓰지 않은 이유는 클래스 주석에 있어요. 그 설정은 값이 비어 있으면 서버가 뜨지 않아서, 키가 없는 환경(로컬, CI)에서도 서버가 뜨게 하려고요.
- 돌아올 주소는 `myblog.oauth.redirect-base`(= 환경 변수 `SITE_URL`) + `/login/oauth2/code/{registrationId}`예요. `SITE_URL`이 비면 요청 주소(`{baseUrl}`)를 쓰고, 끝의 `/`는 떼요. 로컬 개발은 Vite 프록시가 `/oauth2`, `/login/oauth2`도 서버로 넘기고 Host를 그대로 두어서 `http://localhost:5173/login/oauth2/code/...`가 돼요.
- 카카오는 Spring에 기본 설정이 없어서 주소를 직접 적어요: 인증 `kauth.kakao.com/oauth/authorize`, 토큰 `kauth.kakao.com/oauth/token`, 회원 정보 `kapi.kakao.com/v2/user/me`, 동의 항목 `profile_nickname`, `account_email`, client secret은 POST 몸통(`CLIENT_SECRET_POST`)으로 보내요.
- 구글은 `CommonOAuth2Provider.GOOGLE`을 쓰고 동의 항목은 `openid`, `profile`, `email`이에요.
- `enabledIds()`가 켜진 제공자 이름(kakao, google 순)을 돌려주고, `ConfigController`가 이것을 `/api/config`의 `socialLogin`으로 내려 줘요. 키가 없으면 `[]`라서 버튼이 안 보여요.
- 제공자의 액세스 토큰은 회원 정보를 받는 데만 쓰고 보관하지 않아요. `SecurityConfig.DiscardingAuthorizedClientRepository`가 저장을 버려요. 기본 저장소는 로그인마다 토큰을 서버 메모리에 쌓기 때문이에요.

### 제공자 정보 꺼내기: SocialProfile

| --- | --- | --- | --- | --- |
| 카카오 | `id` | `kakao_account.email` | `kakao_account.is_email_verified` | `kakao_account.profile.nickname` (없으면 `properties.nickname`) |

`SocialProvider`는 enum `KAKAO`, `GOOGLE`이에요. DB(`member_social_accounts.provider`)에는 대문자 이름 그대로, 주소와 화면에는 소문자(`kakao`)로 써요.

### 어디로 보낼지 정하기: SocialLoginService.complete

`@Transactional`이 붙어 있어요. 위에서부터 처음 맞는 경우로 가요.

| 순서 | 조건 | 하는 일 | 보내는 곳 |
| --- | --- | --- | --- |
| 0 | 세션에 탈퇴 확인 정보(`WithdrawIntent`)가 있음(v1.9.1) | 정보를 지우고 `completeWithdraw` (위 "소셜 계정으로 확인하고 탈퇴") | `/?social=withdraw-done`, `/me?social=withdraw-mismatch`, `/?social=failed` 중 하나 |
| 1 | 제공자 회원 번호가 없음 | 인증 정보 지우기 | `/?social=failed` |
| 2 | `member_social_accounts`에 (제공자, 제공자 회원 번호)가 있음 | `logInOrRefuse`: 탈퇴 신청 상태면 인증 정보를 지우고, `password_set`이 false면 세션에 `PendingRestore`(회원 번호, 10분)를 둬요(v1.9.2). 아니면 `startSession` | 복구 대기면 `/?social=restore-confirm`, 탈퇴면 `/?social=withdrawn`, 아니면 `/` |
| 3 | 이메일이 없거나 제공자가 인증하지 않음(`emailVerified` false), 또는 이메일 모양이 틀림 | 인증 정보 지우기 | `/?social=no-email` |
| 4 | 그 이메일의 회원이 있고 `password_set`이 false(다른 소셜로 가입)(v1.9.0) | 연결하지 않고 인증 정보 지우기. 탈퇴 상태여도 같아요 | `/?social={가입 제공자}-account` (`SocialLoginService.otherProvider`, 예: `/?social=kakao-account`). 가입 제공자를 못 찾으면 `/?social=failed` |
| 5 | 그 이메일의 회원이 있고 이메일 가입(`password_set` true)(v1.9.0) | 연결하지 않고 인증 정보 지우기 | 탈퇴 신청 상태면 `/?social=withdrawn`, 아니면 `/?social=email-account` |
| 6 | 처음 보는 이메일 | 인증 정보 지우고, 세션 속성 `myblog.socialSignup`에 가입 대기 정보(`Pending`)를 넣어요 | `/social/signup` |

- 이메일은 `EmailNormalizer.normalize`로 이메일 가입과 똑같이 정리한 뒤 비교해요.
- **인증된 이메일만 믿어요.** 제공자가 인증하지 않은 이메일은 받지 않아요(`SocialProfile` 주석). 이 이메일이 소셜 가입 회원의 이메일이 되고, 같은 이메일의 가입 방법을 찾는 데도 쓰이기 때문이에요.
- **같은 이메일이어도 연결하지 않아요(v1.9.0).** v1.8.0~v1.8.1에서는 4·5번 경우에 기존 회원에 연결하고 로그인시켰어요. 지금은 계정마다 가입한 방법 하나로만 로그인하고, 어느 방법으로 로그인하면 되는지만 알려 줘요.
- "인증 정보 지우기"(`forgetAuthentication`)는 `oauth2Login`이 세션에 넣어 둔 소셜 인증(`OAuth2AuthenticationToken`)을 빈 `SecurityContext`로 덮어써요. 우리 회원으로 로그인시키지 않을 때 소셜 인증만 남아 있으면 안 되니까요.
- 핸들러에서 예외가 나면(`RuntimeException`) 인증 정보를 지우고 `/?social=failed`로 보내요. 사용자가 동의를 취소하는 등 `oauth2Login` 자체가 실패하면(`onAuthenticationFailure`) `SocialLoginService.failed`가 탈퇴 확인 중이었는지 보고, 아니면 인증 정보를 지우고 `/?social=failed`, 맞으면 `/me?social=withdraw-cancelled`로 보내요.
- `Pending`은 `Serializable` record예요. 세션이 Redis에 저장되기 때문이에요.
- 2번의 복구는 가입한 소셜 계정으로 들어왔을 때만 해요. v1.9.2부터는 이메일 로그인처럼 바로 복구하지 않고 화면이 묻는데, `SocialLoginNotice`가 `GET /api/auth/social/restore`로 복구 기한을 받아 `window.confirm`으로 묻고, 확인하면 `POST`(복구하고 `startSession`), 취소하면 `DELETE`(대기 정보 지우기)를 불러요. 탈퇴 직후 실수로 로그인해도 탈퇴가 취소되지 않게 하려는 거예요. 그 계정의 주인임이 확인된 셈이라, 비밀번호가 없는 회원에게 이메일 로그인 대신 이 길을 열어 줬어요. 4·5번처럼 이메일만 같은 소셜 계정으로는 연결하지도, 복구하지도 않아요.
- 화면 `SocialLoginNotice`는 `restore-confirm`이면 위처럼 묻고, 복구하면 "탈퇴 신청을 취소하고 계정을 복구했어요. 다시 만나서 반가워요!"를, `withdraw-done`("탈퇴 신청이 완료되었습니다")을 보통 안내로, 나머지는 오류 안내로 띄워요. `email-account`는 "이메일로 가입한 계정입니다. 이메일과 비밀번호로 로그인해 주세요", `kakao-account`·`google-account`는 "카카오로 가입한 이메일입니다. 카카오로 로그인해 주세요"(구글이면 "구글로 …")예요(v1.9.0).

### 소셜 가입 끝내기: SocialAuthController와 SocialLoginService.signup

- `GET /api/auth/social/pending`: 세션의 `Pending`에서 `{provider, email, nickname}`을 돌려줘요. 없으면 `404 SOCIAL_SIGNUP_NOT_FOUND`.
- 추천 닉네임(`suggestNickname`)은 제공자 닉네임에서 `[^가-힣A-Za-z0-9]`를 지우고 최대 길이(10자, 코드 포인트)로 잘라요. 최소 길이(2자)보다 짧으면 빈 값이라 화면에서 직접 넣어요.
- `POST /api/auth/social/signup` `{nickname}`:
  1. `Pending`이 없으면 `404 SOCIAL_SIGNUP_NOT_FOUND`.
  2. `preventDuplicate("social-signup", "KAKAO:<제공자 회원 번호>")`로 5초 연타를 막아요(Redis `submit:social-signup:...`).
  3. `SocialLoginService.signup`(`@Transactional`): `NicknamePolicy.validate` → `SignupService.createMember`(이메일 가입과 같은 함수. 겹침 확인, `members` 넣기, 블로그와 기본 다이어리 만들기) → `members.markPasswordUnset`(`password_set = false`, v1.8.1) → `member_social_accounts`에 연결 → 세션에서 `Pending` 지우기 → `startSession`.
  4. 응답은 `201` `{id, member}`. 이메일 가입(`{id}`)과 로그인(`member`)을 합친 모양이에요.
- 비밀번호 해시는 `SecureRandom` 32바이트를 base64로 만든 값을 BCrypt로 섞어 넣어요. 아무도 모르는 값이고, v1.9.0부터는 이메일 로그인 자체를 `SOCIAL_ACCOUNT`로 막고 비밀번호 찾기도 이 회원의 비밀번호를 바꾸지 않아요.
- 그래서 v1.8.1부터 `members.password_set`(V22)으로 "직접 정한 비밀번호가 있는지"를 따로 적어요. 소셜 가입은 `false`로 시작하고, `MemberRepository.updatePassword`(비밀번호 찾기와 비밀번호 변경이 함께 씀)가 해시를 바꿀 때 `true`로 바꿔요. 두 곳 모두 v1.9.0부터 `true`인 회원에게만 쓰이니, 소셜 가입 회원은 계속 `false`예요.
- 컬럼 기본값이 `true`라 V22는 그 전에 있던 회원을 모두 `true`로 채웠어요. 그래서 v1.8.0 때 카카오 · 구글로 가입한 회원도 `true`가 되어, 정한 적 없는 비밀번호를 물어 탈퇴할 수 없었어요. `V23__social_signup_password_unset.sql`이 가입 직후 5초 안에 소셜 연결이 생긴 회원을 소셜 가입 회원으로 보고 `false`로 되돌려요(v1.9.0, 데이터만 바꾸는 마이그레이션).
- `password_set`이 `false`인 회원은 이메일 로그인이 막히고(`SOCIAL_ACCOUNT`), 비밀번호 변경이 막히고(`PASSWORD_NOT_SET`), 탈퇴는 가입한 소셜 계정으로 다시 확인하고(v1.9.1), 복구는 가입한 소셜 로그인으로 해요(위 "마이페이지", "탈퇴와 30일 안 복구", "소셜 계정으로 확인하고 탈퇴").

### 연결은 언제 사라지나

- `member_social_accounts.member_id`는 `members`를 `ON DELETE CASCADE`로 가리켜요. 다만 회원 줄은 지우지 않으니, 실제로는 `WithdrawalCleaner.anonymize`가 익명화할 때 `DELETE FROM member_social_accounts WHERE member_id = ?`로 지워요. 그 뒤에는 같은 소셜 계정으로 새로 가입할 수 있어요.
- (제공자, 제공자 회원 번호)에 고유 제약이 있어서 소셜 계정 하나는 회원 한 명에게만 연결돼요. v1.9.0부터는 소셜 가입할 때만 연결을 만들어서, 연결은 소셜 가입 회원에게 가입한 제공자 하나뿐이에요(`SocialAccountRepository.signupProviderOf`).
- `V24__separate_signup_methods.sql`은 이메일 가입 회원(`password_set` true)에게 v1.8.0~v1.8.1 동안 자동으로 붙은 연결을 지웠어요(v1.9.0, 데이터만 바꾸는 마이그레이션). 그 회원은 이메일과 비밀번호로 로그인해요.
- 연결을 끊는 API는 없어요.

### Redis가 꺼지면 (RedisGuard)

`RedisGuard`는 Redis 오류(`DataAccessException`)를 두 가지로 다뤄요.
- `required`: 인증번호 받기·확인, 인증됨 확인처럼 Redis 없이 못 하는 일. `503 SERVICE_UNAVAILABLE`("잠시 뒤 다시 시도해 주세요").
- `optional`: 가입 연타 막기, 인증됨 표시 지우기처럼 건너뛰어도 되는 일. 빈 값을 돌려주고 넘어가요.

세션 자체가 Redis에 있으므로, Redis가 꺼지면 로그인과 로그인한 상태로 하는 일은 안 돼요. 로그인 없이 글 읽기는 PostgreSQL만 쓰니까 돼요.

### 메일 보내기 (mail 패키지)

- `MailSender` 인터페이스에 구현이 두 개예요. `myblog.mail.mode`가 `log`(기본)이면 `LogMailSender`가 서버 로그에 `[메일] to=... subject=...`로 찍기만 하고, `smtp`면 `SmtpMailSender`가 Spring Mail로 보내요.
- `SmtpMailSender.isAvailable`은 `testConnection()`으로 SMTP 서버에 바로 붙어 봐요. 실제 `send`는 `@Async("mailExecutor")`로 따로 돌아서, 보내기 실패는 로그로만 남아요. 그래서 붙어 볼 수 없으면 인증번호 요청 자체를 `MAIL_SEND_FAILED`로 바로 거절해요.
- `MailTemplates`가 가입 인증번호, 비밀번호 찾기 인증번호, 소셜 가입 계정의 비밀번호 찾기 안내(`socialAccountNoPassword`, v1.9.0), 비밀번호 변경 알림 네 가지 내용을 만들어요. 유효시간 숫자는 `code-ttl` 설정에서 가져와요.
- 운영 배포(`deploy/deploy.sh`)는 GitHub Secrets에 `SMTP_HOST`가 있을 때만 `app.env`에 `MYBLOG_MAIL_MODE=smtp`와 `SMTP_*`, `MAIL_FROM`을 적어요(v1.7.1). 없으면 기본 `log` 모드예요.

## 데이터는 어디에

| 무엇 | 어디에 | 언제 사라지나 |
| --- | --- | --- |

| 소셜 가입 대기 정보 | 세션 속성 `myblog.socialSignup` (Redis 세션 안) | 가입을 마치거나 세션이 끝날 때 |
| 소셜 탈퇴 확인 정보(`WithdrawIntent`: 회원 번호, 제공자, 마감 시각) | 세션 속성 `myblog.socialWithdraw` (Redis 세션 안, v1.9.1) | 제공자에서 돌아오거나 취소할 때. 마감은 10분 |
| 로그인 세션(누가 로그인했나) | Redis `myblog:session:...` (Spring Session) | 7일 동안 안 쓰면, 로그아웃·만료 처리 때 |
| 회원별 세션 목록 | Redis `myblog:session:` 아래 색인 키 | 세션과 함께 |
| 세션 쿠키 `MYBLOG_SESSION` | 브라우저 쿠키(HttpOnly) | 7일, 쓸 때마다 연장 |
| CSRF 토큰 `XSRF-TOKEN` | 브라우저 쿠키(자바스크립트로 읽기 가능) | 브라우저를 닫으면(세션 쿠키) |
| 내 정보 캐시 | 브라우저 메모리(React Query `me`) | 새로고침, 로그아웃 때 |

## 왜 이렇게 만들었나

- **세션 + 쿠키를 고르고 JWT는 안 씀**: research.md §2에 JWT는 기술스택에서 뺐다고 적혀 있어요. 세션은 서버가 끊을 수 있어서, 비밀번호 변경·탈퇴 때 다른 기기를 로그아웃하는 기능을 만들 수 있어요.
- **세션을 Redis에**: research.md는 처음에 PostgreSQL(Spring Session JDBC)로 정했지만, 지금 코드는 Redis예요. `SecurityConfig`와 `application.yml`의 주석에 이유가 있어요. 서버를 새로 띄워도 로그인이 유지돼 무중단 배포가 되고, 두 서버가 같은 세션을 봐요. `indexed`는 회원별 세션 목록을 Redis가 들고 있게 해서 다른 기기 로그아웃을 하기 위해서예요.
- **폼 로그인 대신 컨트롤러에서 직접 로그인**: research.md §2. JSON 응답과 잠금 규칙을 직접 다루기 위해서예요.
- **CSRF를 끄지 않음**: research.md §2에 "CSRF 끄기"는 요구사항(NF-11) 위반이라 버린 선택지로 적혀 있어요. SPA에서 쿠키 세션과 CSRF를 같이 쓰는 표준 구성이 쿠키 토큰 + 헤더예요.
- **인증번호를 Redis에, 키에 용도 넣기**: research.md §3. DB 표에 넣으면 만료된 번호를 치우는 작업이 따로 필요한데, Redis는 수명(TTL)이 지나면 저절로 지워요. 용도를 키에 넣어 가입 인증으로 비밀번호를 바꾸지 못하게 했어요.
- **비밀번호 찾기에서 가입 여부 숨기기**: research.md §3, 코드 주석(CF-25-3). 없는 이메일에도 횟수를 똑같이 세고 같은 응답을 줘요.
- **소셜 로그인을 Spring Security oauth2Login으로, 세션은 그대로**: 제공자와 주고받는 OAuth2 절차(state, code 교환)는 Spring Security에 맡기고, 끝난 뒤에는 우리 세션(`startSession`)으로 바꿔 끼워요. 그래서 로그인 뒤의 동작(7일 유지, 다른 기기 로그아웃, CSRF)이 이메일 로그인과 똑같아요. 키가 없는 제공자는 켜지 않아 로컬·CI에서도 서버가 떠요(`SocialClientRegistrations` 주석).
- **가입한 방법으로만 로그인, 같은 이메일이어도 연결하지 않음**(v1.9.0): v1.8.0은 계정이 둘로 나뉘지 않게 같은 이메일이면 기존 계정에 연결했어요. 그런데 메일 서버가 없던 동안에는 남의 이메일로 먼저 가입해 둘 수 있어서, 그 계정에 진짜 주인의 소셜 계정이 연결될 수 있었어요. 그래서 자동 연결을 없애고 어느 방법으로 로그인하면 되는지만 알려 줘요(CHANGELOG v1.9.0, `V24__separate_signup_methods.sql` 주석).
- **비밀번호 없는 소셜 회원은 소셜 계정으로 확인하고 탈퇴, 소셜 로그인으로 복구**: 모르는 비밀번호를 묻는 대신, 비밀번호가 있는지를 `password_set`으로 적어 두고 그에 맞게 화면과 서버 확인을 나눴어요(CHANGELOG v1.8.1, `V22__member_password_set.sql` 주석). v1.8.1은 "탈퇴합니다"를 입력하게 했는데, v1.9.1부터는 비밀번호 대신 가입한 제공자에 다시 로그인해 본인을 확인해요. 문구를 입력할 때 한글이 안 쳐지던 불편도 함께 없어졌어요(CHANGELOG v1.9.1). 제공자가 이미 로그인된 상태로 그냥 통과시키지 않게 `prompt`를 붙여요(`ReconfirmingAuthorizationRequestResolver` 주석).
- **비밀번호 찾기 번호를 응답에서 뺌**: v1.7.1 보안 수정이에요. 메일 서버가 없을 때 편하려고 번호를 응답에 실었는데, 비밀번호 찾기에서는 그게 곧 남의 비밀번호를 바꾸는 길이었어요(CHANGELOG v1.7.1, `AuthController.sendCode` 주석).
- **메일 두 가지 모드**: research.md §4. 발송 계정이 정해지지 않아도 개발을 계속할 수 있게 `log` 모드를 뒀고, 비동기 발송 실패는 사용자가 알 수 없으니 요청 때 연결부터 확인해요.
- **탈퇴를 바로 지우지 않고 30일 보관**: research.md §11은 "바로 지우기"로 적혀 있지만 지금 코드는 다르게 바뀌었어요(V4 `soft_withdraw`). `MyPageService.withdraw`와 `WithdrawalCleaner` 주석에 따르면 보관 기간 안에는 복구할 수 있게 하고, 지나면 블로그·글을 지우고 개인정보를 익명화해요. 회원 줄을 남기는 이유는 남의 글에 단 댓글과 신고 기록을 남기기 위해서예요.

## 공부 키워드

- Spring Security SecurityFilterChain: 주소별로 로그인 필요 여부를 정하는 필터 묶음
- Spring Session Redis indexed: 세션을 Redis에 두고 사용자 이름으로 찾는 방법
- Session Fixation (세션 고정 공격): 로그인 때 세션 번호를 바꾸는 이유
- CSRF Double Submit Cookie: 쿠키 값을 헤더로 다시 보내 위조를 막는 방식
- BCrypt salt cost: 느린 해시로 비밀번호를 지키는 원리
- Timing attack (타이밍 공격): 응답 시간 차이로 정보를 알아내는 공격과 더미 해시
- Redis TTL, SETNX: 저절로 사라지는 키와 "없을 때만 넣기"
- Transaction propagation REQUIRES_NEW: 예외가 나도 실패 횟수를 남기는 방법
- Soft delete: 지우지 않고 표시만 해 두는 삭제
- Spring @Scheduled cron: 정해진 시각에 저절로 도는 작업
- OAuth 2.0 Authorization Code Grant: code를 받아 토큰으로 바꾸는 로그인 절차
- OpenID Connect (sub, email_verified): 구글 로그인이 주는 사용자 정보
- Spring Security oauth2Login, ClientRegistrationRepository, AuthenticationSuccessHandler
- Account linking (계정 연결): 같은 이메일로 계정을 자동으로 붙일 때의 위험과, 붙이지 않고 가입 방법을 나누는 선택
- OAuth2AuthorizationRequestResolver, OIDC `prompt` (login, select_account): 인가 요청에 파라미터를 더해 다시 로그인하게 하기
- Cookie Secure, SameSite=Lax: HTTPS에서만 보내기, 다른 사이트에서 올 때 언제 보내나
