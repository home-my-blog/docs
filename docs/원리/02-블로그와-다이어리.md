# 02. 블로그와 다이어리: 동작 원리

> 기능 설명은 [기능/02-블로그와-다이어리.md](../기능/02-블로그와-다이어리.md)에 있어요. 2026-10-13 코드(develop) 기준이에요.

## 큰 흐름

### 가입할 때 블로그와 "일기장"이 생기는 흐름

1. 브라우저가 `POST /api/auth/signup`으로 가입을 보내요.
2. `SignupService.signup`(`@Transactional`)이 회원 줄을 `members` 표에 넣고, 바로 `BlogService.createFor(회원번호, 닉네임)`를 불러요.
3. `createFor`는 `TopicService.byCode("hobby")`로 기본 주제의 번호를 찾고, `blogs` 표에 "{닉네임}의 블로그"를 넣어요. 새 블로그 번호는 `GeneratedKeyHolder`(DB가 만든 번호를 돌려받는 도구)로 받아요.
4. 이어서 `CategoryService.createDefault(블로그번호)`가 `categories` 표에 기본 다이어리를 넣어요. 이름은 `myblog.blog.default-category-name`(일기장), 순서 1, `is_default = true`, 표지 색 0번이에요.
5. 이 셋(회원, 블로그, 일기장)이 한 트랜잭션(전부 되거나 전부 안 되거나 하는 묶음) 안에서 일어나요. 그래서 "회원은 있는데 블로그가 없는" 상태가 생기지 않아요.

### 블로그 화면을 여는 흐름

1. 브라우저가 `/blogs/{번호}`를 열면 React의 `BlogPage`가 `BlogShell`로 감싸져 그려져요.
2. `BlogShell`이 `GET /api/blogs/{blogId}`를 먼저 부르고, 성공하면 `GET /api/blogs/{blogId}/categories`(다이어리 목록)와 `GET /api/blogs/{blogId}/tags`(태그 모음)를 불러요.
3. 첫 화면(다이어리·태그 없음, 1쪽)이면 `BlogIntro`가 `GET /api/blogs/{blogId}/about`을, `PinnedPosts`가 `GET /api/blogs/{blogId}/pinned`를 불러요.
4. `BlogPostList`가 `GET /api/blogs/{blogId}/posts?categoryId=&tag=&sort=&page=`로 글 목록을 받아요.
5. 서버에서는 `BlogController`와 `PostController`가 받아서 `BlogService`, `CategoryService`, `SubscriptionService`, `PostQueryService`를 불러요. 모든 SQL은 `JdbcClient`로 PostgreSQL에 바로 보내요.
6. 볼 수 있는 글인지는 SQL 조건 `PostQueryService.VISIBLE_TO` 하나로 정해요. 그래서 글 수, 태그 수, 대표글이 보는 사람마다 달라져요.

## 자세히 보기

### 1인 1블로그는 DB가 지켜요

`blogs.owner_id`에 `UNIQUE` 제약(`uk_blogs_owner_id`, V1에서 만들고 V2에서 이름을 복수형으로 바꿈)이 있어요. 코드가 실수로 블로그를 두 번 만들려 해도 DB가 거절해요. `BlogService.blogIdOf(회원번호)`가 `Optional`(있을 수도 없을 수도 있는 값)로 하나만 돌려주는 것도 이 제약 덕분이에요. specs의 data-model.md에는 "나중에 1인 여러 블로그로 늘릴 때는 `owner_id`의 UNIQUE만 없앤다"고 적혀 있어요.

### 블로그 정보와 "주인인가?"

- `BlogService.find`는 `blogs`, `topics`, `members`를 묶어서 블로그 한 줄(`BlogRow`)을 읽어요. 조건에 `m.deleted_at IS NULL`이 있어서 탈퇴 신청한 회원의 블로그는 못 찾아요. `get`은 못 찾으면 `BLOG_NOT_FOUND`(404)를 던져요.
- `BlogService.summary`가 화면용 응답을 만들어요. 이름, 소개, 주제, 주인 닉네임·자기소개, `isOwner`, 그리고 보는 사람 기준의 글 수와 마지막 글 시각이에요. 글 수는 `count(*) ... WHERE p.blog_id = :blog AND VISIBLE_TO`로 세요.
- `BlogController.blog`가 여기에 `subscriberCount`(`SubscriptionService.subscriberCount`)와 `subscribedByMe`를 붙여요.
- `requireOwner(blogId, 회원번호)`는 주인이 아니면 `FORBIDDEN`이 아니라 `BLOG_NOT_FOUND`를 던져요. 남의 블로그가 있는지 없는지 알려 주지 않으려는 거예요(요구사항 NF-02).

### 블로그 설정 저장

`PATCH /api/blogs/{blogId}` → `BlogService.update`. 몸통은 `Update(name, description, about, topicCode)` 레코드예요.

1. `requireOwner`로 주인인지 확인해요.
2. 칸마다 "`null`이면 지금 값을 그대로 쓴다"는 규칙이에요. 화면(`SettingsPage`)은 바뀐 칸만 보내요.
3. 이름은 `Texts.trim`으로 앞뒤 공백을 지우고, 비었으면 `BLOG_NAME_REQUIRED`, 30자를 넘으면 `BLOG_NAME_TOO_LONG`이에요. 글자 수는 `Texts.length`가 코드 포인트(유니코드 글자 하나)로 세요.
4. 소개는 200자, 소개 글(about)은 `strip()` 뒤 5000자까지예요. 넘으면 `ApiException.field`로 어느 칸이 틀렸는지 알려 줘요.
5. 주제는 `TopicService.byCode`로 번호를 찾아요. 없는 코드면 `TOPIC_NOT_FOUND`(404)예요.
6. 마지막에 `UPDATE blogs SET name, description, about, topic_id, updated_at`을 한 번에 해요.

입력 검사는 Bean Validation(`@Valid`)을 쓰지 않고 이렇게 서비스 코드에서 직접 해요.

### 블로그 소개(about)

`GET /api/blogs/{blogId}/about`은 `ownerNickname`, `ownerBio`, `about` 세 가지만 돌려줘요. 화면의 `BlogIntro`(`frontend/src/pages/BlogAboutPage.tsx`)가 이걸 그려요. `useLayoutEffect`에서 본문의 `scrollHeight`가 `clientHeight`보다 크면(4줄 높이를 넘으면) `더보기` 버튼을 보여 줘요. 4줄 높이는 CSS `.intro__body { max-height: calc(1.8em * 4) }`가 정해요. `/blogs/:blogId/about` 경로는 `BlogAboutPage`가 `<Navigate replace>`로 첫 화면으로 보내요.

### 블로그 글 목록과 정렬

`PostQueryService.blogPosts`가 WHERE 조건을 조립해요.

- 기본: `p.blog_id = :blog AND VISIBLE_TO`
- 다이어리를 골랐으면 `AND p.category_id = :category`
- 태그를 골랐으면 `post_tags`와 `tags`를 묶어 `g.name_key = :tag`인 글만. 태그는 `PostController`에서 앞의 `#`을 떼고 소문자 키로 바꿔요.
- 정렬: `popular`는 `POPULARITY`(조회 + 좋아요×5 + 댓글 단 사람×3 + 책갈피×4, 글쓴이 본인 것 빼고) 내림차순, `oldest`는 `created_at` 오름차순, 그 밖에는 최신순이에요.

화면은 고른 값들을 `useSearchParams`로 주소에 넣어요. 다른 값을 바꾸면 `page`는 지워서 1쪽으로 돌아가요.

### 태그 모음

`PostQueryService.blogTags`가 `post_tags`, `tags`, `posts`를 묶어 `GROUP BY g.id`로 세고 `ORDER BY cnt DESC, g.name LIMIT :limit`로 잘라요. limit은 `myblog.blog.blog-tags`(12)예요. 여기도 `VISIBLE_TO` 조건이 붙어서 비공개 글에만 붙은 태그는 방문자에게 안 보여요.

### 볼 수 있는 글: VISIBLE_TO

`PostQueryService`의 문자열 상수들이 공개 규칙의 전부예요.

- `OPEN_CATEGORY`: 글의 다이어리가 공개가 아닌 다이어리 목록에 없을 것
- `SUBSCRIBER_VISIBLE`: 글과 다이어리 모두 비공개가 아니고, 보는 사람이 그 블로그(`subscriptions`)나 그 다이어리(`diary_subscriptions`)를 구독 중일 것
- `VISIBLE_TO`: (공개 글이면서 `OPEN_CATEGORY`) 또는 내가 쓴 글 또는 `SUBSCRIBER_VISIBLE`, 그리고 글쓴이가 탈퇴 신청하지 않았을 것

로그인 안 한 사람은 `:viewer`에 `-1`을 넣어요. 어떤 회원 번호와도 맞지 않으니 공개 글만 남아요.

### 다이어리 목록

`GET /api/blogs/{blogId}/categories` → `CategoryService.list(blogId, owner, viewer)`.

- 조건: `:owner OR c.visibility = 'PUBLIC' OR (c.visibility = 'SUBSCRIBERS' AND SUBSCRIBED_TO_DIARY)`. 주인은 다 보고, 방문자는 공개 다이어리만, 구독자는 구독자만 다이어리까지 봐요.
- 다이어리마다 같은 SQL 안의 하위 쿼리(subquery, 쿼리 안의 작은 쿼리)로 글 수(`VISIBLE_TO` 적용), 구독자 수(`SubscriptionService.DIARY_SUBSCRIBERS`, 탈퇴 신청자 제외), 내가 구독했는지(`EXISTS`)를 함께 구해요.
- 순서는 `ORDER BY c.sort_order, c.id`예요.

블로그 머리의 "글 N개"는 화면이 이 목록의 `postCount`를 더한 값이에요.

### 다이어리 만들기

`POST /api/blogs/{blogId}/categories` → `blogs.requireOwner` → `CategoryService.add`.

1. `validName`이 공백을 지우고 1~20자인지 봐요.
2. `SELECT coalesce(max(sort_order), 0) + 1, count(*)`로 다음 순서 번호와 지금 다이어리 수를 한 번에 구해요.
3. 순서는 맨 끝(최댓값 + 1), 표지 색은 `count % color-count`(8)예요. 그래서 다이어리를 만들 때마다 색이 0, 1, 2… 차례로 돌아가요.
4. `name_key`에는 `name.toLowerCase(Locale.ROOT)`를 넣어요. `UNIQUE (blog_id, name_key)` 제약 때문에 같은 블로그에서 "Diary"와 "diary"는 같이 못 있어요.
5. 제약에 걸리면 `DataIntegrityViolationException`을 잡아 `CATEGORY_NAME_TAKEN`(409)으로 바꿔요. 먼저 SELECT로 확인하지 않고 DB 제약에 맡기니까, 두 요청이 동시에 와도 하나만 들어가요.

### 다이어리 설정 바꾸기

`PATCH /api/categories/{id}` → `BlogController.ownBlog(me)`로 내 블로그 번호를 구하고 → `CategoryService.update`.

- `requireOwned`가 그 다이어리가 내 블로그 것인지 봐요. 아니면 `CATEGORY_NOT_FOUND`(404)예요.
- `Update(name, description, colorIndex, visibility)`에서 `null`이 아닌 칸만 하나씩 `UPDATE` 해요.
- 이름은 `rename`(검사 + `name_key` 갱신 + 중복이면 409), 소개는 100자, 표지 색은 0 이상 `color-count` 미만, 공개 범위는 `PUBLIC`, `SUBSCRIBERS`, `PRIVATE` 중 하나예요.
- `PRIVATE`으로 바꾸면 같은 트랜잭션에서 `DELETE FROM diary_subscriptions WHERE category_id = ?`로 그 다이어리 구독을 지워요.
- 메서드 전체가 `@Transactional`이라 중간 칸에서 검사가 실패하면 앞에서 바꾼 이름도 되돌아가요.

화면의 `DiarySettingsModal`은 이름이 바뀐 경우에만 `name`을 보내고, 소개·색·공개 범위는 늘 보내요.

### 다이어리 순서 바꾸기

`POST /api/categories/{id}/move` 몸통 `{direction: "up" | "down"}` → `CategoryService.move`.

1. 위로면 `sort_order < 내 순서` 중 가장 큰 것, 아래로면 `sort_order > 내 순서` 중 가장 작은 것을 이웃으로 찾아요.
2. 이웃이 있으면 두 줄의 `sort_order` 값을 서로 바꿔요(UPDATE 두 번).
3. 이웃이 없으면(맨 위에서 위로) 아무 일도 안 해요.

번호를 1, 2, 3으로 다시 매기지 않고 두 칸만 맞바꾸니 바뀌는 줄이 늘 두 개뿐이에요.

### 다이어리 지우기

`DELETE /api/categories/{id}` → `CategoryService.delete`.

1. `is_default`면 `DEFAULT_CATEGORY`(409)로 거절해요.
2. `SELECT count(*) FROM posts WHERE category_id = ?`가 0보다 크면 `CATEGORY_HAS_POSTS`(409)로 거절하고, `details.postCount`에 글 수를 담아요. 이 수는 비공개 글까지 센 값이에요.
3. 통과하면 `DELETE FROM categories`. `diary_subscriptions`는 `ON DELETE CASCADE`라 같이 지워져요.

DB에도 안전장치가 있어요. `posts.category_id`가 `ON DELETE RESTRICT`라서, 서비스 검사를 빼먹어도 글이 든 다이어리는 DB가 지우지 않아요. 기본 다이어리는 부분 고유 인덱스 `UNIQUE (blog_id) WHERE is_default`로 블로그마다 하나만 있을 수 있어요.

글을 옮기는 일은 다른 API가 해요. `POST /api/blogs/{blogId}/posts/move`(`PostCommandService.movePosts`)가 내 글인지 확인하고 `UPDATE posts SET category_id = :cat WHERE id IN (:ids)` 한 번으로 옮겨요. `content_updated_at`은 건드리지 않아요.

### 기본 다이어리 이름 "일기장"과 V20

새 블로그는 `application.yml`의 `default-category-name: 일기장`으로 만들어요. 예전 블로그의 "미분류"는 V20 마이그레이션이 `is_default`이고 `name_key = '미분류'`인 줄만 "일기장"으로 바꿨어요. 같은 블로그에 이미 "일기장"이 있으면 `NOT EXISTS` 조건으로 건너뛰어요. 그대로 바꾸면 `UNIQUE (blog_id, name_key)`에 걸려 마이그레이션 전체가 실패하기 때문이에요.

### 대표글 고정

- V7이 `posts.pinned_at`(timestamptz, NULL이면 고정 안 함) 칸과 부분 인덱스 `idx_posts_blog_pinned (blog_id, pinned_at) WHERE pinned_at IS NOT NULL`을 만들었어요.
- `PUT /api/posts/{id}/pin` → `PostCommandService.togglePin`. 먼저 `requireAuthor`로 글쓴이인지 봐요.
- 그다음 `SELECT id FROM blogs WHERE id = ? FOR UPDATE`로 **블로그 줄을 잠가요**. 두 탭에서 동시에 4번째를 누르면, 둘 다 "지금 2개"를 읽고 둘 다 고정하는 일이 생길 수 있어요. 잠그면 두 번째 요청은 첫 번째가 끝날 때까지 기다렸다가 새 개수를 읽어요.
- 이미 고정이면 `pinned_at = NULL`로 풀고, 아니면 개수가 `pin-limit`(3) 이상일 때 `PIN_LIMIT`(409)로 거절, 아니면 `pinned_at = 지금`으로 고정해요.
- `GET /api/blogs/{blogId}/pinned` → `PostQueryService.pinned`가 `pinned_at IS NOT NULL AND VISIBLE_TO`를 `ORDER BY p.pinned_at, p.id`로 읽어요. 고정 시각 순서가 곧 보여 주는 순서예요.
- 글 화면 응답(`GET /api/posts/{id}`)의 `pinned` 값으로 버튼 글자를 정해요.

### 분야(topics)

- `topics` 표: `id`, `code`, `name`, `description`, `sort_order`. `TopicService.list`가 `sort_order` 순으로 돌려주고 `GET /api/topics`가 그대로 내보내요.
- 블로그에는 `blogs.topic_id`, 글에는 V8부터 `posts.topic_id`(NOT NULL), 임시저장에는 `drafts.topic_id`(비워도 됨)가 있어요.
- 글을 쓸 때 `topicCode`를 비우면 `PostCommandService`가 `SELECT topic_id FROM blogs`로 블로그 주제를 넣어요.
- 마이그레이션 이력
  - V1: `topic` 표와 시드 5개(travel, food, hobby, exercise, dev)
  - V8: `posts.topic_id`를 더하고 `UPDATE posts ... FROM blogs`로 블로그 주제를 채운 뒤 NOT NULL로 바꿈. `drafts.topic_id`도 더함
  - V9: 14개를 더해 19개, `sort_order`를 다시 매김
  - V10: 9개를 빼고 10개. 빠진 분야의 글·블로그는 `etc`로, 임시저장은 NULL로
  - V11: `game`, `culture`, `money`를 넣고(`ON CONFLICT (code) DO NOTHING`), `dev`→`study`, `book`·`movie`→`culture`, `etc`→`daily`로 글과 블로그를 옮긴 뒤 네 개를 지움. 최종 9개와 순서(daily 1 … money 9)
- 분야를 지울 때는 먼저 그 분야를 쓰는 `posts`, `blogs`를 옮기고 `drafts`를 비운 뒤에 `DELETE`해요. `posts.topic_id`, `blogs.topic_id`가 외래 키라서 순서를 바꾸면 지우기가 실패해요.

### 구독자 수

- 블로그: `SubscriptionService.subscriberCount`가 `subscriptions`와 `members`를 묶어 `deleted_at IS NULL`인 사람만 세요.
- 다이어리: `DIARY_SUBSCRIBERS` SQL 조각이 `diary_subscriptions`를 같은 방식으로 세요. 이 조각은 `CategoryService.list` 같은 다른 쿼리에 끼워 써요.
- 화면 글자는 `messages.ts`의 `SUBSCRIBE.blogCount`("블로그 구독자 N명")와 `SUBSCRIBE.count`("구독자 N명")예요.

## 데이터는 어디에

| 무엇 | 어디에 | 언제 사라지나 |
| --- | --- | --- |
| 블로그 이름·소개·소개 글·주제 | PostgreSQL `blogs` 표 | 탈퇴 보관 기간(30일)이 지나 정리될 때 |
| 다이어리 이름·소개·표지 색·공개 범위·순서·기본 여부 | PostgreSQL `categories` 표 | 주인이 지울 때, 블로그가 지워질 때(`ON DELETE CASCADE`) |
| 대표글 고정 | PostgreSQL `posts.pinned_at` | 고정을 풀거나 글을 지울 때 |
| 분야 목록 | PostgreSQL `topics` 표 | 마이그레이션으로 지울 때만 |
| 블로그 구독 / 다이어리 구독 | PostgreSQL `subscriptions` / `diary_subscriptions` | 구독 취소, 다이어리 비공개 전환·삭제, 회원 삭제 |
| 표지 색 8가지의 실제 색 값 | 프론트엔드 코드 `lib/format.ts` (`CATEGORY_COLORS`) | 코드를 바꿀 때 |
| 블로그 화면 응답 캐시 | 브라우저 메모리(React Query) | 새로고침하거나 저장 후 `invalidateQueries`할 때 |

## 왜 이렇게 만들었나

- **1인 1블로그**: 요구사항 CF-03-1이 블로그를 한 사람에 하나로 정했어요. 그래도 표를 `members`와 `blogs`로 나눠 두고 `owner_id`의 UNIQUE만 걸어서, 나중에 여러 개로 늘릴 때 제약 하나만 빼면 되게 했어요(spec.md, data-model.md).
- **가입과 블로그 만들기를 한 트랜잭션에**: 가입은 됐는데 블로그가 없으면 글쓰기, 관리 화면이 다 깨져요. 그래서 `SignupService.signup` 안에서 같이 만들어요.
- **표와 칸 이름은 category 그대로**: 화면 이름을 "분류"에서 "다이어리"로 바꿀 때 V6 주석에 "표와 칸 이름은 그대로 둔다"고 적었어요. 이미 쓰던 코드와 DB를 크게 고치지 않으려는 선택이에요.
- **다이어리를 지울 때 글을 옮기지 않음**: 요구사항 CF-08-6, 8이 "글이 있는 분류와 기본 분류는 지울 수 없다"로 정했어요. 지우는 순간 글이 엉뚱한 곳으로 가는 것보다, 주인이 직접 옮기게 하는 쪽이 안전해요.
- **이름 중복은 DB 제약으로**: 먼저 SELECT로 확인하면 두 요청이 동시에 올 때 둘 다 통과할 수 있어요. `UNIQUE (blog_id, name_key)`에 맡기고 예외를 409로 바꾸면 그런 틈이 없어요.
- **주인 아님 = 없음**: 남의 블로그를 고치는 요청에 403 대신 404를 줘서, 무엇이 있는지 알려 주지 않아요(NF-02).
- **블로그 기본 주제 취미**: research.md 12절에서 가입 시 기본 주제를 `hobby`로 정하고 블로그 설정에서 바꾸게 했어요. spec.md에는 원본 요구사항에 주제 항목이 없어 추가했다고 "확인 필요"로 적혀 있어요.
- **글마다 분야(V8)**: 한 블로그에 여행 글과 음식 글이 섞이는데, 블로그 주제 하나로 나누면 분야 탭이 맞지 않았어요. V8 주석에 "지금까지는 블로그의 주제를 글이 따라갔다"고 적고 글마다 고르게 바꿨어요.
- **분야 9개(V11)**: CHANGELOG v1.4.0에 "v1.3.0에서 19개로 늘렸던 것을 줄였다"고 적혀 있어요. 없앤 분야의 글은 지우지 않고 가까운 분야로 옮겼어요.

## 공부 키워드

- `UNIQUE 제약과 부분 고유 인덱스(partial unique index)`: "블로그마다 기본 다이어리 하나" 같은 규칙을 DB에 맡기는 법
- `@Transactional 롤백`: 런타임 예외가 나면 앞의 변경까지 되돌아가는 원리
- `SELECT ... FOR UPDATE`: 줄을 잠가 동시에 들어온 요청을 줄 세우는 법
- `DataIntegrityViolationException`: DB 제약 위반을 Spring이 바꿔 주는 예외
- `ON DELETE CASCADE / RESTRICT`: 부모 줄을 지울 때 자식 줄을 어떻게 할지
- `상관 하위 쿼리(correlated subquery)`: 다이어리마다 글 수·구독자 수를 한 쿼리에서 세는 법
- `Flyway 마이그레이션`: V1, V8, V11처럼 번호 순서로 DB 구조와 데이터를 바꾸는 도구
- `Spring JdbcClient`: JPA 없이 SQL을 직접 쓰는 Spring 6의 도구
- `React Query invalidateQueries`: 저장한 뒤 화면 데이터를 다시 받아오게 하는 법
- `useSearchParams`: 고른 다이어리·태그·정렬을 주소에 담는 React Router 훅
