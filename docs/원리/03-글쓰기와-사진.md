# 03. 글쓰기와 사진: 동작 원리

> 기능 설명은 [기능/03-글쓰기와-사진.md](../기능/03-글쓰기와-사진.md)에 있어요. 2026-10-13 코드(develop) 기준이에요.

## 큰 흐름

### 흐름 1. 사진을 넣고 글을 올리기

1. 브라우저(`PostEditorPage`의 `onFile`)가 파일 종류와 크기를 먼저 확인해요. 그다음 `FormData`(파일을 담아 보내는 상자, 정식 이름 `multipart/form-data`)에 담아 `POST /api/images`로 보내요(`endpoints.ts`의 `uploadImage`). 로그인 쿠키가 함께 가요.
2. `ImageController.upload`가 받아서 `ImageService.upload`에 넘겨요.
3. `ImageService.upload`가 크기(1바이트~5MB)와 매직 넘버를 검사하고, `posts/2026/10/{UUID}.png` 같은 새 이름(키)을 지어요.
4. `ImageStorage.put`이 파일을 저장해요. 기본은 `DiskImageStorage`라서 서버 디스크(`/data/images`)에 써요.
5. PostgreSQL `post_images` 표에 한 줄을 넣어요. 이때 `post_id`는 비어 있어요. 아직 어느 글에도 안 붙은 사진이에요.
6. 응답 `201 { id, url }`이 돌아오면 브라우저가 본문 커서 자리에 `![](/api/images/posts/...)`를 넣어요. 편집 칸에는 `[📷 사진 N]`으로 보여요.
7. "올리기"를 누르면 `POST /api/blogs/{blogId}/posts`로 제목, 본문, 다이어리(`categoryId`), 분야(`topicCode`), 공개 범위, 태그, 사진 번호들(`imageIds`), 대표 사진(`coverImageId`), 임시저장 번호(`draftId`)를 보내요.
8. `PostCommandService.create`가 트랜잭션(여러 DB 작업을 한 덩어리로 묶어, 하나라도 실패하면 모두 되돌리는 것) 하나 안에서 이 순서로 일해요.
   1. `blogs.requireOwner`: 내 블로그인지 확인
   2. `validate`: 제목·본문·다이어리·분야·공개 범위·태그 검사
   3. `cover`: 대표 사진이 내가 올린 사진인지 확인
   4. `posts`에 INSERT (`cover_image_id` 포함)
   5. `tags.replace`: 태그 연결
   6. `images.attach`: `post_images.post_id`를 이 글 번호로 채움
   7. `drafts.deleteQuietly`: 이어 쓰던 임시저장 글 지움
   8. `ink.rewardPost`: 공개 글이면 잉크 적립(06 문서)
9. 응답 `201 { id }`를 받으면 브라우저가 `/posts/{id}`로 이동해요.

### 흐름 2. 임시저장과 이어 쓰기

1. 새 글 화면이 열리면 `GET /api/me/drafts`로 목록을, `GET /api/config`의 `draftAutosaveSeconds`(60)로 자동 저장 간격을 받아요.
2. `setInterval`이 60초마다 `saveDraft(true)`를 불러요. 지금 내용(`snapshot`)이 마지막 저장 내용(`savedSnapshot`)과 같으면 아무것도 안 보내요.
3. 처음이면 `POST /api/me/drafts`, 그 뒤로는 `PUT /api/me/drafts/{id}`로 보내요.
4. `DraftService.save`가 검사하고 `drafts` 표에 INSERT 또는 UPDATE 해요. 응답은 `{ id, updatedAt }`이에요.
5. 브라우저는 `history.replaceState`로 주소만 `/write?draft={id}`로 바꿔요. 화면을 다시 그리지 않아서 쓰던 흐름이 끊기지 않아요.
6. 나중에 `/write?draft={id}`로 오면 `CreateLoader`가 `GET /api/me/drafts/{id}`로 내용을 받아 편집 칸을 채워요.
7. 그 상태로 올리면 요청에 `draftId`가 들어가고, 흐름 1의 8-7단계에서 지워져요.

## 자세히 보기

### 글 검사: `PostCommandService.validate`

입력 검사는 Bean Validation(`@Valid`)이 아니라 이 메서드에서 직접 해요. 틀리면 `ApiException.field("칸 이름", 문구)`를 던져서 화면이 그 칸 아래에 문구를 보여 줘요.

- 제목은 앞뒤 공백을 지운 뒤(`Texts.trim`) 비었는지, `title-max`(100)를 넘는지 봐요.
- 본문은 공백뿐이면 거절, `body-max`(10,000)를 넘어도 거절해요. 본문은 앞뒤 공백을 지우지 않아요.
- 글자 수는 `Texts.length`가 코드 포인트로 세요. 그래서 이모지 하나도 1자예요. 화면은 자바스크립트 `length`로 세기 때문에 이모지가 많으면 화면과 서버 숫자가 조금 다를 수 있어요.
- 다이어리는 `categories.get`으로 찾고, 그 다이어리의 `blogId`가 이 블로그가 아니면 거절해요.
- 분야(`topicCode`)가 비면 `blogs.topic_id`를 그대로 써요. 있으면 `topics.idOf`로 찾고, 없는 코드면 거절해요.
- 공개 범위가 `null`이면 `PUBLIC`, 세 값(PUBLIC, SUBSCRIBERS, PRIVATE) 밖이면 거절해요. DB에도 같은 CHECK 제약이 있어요(V18).
- 태그는 `TagService.normalize`가 정리해요.

### 태그 정리: `TagService`

- `normalize`: 앞의 `#`을 지우고, 빈 것은 건너뛰고, 15자를 넘거나 공백·쉼표가 있으면 거절해요. 소문자로 바꾼 값(`name_key`)으로 중복을 지우는데, 처음 쓴 철자를 남겨요. 그래도 5개를 넘으면 `TOO_MANY_TAGS`예요.
- `replace`: 이 글의 `post_tags`를 모두 지우고 다시 넣어요. `tags` 표는 모든 글이 같이 쓰는 표라서, 없으면 `ON CONFLICT (name_key) DO NOTHING`으로 만들고 있으면 그대로 써요.
- 화면(`validation.ts`의 `normalizeTag`, `isValidTag`)도 같은 규칙으로 먼저 걸러요. 서버 검사는 마지막 방어선이에요.

### 마크다운을 안전하게 그리기: `MarkdownView`

본문은 DB에 마크다운 원문 그대로 들어 있어요. HTML로 바꾸는 일은 화면에서만 해요.

- `react-markdown`(마크다운을 React 화면 조각으로 바꾸는 라이브러리)에 `remark-gfm` 플러그인을 붙였어요. GFM(GitHub식 마크다운)이라서 표, 취소선, 체크 목록, 주소 자동 링크가 돼요.
- `skipHtml`: 본문에 `<script>`, `<img onerror=...>` 같은 원시 HTML이 있어도 그리지 않고 버려요. XSS(남의 화면에서 내 스크립트를 돌리는 공격)를 막는 첫 번째 장치예요.
- `urlTransform={safeUrlTransform}` (`lib/markdown.ts`): 링크와 사진 주소를 허용 목록으로 걸러요.
  - 사진(`img`의 `src`): `/api/images/`로 시작하거나 `http(s)://`만 통과
  - 링크: `http(s):`, `mailto:`, 같은 사이트 경로(`/...`, 단 `//`로 시작하면 안 됨), `#...`만 통과
  - 나머지(`javascript:`, `data:` 등)는 빈 문자열이 돼서 아무 데도 안 가요.
- `components`로 `a`와 `img`를 바꿔 그려요. 바깥 링크(`http(s)://`)에는 `target="_blank" rel="noopener noreferrer nofollow"`를 붙여서 새 탭이 내 창을 건드리지 못하게 해요. 사진에는 `loading="lazy"`를 붙여 화면에 가까워질 때 받아요.
- 글쓰기 화면의 "미리보기" 탭도 같은 `MarkdownView`를 써서, 올린 뒤와 똑같이 보여요.

### 사진 이름표: `lib/photoTokens.ts`

긴 주소가 편집 칸을 어지럽히지 않게, 화면에서만 바꿔 보여 줘요.

- `toDisplay(body, photos)`: 본문의 `![...](주소)` 중 이번에 올린 사진(`images` 배열에 있는 주소)을 `[📷 사진 N]`으로 바꿔요. N은 배열에서의 순서 + 1이에요. 모르는 주소는 그대로 둬요.
- `fromDisplay(text, photos)`: 반대로 `[📷 사진 N]`을 `![](주소)`로 되돌려요. 없는 번호면 글자 그대로 둬요.
- 편집 칸의 `value`는 `toDisplay(body)`이고, 입력이 바뀌면 `fromDisplay`를 거쳐 `body` 상태에 저장해요. 그래서 상태와 서버로 가는 본문은 늘 진짜 마크다운이에요.
- `images` 배열은 이번 화면에서 올린 모든 사진이에요. `usedImages`는 그중 `body`에 주소가 들어 있는 것만 고른 거예요. 사진 줄, 10장 검사, 서버로 보내는 `imageIds`는 모두 `usedImages`를 써요.
- 대표 사진은 `usedImages` 안에 있을 때만 보내요. 본문에서 빼면 대표 사진도 자동으로 빠져요.

### 사진 받기와 검사: `ImageService.upload`

1. `file.getBytes()`로 전부 메모리에 읽어요. 그 전에 Spring이 `multipart.max-file-size`(6MB)를 넘는 요청을 먼저 막아요.
2. 0바이트이거나 `max-bytes`(5,242,880)를 넘으면 `INVALID_IMAGE`(400)예요.
3. `detect`가 파일 앞 바이트(매직 넘버, 파일 종류마다 정해진 첫 몇 바이트)를 봐요.
   - JPEG: `FF D8 FF`
   - PNG: `89 50 4E 47` (`\x89PNG`)
   - GIF: `47 49 46 38` (`GIF8`)
   - WebP: 0~3번째가 `RIFF`, 8~11번째가 `WEBP`
   - 이 넷이 아니면 `INVALID_IMAGE`예요. 브라우저가 보낸 Content-Type이나 파일 이름은 보지 않아요.
4. 키를 `posts/{yyyy}/{MM}/{UUID}.{확장자}`로 지어요. 연·월은 `KoreanClock`(한국 시간)으로 정해요. UUID(겹칠 일이 사실상 없는 무작위 128비트 번호)라서 같은 이름으로 덮어쓸 걱정이 없고, 원래 파일 이름에 있던 개인정보도 남지 않아요.
5. `storage.put`으로 파일을 먼저 저장하고, 그다음 `post_images`에 `uploader_id`, `storage_key`, `content_type`, `size_bytes`, `created_at`을 넣어요. 새 줄의 `id`가 사진 번호예요.
6. `Uploaded(id, "/api/images/" + key)`를 돌려줘요.

DB에도 안전장치가 있어요(V1). `storage_key`는 UNIQUE, `size_bytes`는 1~5,242,880, `content_type`은 네 종류만 받는 CHECK 제약이에요.

### 저장소 갈아끼우기: `ImageStorage`

`ImageStorage`는 `put(key, bytes, contentType)`, `get(key)`, `delete(key)` 세 메서드만 있는 인터페이스예요. 구현이 둘 있고, `@ConditionalOnProperty`가 `myblog.image.storage` 값으로 하나만 빈(Spring이 만들어 관리하는 객체)으로 만들어요.

- **`DiskImageStorage`** (`disk`, 값이 없을 때도 이것): `myblog.image.disk-path` 아래에 키 그대로 폴더를 만들어 써요. `resolve`가 경로를 `normalize`한 뒤 루트 폴더 밖이면 거절해요. 키에 `../`를 넣어 다른 파일을 읽는 공격(경로 조작)을 막아요.
- **`S3ImageStorage`** (`s3`): AWS SDK v2로 MinIO 같은 S3 호환 저장소에 `forcePathStyle(true)`로 붙어요. 주소·버킷·계정은 `myblog.image.s3.*`(`MINIO_ENDPOINT`, `MINIO_BUCKET`, `MINIO_USER`, `MINIO_PASSWORD`)에서 읽어요. 로컬에서 고를 수 있는 선택지이고, 운영은 디스크를 써요.

운영에서는 `Dockerfile`이 `MYBLOG_IMAGE_DISK_PATH=/data/images`로 정하고, `deploy.sh`가 서버의 `~/myblog-data/images`를 컨테이너 `/data/images`에 붙여요. 그래서 블루-그린으로 새 서버를 띄워도 사진이 그대로 있어요.

`ImageService`는 어느 구현인지 몰라요. 인터페이스만 보고 일하니까 저장소를 바꿔도 다른 코드는 그대로예요.

### 사진 내려 주기: `ImageController.get`

- `GET /api/images/**`의 나머지 경로를 키로 써요. `SecurityConfig`가 `GET /api/**`를 모두 허용해서 로그인 없이도 받을 수 있어요.
- `ImageService.read`가 `post_images`에서 `content_type`을 찾고, 저장소에서 바이트를 꺼내요. 어느 쪽이든 없으면 `IMAGE_NOT_FOUND`(404)예요. DB에 기록이 없는 키는 디스크에 파일이 있어도 내주지 않아요.
- 응답 헤더:
  - `Content-Type`: DB에 적어 둔 종류
  - `Cache-Control: max-age=2592000, public` (30일). 키가 UUID라서 내용이 바뀔 일이 없으니 오래 캐시해도 돼요.
  - `X-Content-Type-Options: nosniff`: 브라우저가 내용을 보고 종류를 멋대로 추측하지 않게 해요.
- 글의 공개 범위는 보지 않아요. 사진 주소를 아는 사람은 누구나 볼 수 있어요.

### 글과 연결하기: `ImageService.attach`

글을 만들 때와 고칠 때 모두 불려요.

1. 보낸 `imageIds`에 `coverImageId`를 더하고(`PostCommandService.imageIds`) 중복을 지워요.
2. 10장(`max-per-post`)을 넘으면 `TOO_MANY_IMAGES`(400). 트랜잭션이라 글 저장도 함께 취소돼요.
3. `UPDATE post_images SET post_id = NULL WHERE post_id = 글번호`로 기존 연결을 모두 풀어요.
4. `UPDATE post_images SET post_id = 글번호 WHERE id IN (...) AND uploader_id = 나`로 다시 붙여요. 남의 사진 번호를 끼워 넣어도 `uploader_id` 조건 때문에 붙지 않아요.

대표 사진은 `PostCommandService.cover`가 `images.ownedBy`로 내 사진인지 보고, 아니면 `coverImageId` 칸 오류를 내요. 통과하면 `posts.cover_image_id`에 사진 번호를 적어요. 이 외래 키는 `ON DELETE SET NULL`이라 사진 줄이 지워지면 대표 사진 칸만 비어요.

### 목록 미리보기: `PostQueryService.summary`와 `ExcerptMaker`

- 목록용 글 한 개를 만들 때 `coverImageUrl`을 이렇게 정해요. `cover_image_id`의 `storage_key`가 있으면 그 주소, 없으면 `ExcerptMaker.firstImage(body)`.
- `firstImage`는 정규식으로 본문의 첫 `![...](주소)`를 찾되, 주소가 `/api/images/...` 또는 `http(s)://...`인 것만 골라요.
- 글 화면(`PostController.detail`)은 `cover_key`만 써요. 그래서 대표 사진을 안 고르면 글 위쪽 큰 사진은 없어요.
- 본문 앞부분(`excerpt`)은 `ExcerptMaker.plain`이 코드 울타리, 사진, 링크, 제목 기호, 인용, 목록 기호, 굵게·기울임 기호, 가로줄을 걷어 내고 공백을 하나로 줄인 뒤, `Texts.cut`으로 100자 + "…"로 잘라요. 임시저장 목록의 미리보기도 같은 함수를 써요.
- 화면 쪽 `components/Cards.tsx`:
  - `Thumb`: `src`가 있으면 `<img loading="lazy">`, 없으면 `thumb--paper` 칸을 그려요. CSS가 `repeating-linear-gradient`로 14px마다 줄을 그어 회색 줄노트처럼 보여요. 홈의 인기 글(`pop-thumb`)·추천 글(`rec-thumb`) 카드가 써요.
  - `PostRow`: `coverImageUrl`이 있을 때만 사진 칸을 그려요. 그래서 분야별 글, 검색, 태그 글 같은 가로 목록은 사진이 없으면 칸 자체가 없어요.

### 고아 사진 정리: `ImageService.cleanOrphans`

고아 사진은 올렸지만 어디에도 안 쓰이는 사진이에요. `@Scheduled(fixedDelay = 3_600_000, initialDelay = 60_000)`이라 서버가 켜지고 1분 뒤 처음 돌고, 그 뒤로는 앞 작업이 끝나고 1시간 뒤에 다시 돌아요.

지우는 조건은 넷을 모두 만족할 때예요.

1. `post_id IS NULL` (어느 글에도 안 붙음)
2. `created_at < 지금 - orphan-ttl(24h)` (올린 지 24시간 지남)
3. 어떤 글의 `cover_image_id`도 아님
4. 어떤 임시저장 글의 `image_ids` 배열에도 없음 (`= ANY (d.image_ids)`)

찾은 줄마다 `post_images`에서 지우고 `deleteFilesAfterCommit`으로 파일을 지워요. 이 메서드는 트랜잭션 밖이라 파일도 바로 지워요. 기준이 "연결이 풀린 때"가 아니라 "올린 때"라서, 오래전에 올린 사진을 본문에서 빼고 저장하면 다음 정리 때 바로 지워질 수 있어요.

### 글 수정: `PostCommandService.update`

- `queries.requireAuthor`가 볼 수 있는 글인지, 글쓴이가 나인지 봐요. 아니면 `POST_NOT_FOUND`(404)로 답해서 글이 있는지조차 알려 주지 않아요.
- 고칠 화면은 `GET /api/posts/{id}/edit`(로그인 필수)로 원본 마크다운, 태그, 연결된 사진(`post_images.post_id = 글`을 `id` 순서로), 대표 사진 번호를 받아요.
- 제목·본문·다이어리·분야·공개 범위를 이전 값과 비교해서 하나라도 다르면 `content_updated_at`을 지금으로, 아니면 이전 값 그대로 UPDATE 해요. 태그, 사진, 대표 사진은 비교에 넣지 않아요.
- 그다음 `tags.replace`와 `images.attach`를 다시 해요. 본문에서 빠진 사진은 연결만 풀리고 정리 작업이 지워요.

### 글 삭제: `PostCommandService.delete`

1. `requireAuthor`로 확인해요.
2. `images.keysOfPost`로 이 글 사진들의 키를 **먼저** 모아 둬요. 글을 지우면 사진 줄도 사라지니까요.
3. `DELETE FROM posts WHERE id = ?` 한 줄만 실행해요. 나머지는 외래 키의 `ON DELETE CASCADE`가 지워요: `post_images`, `post_tags`, 댓글, 좋아요, 책갈피(`bookmarks`).
4. `deleteFilesAfterCommit(keys)`가 `TransactionSynchronization.afterCommit`에 파일 삭제를 걸어 둬요. DB 삭제가 확정된 **뒤에만** 파일을 지워요. 파일 삭제가 실패하면 경고 로그만 남겨요.
5. 서버는 `{ blogId }`를 돌려줘요. 글 화면(`PostDetailPage`)은 들고 있던 글의 블로그 번호로 `/blogs/{blogId}`에 돌아가요.

### 한꺼번에 옮기기·지우기

- `POST /api/blogs/{blogId}/posts/move`, `POST /api/blogs/{blogId}/posts/delete`에 `{ postIds, categoryId }`를 보내요. 화면은 `BlogPage`의 다이어리 편집 영역이에요.
- `requireOwnPosts`가 블로그 주인인지 보고, `blog_id = 이 블로그 AND author_id = 나 AND id IN (...)`인 글 수를 세요. 보낸 개수와 다르면 하나라도 남의 글이라는 뜻이라 전부 `POST_NOT_FOUND`로 거절해요. 빈 목록이면 `postIds` 칸 오류예요.
- `movePosts`: 옮길 다이어리가 이 블로그 것인지 보고 `category_id`만 바꿔요. `content_updated_at`은 건드리지 않아요.
- `deletePosts`: 사진 키를 먼저 모으고, `DELETE ... WHERE id IN (...)`, 그다음 커밋 뒤 파일 삭제. 한 개 지울 때와 같은 방식이에요.

### 마지막 다이어리 기억: `PostCommandService.lastCategory`

`GET /api/me/last-category`가 내 블로그에서 `created_at DESC, id DESC`로 가장 최근 글 하나의 `category_id`를 돌려줘요. 글이 없으면 `is_default`인 다이어리예요. 따로 저장해 두지 않고 매번 `posts`에서 찾아요. 글을 올린 뒤 화면이 `qk.lastCategory` 캐시를 지워서 다음 글쓰기에 바로 반영돼요.

### 임시저장 검사: `DraftService.save`

정식 글보다 느슨해요(V5 주석 그대로).

- 제목과 본문이 **둘 다** 비어야 `DRAFT_EMPTY`. 길이 상한(100자, 10,000자)은 같아요.
- 다이어리는 `ownCategory`가 내 블로그 것인지 보고, 아니면 오류 대신 `null`로 비워요.
- 분야는 없는 코드면 `null`, 공개 범위는 SUBSCRIBERS·PRIVATE가 아니면 PUBLIC으로 바꿔요.
- 태그는 정식 글과 같은 `normalize`라서 규칙에 어긋나면 거절돼요.
- 태그와 사진 번호는 PostgreSQL 배열 칸(`tags varchar(15)[]`, `image_ids bigint[]`)에 그대로 넣어요. 정식 표(`post_tags`, `post_images.post_id`)에는 올릴 때만 연결해요.
- 새로 만들 때만 `count(*)`로 20개를 세고, 넘으면 `DRAFT_LIMIT`(409)예요. 덮어쓰기는 세지 않아요.
- UPDATE·DELETE는 언제나 `member_id = 나` 조건을 붙여요. 남의 임시저장 번호면 0줄이 바뀌어서 `DRAFT_NOT_FOUND`(404)예요.
- 불러올 때(`get` → `view`)는 `image_ids` 중 지금도 `post_images`에 있고 내가 올린 사진만 `{ id, url }`로 돌려줘요.

### 저장 안 한 내용 지키기: `useUnsavedChangesPrompt`

- 편집 화면은 제목, 본문, 다이어리, 분야, 공개 범위, 태그, 대표 사진을 `JSON.stringify`로 묶은 `snapshot`을 만들어요. 마지막 저장·불러오기 때의 값과 다르거나 태그 칸에 글자가 남아 있으면 `dirty`예요.
- `dirty`이면 React Router의 `useBlocker`로 화면 이동을 잡아 `confirm`을 띄우고, `beforeunload`로 창 닫기·새로고침도 잡아요.
- 저장에 성공하면 `allowNavigation()`을 먼저 불러서 글 화면으로 갈 때는 묻지 않아요.
- 화면은 `busy` ref로 "올리기" 연타를 막아요. 자동 임시저장도 `draftBusy`, `busy`를 보고 겹치지 않게 해요.

## 왜 이렇게 만들었나

- **본문을 마크다운 원문으로 저장**: 서버에 HTML을 저장하면 정화(위험한 것 걷어 내기) 라이브러리와 저장 형식이 늘어나요. 원문으로 두면 정화 규칙을 화면 렌더러 한 곳에서만 관리해요. WYSIWYG 편집기(보이는 대로 편집하는 도구)는 원본 기획에서 "편집기 고급 기능 제외"라 쓰지 않았어요. (research.md §6)
- **`skipHtml` + 주소 허용 목록**: 원시 HTML을 아예 안 그리고, 주소는 쓸 것만 허용하는 방식(허용 목록)이 막을 것을 하나하나 적는 방식(차단 목록)보다 빠뜨릴 위험이 적어요. (research.md §6, NF-07)
- **매직 넘버로 종류 확인**: 확장자와 브라우저가 보낸 Content-Type은 보내는 쪽이 마음대로 바꿀 수 있어요. 파일 내용은 속이기 어려워요. (research.md §5)
- **`ImageStorage` 인터페이스로 감싸기**: 04-MinIO 문서 권고대로 S3 표준 SDK를 쓰되 인터페이스 뒤에 숨겨서, 디스크와 S3를 설정 하나로 바꿔요. (research.md §5)
- **사진을 서버가 직접 내려 주기**: MinIO 공개 주소를 쓰면 MinIO 포트를 밖에 열어야 해요. 서버가 읽어서 내려 주면 저장소는 안쪽에만 둬도 돼요. 미리 서명한 주소(presigned URL)는 배포 때 검토할 대안으로 남겼어요. (research.md §5, `ImageController` 주석)
- **파일 삭제는 커밋 뒤에**: DB를 지우다 실패해 되돌렸는데 파일만 먼저 지워졌으면 깨진 사진이 남아요. 반대로 파일 삭제가 실패하면 디스크에 쓰레기만 조금 남고 화면은 멀쩡해요. 덜 나쁜 쪽을 골랐어요. (research.md §5)
- **올리자마자 저장하고 나중에 연결**: 글을 올리기 전에 미리보기에서 사진이 보여야 해서 먼저 저장해요. 그 대신 버려진 사진이 생기니 24시간 정리 작업으로 치워요. (research.md §5)
- **임시저장은 배열 칸에**: 아직 올린 글이 아니라서 정식 연결 표를 건드리지 않고 배열로만 들고 있어요. 올릴 때 한 번에 정식 표로 옮겨요. (V5 주석)

## 공부 키워드

- `multipart/form-data`: 파일을 HTTP로 보낼 때 쓰는 요청 형식
- 매직 넘버(파일 시그니처): 파일 종류마다 정해진 첫 몇 바이트
- UUID: 겹칠 일이 사실상 없는 무작위 식별자
- 경로 조작(path traversal): `../`로 허용된 폴더 밖 파일에 접근하는 공격
- XSS와 허용 목록(allowlist): 남의 화면에서 스크립트를 돌리는 공격과 그걸 막는 방식
- react-markdown, remark-gfm: 마크다운을 React로 그리는 라이브러리와 GFM 확장
- HTTP 캐시(`Cache-Control`, `max-age`): 브라우저가 응답을 다시 받지 않고 재사용하는 규칙
- Spring `@Transactional`과 `TransactionSynchronization.afterCommit`: 트랜잭션과 커밋 뒤에 할 일 걸기
- 외래 키 `ON DELETE CASCADE` / `SET NULL`: 부모 줄이 지워질 때 자식 줄을 어떻게 할지
- Spring `@Scheduled(fixedDelay)`, `@ConditionalOnProperty`: 주기 작업, 설정 값으로 빈 고르기
