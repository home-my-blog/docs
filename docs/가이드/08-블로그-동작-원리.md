# 08. 블로그 동작 원리 (실제 코드 기준)

> 공부용 정리예요. 큰 그림부터 보고, 기능 하나씩 "누르면 무슨 일이 생기는지"를 따라가요.
> 2026-10-12에 **지금 돌아가는 코드**를 보고 썼어요. [06-아키텍처-그림.md](06-아키텍처-그림.md)는 만들기 전 가안이라 두 군데가 달라요.

> - 사진 파일: 가안은 MinIO, 실제는 **서버 디스크**(MinIO로 바꿀 수 있게 코드는 있어요)
>
> 기능별 규칙(글자 수, 점수 등)은 [07-기능-설명서.md](07-기능-설명서.md)에 있어요.

## 1. 큰 그림: 누가 무슨 일을 하나

```
[내 브라우저]  ──HTTP 요청──▶  [서버 (Spring Boot)]  ──▶  [PostgreSQL]  글·회원·댓글 등 오래 둘 것
   React 화면   ◀──JSON 응답──                       ──▶  [Redis]       잠깐만 둘 것 (인증번호, 조회수 중복 막기)
                                                     ──▶  [디스크]      사진 파일
```

| 부분 | 쓴 기술 | 하는 일 |
|---|---|---|
| 화면 (프론트엔드) | React 19, Vite, TanStack Query | 보이는 모든 것. 버튼을 누르면 서버에 요청을 보내고 받은 데이터를 그려요 |
| 서버 (백엔드) | Spring Boot 3.5, Java 21 | 요청을 받아 규칙을 검사하고, DB에 읽고 쓰고, 결과를 JSON으로 돌려줘요 |
| 데이터베이스 | PostgreSQL | 회원, 블로그, 다이어리, 글, 댓글, 좋아요, 구독, 잉크 내역 같은 "잃어버리면 안 되는 것" |
| 캐시 | Redis | 10분짜리 인증번호, "30분 안에 또 본 글" 표시처럼 시간이 지나면 사라져도 되는 것 |

### 화면과 서버는 어떻게 대화하나

- 화면은 서버에 `GET /api/posts/12`, `POST /api/posts`처럼 **주소 + 동작(메서드)** 으로 요청해요.
  - GET은 "보여 줘", POST는 "새로 만들어 줘", PUT은 "바꿔 줘/켜 줘", DELETE는 "지워 줘".
- 서버는 `{ "id": 12, "title": "..." }` 같은 **JSON**으로 답해요. 화면은 그걸 받아서 그려요.
- 이런 주소 모음을 **API**라고 불러요. 사각의 API는 모두 `/api/`로 시작해요.
- 화면 쪽 요청 코드는 `frontend/src/api/endpoints.ts`, 서버 쪽 받는 코드는 `...Controller.java` 파일들이에요.

### 화면 파일은 어디서 오나

- 배포할 때 React 화면을 빌드한 파일(html, js, css)을 **서버 안에 같이 넣어요** (`Dockerfile`).
- 그래서 `sagak.java21.net` 하나로 화면도 API도 다 나와요.
- `/blogs/1`처럼 화면 주소로 들어오면 서버는 `index.html`을 주고, 어떤 화면을 그릴지는 React가 정해요 (`SpaConfig.java`).
  이런 방식을 **SPA(Single Page Application)** 라고 해요.

## 2. 회원가입: 이메일 인증번호

1. 이메일을 넣고 "인증번호 받기"를 누르면 `POST /api/auth/verifications`
2. 서버가 먼저 이미 가입된 이메일인지, 닉네임이 겹치는지 봐요.
3. 6자리 번호를 만들어 **Redis에 10분짜리로** 저장하고 메일로 보내요.
   - 다시 받기 간격, 하루 최대 횟수도 Redis에 숫자로 세어 둬요.
   - 새 번호를 받으면 이전 번호는 무효가 돼요.
4. 번호를 입력하면 `POST /api/auth/verifications/confirm` → Redis의 번호와 비교해서 맞으면 "인증됨" 표시를 남기고 번호는 지워요.
5. 마지막으로 `POST /api/auth/signup` 때 서버가 "인증됨" 표시를 **한 번 더** 확인하고 회원을 만들어요.
   - 화면만 믿지 않고 서버가 다시 확인하는 게 중요해요. 화면은 사용자가 마음대로 조작할 수 있거든요.

**비밀번호는 그대로 저장하지 않아요.**
- **BCrypt**라는 방식으로 "되돌릴 수 없게 섞은 값(해시)"만 DB에 저장해요.
- 로그인할 때는 입력한 비밀번호를 같은 방식으로 섞어서 저장된 값과 같은지만 봐요.
- 그래서 DB가 유출돼도 원래 비밀번호는 알 수 없어요.

> 메일을 실제로 보내는 SMTP 설정은 아직 미뤄 둔 상태예요. 설정 전에는 메일 내용을 서버 로그에만 찍는 모드가 있어요 (`LogMailSender`).

## 3. 로그인: 세션과 쿠키

HTTP는 원래 **기억력이 없어요.** 요청 하나하나가 독립이라, "아까 로그인한 그 사람"을 알려면 따로 장치가 필요해요. 사각은 **세션 + 쿠키** 방식을 써요.

1. 이메일·비밀번호를 넣고 로그인 → `POST /api/auth/login`
2. 서버(`LoginService`)가 비밀번호를 BCrypt로 확인해요.
   - **5번 틀리면 10분 잠가요.** (무작정 비밀번호를 대입하는 공격 막기)
   - 없는 이메일이어도 일부러 똑같이 시간을 써서, 응답 속도로 "이 이메일이 가입돼 있구나"를 알아채지 못하게 해요.
3. 맞으면 서버가 **세션**을 만들어요. 서버 메모리에 "세션 번호 abc123 = 회원 7번"이라고 적어 두는 거예요.
4. 그 세션 번호를 **쿠키**(`MYBLOG_SESSION`)에 담아 브라우저에 줘요.
5. 이후 브라우저는 요청마다 이 쿠키를 자동으로 같이 보내요. 서버는 번호를 보고 "아, 7번 회원이구나" 해요.

더 알아 두면 좋은 것:
- 쿠키는 **7일** 유지되고, 사이트를 쓸 때마다 다시 7일로 늘어나요 (`SessionCookieRefreshFilter`).
- 로그인할 때 세션 번호를 **새로 바꿔 줘요**. 로그인 전 번호를 훔쳐 둔 사람이 그대로 쓰지 못하게 하는 장치예요 (세션 고정 공격 방지).
- 비밀번호를 바꾸거나 탈퇴하면 다른 기기의 로그인도 끊어요 (`MemberSessionService`).
- 로그인이 필요한 곳(글쓰기, 내 정보 등)에 쿠키 없이 오면 서버가 **401**을 돌려주고, 화면은 그걸 보고 로그인 창을 띄워요.
- 어떤 주소가 로그인이 필요한지는 `SecurityConfig.java` 한 곳에 모여 있어요. 대체로 "보기(GET)는 누구나, 쓰기는 로그인한 사람만"이에요.

### CSRF 토큰: 남의 사이트가 나인 척 요청하는 것 막기

- 쿠키는 브라우저가 **자동으로** 붙여 보내요. 그래서 내가 로그인한 채로 나쁜 사이트에 들어가면, 그 사이트가 몰래 사각에 "글 지워 줘" 요청을 보낼 수 있어요. 이걸 **CSRF 공격**이라고 해요.
- 막는 방법: 서버가 `XSRF-TOKEN` 쿠키로 랜덤 값을 주고, 화면은 쓰기 요청마다 그 값을 `X-XSRF-TOKEN` **헤더에 직접 옮겨 적어** 보내요.
- 다른 사이트는 사각 쿠키 내용을 읽을 수 없으니 헤더를 채울 수 없고, 서버는 헤더가 없거나 틀린 요청을 거절해요.
- 코드: 화면 `frontend/src/api/client.ts`, 서버 `SecurityConfig.java`.

## 4. 글쓰기와 글 읽기

**쓰기**
1. 발행하면 `POST /api/blogs/{블로그}/posts`로 제목, 본문(마크다운), 다이어리, 분야, 태그, 공개 범위, 사진 번호들을 보내요.
2. 서버(`PostCommandService`)가 검사해요.
   - **내 블로그인지** (남의 블로그엔 못 써요)
   - 제목·본문 길이, 다이어리·분야가 실제로 있는지
3. 통과하면 `posts` 표에 저장하고, 태그와 사진을 글에 연결해요. 이 과정을 **트랜잭션** 하나로 묶어서, 중간에 실패하면 전부 없던 일로 돌려요.
4. 공개 글을 새로 올리면 잉크도 적립돼요 (6번).
- 쓰다가 나가도 괜찮게 **임시저장**(`drafts` 표)이 따로 있어요.

**읽기**
1. 글을 열면 `GET /api/posts/12`
2. 서버가 **이 사람이 이 글을 볼 수 있는지** 먼저 봐요.
   - 공개 글: 누구나
   - 구독자만: 그 블로그나 다이어리를 구독한 사람 + 주인
   - 비공개: 주인만
   - 다이어리 자체가 비공개면 그 안의 글은 다 주인만
   - 볼 수 없는 글은 "없는 글"(404)처럼 답해요. 글이 있다는 사실도 알려 주지 않으려고요.
3. 본문은 마크다운 그대로 보내고, 화면이 `react-markdown`으로 HTML로 그려요. 이때 위험한 링크(`javascript:` 같은)는 걸러요.

**조회수는 어떻게 세나** (`ViewRecorder`)
- 로그인 안 한 사람도 구분하려고 `MYBLOG_VID`라는 1년짜리 쿠키를 줘요.
- 글을 열면 Redis에 "이 사람이 이 글 봤음"을 **30분짜리로** 적어요. 이미 있으면 조회수를 안 올려요. 새로고침 연타로 조회수를 부풀리지 못하게요.
- 블로그 방문자 수는 하루(한국 시간) 한 번만 세요.
- 주인 본인이 본 건 안 세요.

## 4-1. 사진 올리기
사진 한 장이 내 컴퓨터에서 글 화면에 보이기까지 일어나는 일을 순서대로 적었어요.
등장인물은 셋이에요.

- **브라우저**: 화면 쪽 코드. React로 만들었어요.
- **서버**: Spring Boot(Java)로 만들었어요.
- **저장소**: 사진 파일은 서버 컴퓨터의 디스크에, 사진 정보는 PostgreSQL 데이터베이스에 둬요.

### 1. 사진 고르기 (브라우저)

1. "이미지 올리기"를 누르면 파일 선택 창이 열려요.
2. 사진을 고르면 브라우저가 그 파일을 `FormData`라는 상자에 담아요.
   - 글자가 아닌 파일을 보낼 때 쓰는 형식이에요. 정식 이름은 `multipart/form-data`예요.
3. 그 상자를 `POST /api/images` 주소로 서버에 보내요.
   - 코드: `frontend/src/api/endpoints.ts`의 `uploadImage`
   - 이때 로그인 쿠키도 함께 가서, 서버는 누가 올렸는지 알 수 있어요.

### 2. 받아서 검사하기 (서버)

`ImageController`가 요청을 받아 `ImageService.upload`에 넘겨요.

1. **크기 검사**: 0바이트이거나 5MB를 넘으면 거절해요.
2. **진짜 사진인지 검사**: 파일 이름의 확장자(.jpg)는 믿지 않아요.
   - 파일 맨 앞 몇 바이트(매직 넘버)를 직접 봐요. PNG는 항상 `89 50 4E 47`로 시작하는 식이에요.
   - 그래서 이름만 .jpg로 바꾼 다른 파일은 걸러져요.
   - jpeg, png, gif, webp만 받아요.
3. **새 이름 붙이기**: `posts/2026-10/랜덤문자열.png`처럼 겹치지 않는 이름(UUID)을 새로 지어요.
   - 원래 파일 이름은 버려요. 같은 이름끼리 덮어쓰지 않고, 이름에 개인정보가 섞여 있어도 남지 않아요.

### 3. 저장하기

1. **파일 자체**는 서버 디스크의 `/data/images` 폴더에 저장해요(`DiskImageStorage`).
   - 이 폴더는 Docker 볼륨이라, 새 버전을 배포해도 사진이 지워지지 않아요.
2. **사진 정보**는 데이터베이스 `post_images` 표에 한 줄 적어요.
   - 누가 올렸는지, 파일 이름, 종류, 크기, 올린 시각이 들어가요.
   - 이 줄의 번호(id)가 사진의 번호가 돼요.
3. 서버는 브라우저에 `{ id: 12, url: "/api/images/posts/2026-10/....png" }`를 돌려줘요.

### 4. 글에 넣기 (브라우저)

1. 브라우저는 받은 주소로 본문에 `![](/api/images/...)`를 넣어요. 사진을 넣는 마크다운 문법이에요.
2. 편집 화면에서는 이게 `[📷 사진 1]`로 짧게 보여요(`photoTokens.ts`). 저장될 때는 원래 문법으로 바뀌어요.
3. 사진 번호(id)들은 따로 모아 두었다가 "발행"할 때 글과 함께 보내요.

### 5. 발행하면 글과 연결하기

1. 서버는 글을 저장하면서 `post_images`의 해당 줄들에 "이 글 소속"이라고 적어요(`attach`).
2. 남의 사진 번호를 몰래 넣어도 소용없어요. 올린 사람이 나인 사진만 연결돼요.
3. 대표 사진(★)은 글 표의 `cover_image_id` 칸에 그 사진 번호를 적어 둔 거예요.

### 6. 화면에 보여 주기

1. 누가 글을 열면 브라우저가 본문의 `![](/api/images/...)`를 보고 그 주소로 사진을 요청해요.
2. 서버는 데이터베이스에서 종류를, 디스크에서 파일을 꺼내 돌려줘요.
3. 이때 "30일 동안 다시 받지 않아도 돼"라는 표시(`Cache-Control`)를 붙여요.
   - 그래서 두 번째부터는 브라우저가 가지고 있던 걸 바로 써서 빨라요.

### 7. 버려진 사진 치우기

사진을 올려 놓고 글을 안 쓰고 나가면, 어디에도 연결되지 않은 사진이 남아요.

- 서버가 1시간마다 이런 사진을 찾아요(`cleanOrphans`).
- 올린 지 24시간이 지났는데 글에도 임시저장에도 안 쓰인 사진이면 파일과 정보를 같이 지워요.

### 한눈에 보기

```
[브라우저] 사진 고름
   │  POST /api/images (파일 + 로그인 쿠키)
   ▼
[서버] 크기·매직넘버 검사 → 새 이름(UUID)
   ├─▶ [디스크] /data/images/posts/2026-10/xxx.png   (파일)
   └─▶ [DB] post_images 한 줄                       (정보)
   │  { id, url } 돌려줌
   ▼
[브라우저] 본문에 ![](url) 넣음 → 발행 때 사진 번호들 함께 보냄
   ▼
[서버] post_images.post_id = 글 번호 (내 사진만)
   ▼
[읽는 사람 브라우저] GET /api/images/... → 사진 표시 (30일 캐시)
```

## 5. 댓글, 좋아요, 구독, 북마크

모두 같은 모양이에요: 버튼 → API 요청 → 서버가 규칙 검사 → DB에 한 줄 쓰거나 지움.

| 기능 | 규칙 | DB |
|---|---|---|
| 댓글·답글 | 로그인 필요. 5초 안에 연달아 못 달아요 (Redis로 막음) | `comments` |
| 좋아요 | 누르면 켜고 다시 누르면 꺼요. 내 글엔 못 눌러요 | `post_likes` |
| 구독 | 블로그 전체나 다이어리 하나를 구독. 내 블로그는 못 해요 | `subscriptions` 등 |
| 북마크 | 폴더로 정리. 나만 봐요 | `bookmarks` |

"누르면 켜고 다시 누르면 끄는" 걸 **토글**이라고 해요.

화면은 **TanStack Query**로 서버 데이터를 들고 있어요. 좋아요를 누르면 관련 데이터를 "낡았음"으로 표시하고 다시 받아 와서 숫자가 바로 바뀌어요.

---

## 6. 잉크와 스티커 상점

- 잉크는 **지갑 잔액 + 내역** 두 가지로 저장해요. 받을 때도 쓸 때도 내역에 한 줄씩 남겨요.
- 버는 법:
  - 하루 첫 방문 출석 (한국 시간 기준)
  - 공개 글 쓰기 (하루 한도 있음)
  - 남의 글에 댓글 (하루 한도 있음)
- 하루 한도는 오늘 내역을 세어서 확인해요.
- 스티커 팩을 사면 잔액이 모자란지 확인하고, 잉크를 빼면서 스티커를 내 것으로 표시해요.
  - 이것도 트랜잭션 하나라서, 중간에 문제가 생기면 잉크만 빠지고 스티커는 없는 일이 안 생겨요.
  - 지갑 줄을 **잠그고** 계산해서, 두 번 빠르게 눌러도 잔액이 꼬이지 않아요.
- 연속 출석, 도전과제 진행도는 출석·글·댓글 내역을 세어서 계산해요.

---

## 7. 검색과 실시간 인기 검색어

- 검색은 `GET /api/search?q=...` → DB에서 제목·본문·블로그 이름 등을 찾아요. **공개 글만** 나와요.
- 검색할 때마다 검색 기록을 남겨요.
- 인기 검색어 (`TrendingService`)
  - **5초마다** 최근 24시간 데이터를 다시 계산해서 서버 메모리에 들고 있어요.
  - 점수 = 검색 수 × 3 + 그 단어가 제목에 든 공개 글의 조회수 × 1 + 댓글 수 × 5
  - 화면은 계산된 결과만 받아 가니까 빨라요.

---

## 8. 시간 맞춰 저절로 도는 일 (스케줄)

| 언제 | 무엇 |
|---|---|
| 5초마다 | 인기 검색어 다시 계산 |
| 1시간마다 | 글에 안 쓰인 채 24시간 지난 사진 지우기 |
| 매일 새벽 4:30 | 오래된 검색 기록 정리 |
| 매일 새벽 4:40 | 탈퇴하고 30일 지난 회원 정리 |

Spring의 `@Scheduled`를 붙이면 서버가 알아서 그 시간에 실행해요.

## 9. Redis가 꺼지면?

`RedisGuard`가 두 가지로 나눠서 다뤄요.
- **꼭 필요한 일** (인증번호): Redis 없으면 "잠시 후 다시 시도" 오류
- **없어도 되는 일** (조회수 중복 막기, 댓글 연타 막기): 그냥 건너뛰어요

그래서 Redis가 꺼져도 로그인과 글 읽기는 돼요.

---

## 10. DB 구조는 어떻게 바꾸나: Flyway

- DB 표를 만들거나 바꿀 땐 `V1__...sql`, `V2__...sql`처럼 **번호 붙은 SQL 파일**을 추가해요 (`backend/src/main/resources/db/migration/`).
- 서버가 켜질 때 Flyway가 "아직 안 한 번호"만 순서대로 실행해요. 지금 V20까지 있어요.
- 이미 실행된 파일은 절대 고치지 않고, 바꿀 게 있으면 새 번호로 추가해요.
  - 예: 미분류 → 일기장 이름 바꾸기가 V20이에요.

---

## 11. 배포: 코드가 사이트에 올라가기까지

1. PR을 main에 머지하면 GitHub Actions가 시작해요 (`.github/workflows/deploy.yml`).
2. **CI**: 백엔드 테스트, 프론트엔드 검사·테스트를 돌려요. 하나라도 실패하면 멈춰요.
3. **CD**:
   - Docker 이미지를 만들어요 (화면 + 서버를 한 상자에).
   - 그 이미지를 서버로 보내요.
   - `deploy/deploy.sh`로 기존 걸 내리고 새 걸 8390 포트로 띄워요.
4. DB 비밀번호 같은 비밀값은 코드에 안 쓰고 **GitHub Secrets**에 넣어 두고 배포 때만 꺼내 써요.
   - 저장소가 공개라서 특히 중요해요.
