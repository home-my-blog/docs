# 05. 배포 준비

> **한 줄 요약:** 배포는 내 컴퓨터가 아닌 곳에 올려서 **다른 사람이 쓸 수 있게** 하는 일입니다. 배포까지 할 가능성이 높지만, **어디에 올릴지는 아직 모릅니다.** 먼저 환경을 확인해야 합니다.
> 상태: 배포 환경은 **미정**입니다. 아래는 가안입니다.
> 관련 파일: [02-도커-컴포즈-쿠버네티스.md](02-도커-컴포즈-쿠버네티스.md), [03-로컬환경-도커컴포즈-사용법.md](03-로컬환경-도커컴포즈-사용법.md), [04-MinIO-현황과-선택.md](04-MinIO-현황과-선택.md)
> 읽는 순서는 [00-목차.md](00-목차.md)를 봅니다.

## 1. 큰 그림

| 환경 | DB·Redis·MinIO | 서버와 화면 |
|---|---|---|
| **로컬(개발)** | Docker Compose로 내 컴퓨터에 켬 | IntelliJ에서 실행 |
| **배포** | **누가 제공하느냐에 따라 달라짐** (아래 표) | 어딘가에 올려서 실행 |

배포에서는 DB·Redis·MinIO뿐 아니라 **우리가 만든 서버(Spring)와 화면(React)도 올릴 곳**이 필요합니다.

## 2. 학교가 무엇을 제공하느냐에 따라 달라진다

| 학교가 제공하는 것 | 우리가 할 일 |
|---|---|
| DB·Redis·MinIO 서버 | 접속 정보(주소, 아이디, 비밀번호)만 받아 설정에 적는다. Compose는 로컬에서만 쓴다 |
| 앱을 올리는 곳이 **Kubernetes** | 우리 구조는 단일 서버로 만들되, **올릴 때는 학교 양식**(Dockerfile과 쿠버네티스 설정)을 따라야 할 수 있다 |
| 서버 컴퓨터 한 대 (SSH 접속) | Compose에 서버와 화면까지 넣어 한 대에 올릴 수 있다 |
| 아무것도 제공 안 함 | 서버 컴퓨터를 직접 구해야 한다 (클라우드 등) |

예전 프로젝트가 쿠버네티스로 배포한 것도 우리가 고른 것이 아니라 **과정의 배포 환경이 그랬기 때문**일 수 있습니다.

## 3. 확인해야 할 질문 (마르코님이나 강사님, 팀 회의에서)

1. 이번 프로젝트는 **배포까지 하나요?** (평가나 시연에 필요한가요?)
2. 한다면 **DB, Redis, MinIO 서버를 학교가 제공하나요?**
3. 서버와 화면을 올릴 곳은 어떤 형태인가요? (쿠버네티스인지, 서버 한 대에 직접 올리는지)

답을 받으면 `CLAUDE.md`와 문서의 "배포: 미정"을 확정합니다.

## 4. 배포하면 새로 생기는 일

| 해야 할 일 | 내용 | 참고 |
|---|---|---|
| **포장** | 서버(Spring)와 화면(React)을 Dockerfile로 포장한다 | 예전 프로젝트의 Dockerfile은 빌드용과 실행용을 나눈 구조(멀티 스테이지)였다 |
| **설정 분리** | 개발(`localhost`)과 배포(환경변수)를 나눈다. 비밀번호는 Git에 올리지 않는다 | 아래 5번 |
| **HTTPS** | 로그인 쿠키를 `Secure`로 쓰려면 배포 서버가 HTTPS여야 한다 | 요구사항 NF-04, NF-10 ([상세/07](../상세/07-공통규칙.md), [상세/01](../상세/01-인증-인가.md)) |
| **웹 서버 앞단** | HTTPS 처리와 요청 전달을 맡는 Nginx 같은 것 | 지금 **미정** |
| **DB·Redis·MinIO** | 학교가 제공하면 접속 정보만 받고, 아니면 한 대에 같이 올린다 | 2번 표 |

## 5. 설정을 나눠 두면 어느 환경이든 같은 코드를 쓸 수 있다

접속 정보를 코드에 박지 않고 **설정으로 분리**합니다.

| 설정 | 내용 |
|---|---|
| `application-dev` | 내 컴퓨터(`localhost`)에서 Compose로 켠 DB·Redis·MinIO에 접속 |
| `application-prod` | 접속 정보를 **환경변수**로 받음 (학교 서버든 직접 구한 서버든) |

## 6. MinIO는 배포하면 판단이 달라질 수 있다

개발 때는 내 컴퓨터 안에서만 돌아서 위험이 작습니다. 배포하면 **인터넷에 열린 서버와 같이 돌게 되므로** 패치 없는 이미지의 위험이 커집니다.

- **MinIO 포트(9000, 9001)는 바깥에 열지 않고**, 우리 서버만 접속하게 한다. 이미지는 서버를 거쳐 보여 준다.
- **학교가 MinIO를 제공**한다면 그걸 쓰면 위험이 줄어든다.
- 직접 올려야 하는데 불안하면 **서버 디스크 저장으로 바꿔 끼운다.** (`ImageStorage` 인터페이스) 자세한 내용은 [04-MinIO-현황과-선택.md](04-MinIO-현황과-선택.md)에 있다.

## 7. 추천 순서

1. **배포 환경 질문 3개를 먼저 확인한다.** 일정이 2주라서, 배포를 마지막에 하면 환경 문제를 뒤늦게 발견할 수 있다.
2. 확인을 기다리는 동안 요구사항 문서와 구현 방식을 정리한다.
3. 구현을 시작하면 **빈 서버와 DB 연결만 있는 상태로 먼저 한 번 배포**해 본다. 환경의 제약을 일찍 알 수 있다.
4. 배포 방식이 정해지면 이 문서에 Dockerfile, 환경변수, HTTPS 설정 방법을 추가한다.

## 8. 정하지 못한 것

- 배포를 하는지, 어디에 올리는지, 누가 DB·Redis·MinIO를 제공하는지
- 웹 서버 앞단(Nginx)을 쓸지
- 배포에서 Docker Compose를 쓸지 (서버가 한 대라서 후보)
- 자동 배포(GitHub Actions)를 할지
