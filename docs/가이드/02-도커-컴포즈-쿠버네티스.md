# 02. 도커, 컴포즈, 쿠버네티스

> **한 줄 요약:** 도커는 프로그램을 담는 **상자**, 컴포즈는 상자 여러 개를 켜는 **주문서**, 쿠버네티스는 서버 여러 대에서 상자를 관리하는 **매니저**입니다. 우리는 **도커 컴포즈(개발용)만** 쓰는 것으로 가안합니다.
> 관련 파일: [01-서버와-접속도구.md](01-서버와-접속도구.md), [03-로컬환경-도커컴포즈-사용법.md](03-로컬환경-도커컴포즈-사용법.md), [05-배포-준비.md](05-배포-준비.md)
> 읽는 순서는 [00-목차.md](00-목차.md)를 봅니다.

## 1. 세 도구의 차이

| 도구 | 하는 일 | 주로 쓰는 때 |
|---|---|---|
| **Docker** (Dockerfile) | 내 프로그램을 상자에 포장 | 개발과 배포 둘 다 |
| **Docker Compose** | 한 컴퓨터에서 상자 여러 개를 주문서 한 장으로 켜고 끔 | **주로 개발용** (내 노트북) |
| **Kubernetes** | 서버 여러 대에서 상자를 자동으로 배치·재시작·교체 | **배포·운영 전용** (서버가 많을 때) |

## 2. 용어를 밀키트에 빗대면

| 용어 | 쉬운 뜻 | 비유 |
|---|---|---|
| 이미지 | 프로그램과 설정이 다 들어 있는 꾸러미 | 밀키트 |
| 컨테이너 | 이미지를 실제로 켠 것 | 밀키트로 만든 요리 |
| 볼륨 | 컨테이너를 지워도 데이터가 남는 저장 공간 | 냉장고 |
| 포트 | 내 컴퓨터에서 접속하는 문 번호 | 가게의 호수 |
| compose 파일 | 무엇을 어떻게 켤지 적은 설정 파일 (`docker-compose.yml`) | 주문서 |

## 3. 쿠버네티스는 서버를 열어 주지 않습니다

| | 비유 | 실제 |
|---|---|---|
| 서버 컴퓨터 | 식당 건물과 주방 | 학교, 클라우드, 직접 산 컴퓨터 |
| Docker 상자 | 요리 하나하나 | 서버·DB·Redis 프로그램 |
| **Kubernetes** | **식당 매니저** | 상자를 어느 주방에 둘지 정하고, 죽으면 다시 켜고, 손님이 늘면 복사해서 늘림 |
| Docker Compose | 우리 집 식탁에 도시락통 몇 개 펴기 | 내 노트북에서 상자 몇 개 켜기 |

매니저는 건물을 지어 주지 않습니다. **서버 컴퓨터는 누군가 먼저 준비해야 합니다.** 쿠버네티스는 DB나 Redis를 제공해 주지도 않습니다.

쿠버네티스가 해 주는 일은 이런 것들입니다.
- 서비스마다 상자를 2개씩 띄우기 (예전 프로젝트의 `replicas: 2`)
- 죽은 상자 자동 재시작
- 새 버전으로 하나씩 교체
- 바깥 요청을 알맞은 상자로 연결 (Ingress)

## 4. 예전 프로젝트(aiot3)에서 확인한 것

| 내용 | 근거 | 확실도 |
|---|---|---|
| 서비스마다 `Dockerfile`이 있었다 | 서비스 9개 이상의 폴더에 각각 있음 | 확인됨 |
| **배포 때**는 이미 켜져 있는 DB·Redis·MinIO 서버에 접속했다 | 쿠버네티스 설정에 접속 정보(secret)만 있음 | 확인됨 |
| **로컬 테스트 때** DB·Redis는 docker-compose로 켜는 것으로 설계했다 | 설계 문서(`member_service_integrated_design.md`)에 적혀 있음 | 문서에 적혀 있음 |
| 자동 배포 흐름: `main`에 올림 → 테스트 → 이미지 생성 → 서버에 설정 파일 복사 후 적용 | GitHub Actions 설정(`deploy.yml`, `central-deploy.yml`) | 확인됨 |
| 그 서버를 학교가 열어 주었다 | 접속 정보만으로는 누가 켰는지 알 수 없음 | 추정 |
| 실제 `docker-compose.yml` 파일이 있었다 | 이 폴더에서는 찾지 못함 (팀원 컴퓨터에 있었을 수 있음) | 확인 못 함 |

정리하면 환경이 **두 종류**였습니다.

| 환경 | DB·Redis는 어디에? | 쓰는 때 |
|---|---|---|
| 배포·공용 환경 | 이미 켜져 있던 서버 | 팀이 함께 쓰는 실제 환경 |
| **내 컴퓨터(로컬)** | **compose로 켠 것** | 코드를 만들고 테스트할 때 |

로컬에서 compose를 쓰는 이유는 문서에 적혀 있지 않아 추정입니다. 공용 서버를 내 테스트로 어지럽히지 않으려고, 내 컴퓨터만으로 실행하려고, 깨끗한 상태로 다시 시작하려고였을 것입니다. 테스트 자동화(GitHub Actions)에서도 PostgreSQL, Redis, MinIO를 상자로 띄웠습니다.

## 5. 우리 프로젝트의 선택

| 도구 | 우리 프로젝트 | 이유 |
|---|---|---|
| Docker Compose | **쓴다** (개발용) | 학교가 열어 주던 서버 준비를 내 컴퓨터에서 대신해 줌 |
| Dockerfile | 배포 단계에서 만든다 | 서버와 화면을 포장할 때 필요. 배포 환경이 정해지면 결정 |
| GitHub Actions (자동 테스트·배포) | 배포 단계에서 검토한다 | |
| **Kubernetes** | **쓰지 않는다** | 서버가 한 대(단일 서버로 확정)라서 과함 |

다만 **학교의 배포 환경이 Kubernetes라면** 올리는 형식은 그쪽 양식을 따라야 할 수 있습니다. 우리 구조가 단일 서버여도 올리는 방식은 환경이 정하기 때문입니다. 이 확인은 [05-배포-준비.md](05-배포-준비.md)에 있습니다.
