## 2. 기술별 설명

### 2.1 React (Vite) — 화면

- **쉬운 설명**: 사용자가 보고 누르는 화면을 만드는 도구입니다. 화면을 "카드", "헤더", "글 목록" 같은 **조각(컴포넌트)**으로 나눠 조립하고, 서버에서 받은 데이터로 그 조각을 채웁니다. Vite는 개발 중에 화면을 빠르게 띄워 주는 도구입니다.
- **우리가 쓰는 곳**: 지금 만든 HTML 시안의 모든 화면을 옮깁니다. 화면 구조, 문구, CSS는 그대로 쓰고, 화면을 그리는 코드만 컴포넌트로 다시 작성합니다.
- **고른 이유**: 풀스택으로 서버와 화면을 나누기로 했고, 글 목록·그래프·댓글처럼 **화면이 자주 바뀌는 기능**이 많아서 조각으로 나눠 다루는 방식이 편합니다. 팀원 문서도 React를 씁니다.
- **대안**: 지금처럼 HTML과 JavaScript만 쓰는 방식(작은 화면에는 충분하지만 화면이 늘면 관리가 어려움), Vue(비슷한 성격이지만 팀과 맞추기 어려움).
- **상태**: 가안

### 2.2 Spring Boot (Java) — 서버

- **쉬운 설명**: 가게의 **점원** 같은 역할입니다. 화면이 "이 글을 지워 주세요"라고 요청하면, 서버가 **"이 사람이 이 글의 주인이 맞나?"를 확인**한 뒤 DB에서 지웁니다. 규칙 검사(글자 수, 중복, 권한)는 모두 서버가 합니다.
- **우리가 쓰는 곳**: 로그인, 글 쓰기, 댓글, 검색 등 모든 요청 처리. 보안 기능은 **Spring Security**가 담당합니다.
- **고른 이유**: 선호하시는 기술이고, 인증·세션·DB 연결에 필요한 도구가 이미 갖춰져 있어서 **직접 만들 코드가 적습니다.** 팀원 문서도 같은 선택입니다.
- **서버 구조**: **단일 서버** 하나로 만들고, 안에서는 기능별(회원, 블로그, 글, 댓글, 검색)로 폴더를 나눕니다. MSA(서버를 여러 개로 쪼개는 구조)는 쓰지 않습니다. (4장)
- **상태**: 가안 (서버 구조는 확정)

### 2.3 PostgreSQL — 데이터베이스

- **쉬운 설명**: 모든 정보를 **엑셀 표처럼** 정리해서 오래 보관하는 곳입니다. 회원 표, 블로그 표, 글 표가 있고, 표끼리 연결됩니다. (예: 글 표의 "작성자" 칸이 회원 표의 한 줄을 가리킴) 서버를 껐다 켜도 데이터가 남습니다.
- **우리가 쓰는 곳**: 회원, 블로그, 분류, 글, 댓글 같은 **오래 남아야 하는 모든 것**, 그리고 **로그인 세션**(2.5).
- **고른 이유**
  1. 우리 데이터는 **서로 강하게 연결**되어 있습니다. (회원 → 블로그 → 글 → 댓글) 이런 데이터는 표로 정리하는 관계형 DB가 맞습니다.
  2. **규칙을 DB가 직접 지켜 줍니다.** 이메일 중복 불가, 글이 있는 분류는 삭제 불가 같은 규칙을 DB에 걸어 두면, 서버 코드에 실수가 있어도 데이터가 망가지지 않습니다.
  3. **여러 작업을 한 묶음으로 처리(트랜잭션)**할 수 있습니다. 글을 지울 때 댓글까지 함께 지우다 중간에 실패하면 전부 취소됩니다.
  4. 무료이고, 검색 기능(단순 포함 검색)이 기본으로 있습니다. 또 나중에 AI 기능(비슷한 글 추천, 의미 기반 검색)을 붙일 때 **`pgvector`**(PostgreSQL에 붙이는 확장)로 **같은 DB 안에서** 처리할 수 있어서, 별도의 벡터 DB를 새로 들이지 않아도 됩니다.
     - 다만 `pgvector`는 글을 숫자 묶음(벡터)으로 **저장하고 비교**해 줄 뿐이고, 그 숫자를 **만드는 AI 모델은 따로 필요**합니다. 외부 AI 호출을 쓸지는 아직 **미정**입니다.
     - 지금 ERD에는 넣지 않습니다. 필요할 때 벡터를 담는 표(예: `post_embeddings`)를 **새로 추가**하면 되어 기존 표를 바꾸지 않습니다. 그때 개발용 Compose의 PostgreSQL도 `pgvector`가 들어 있는 이미지로 바꿔야 합니다.
- **대안과 비교**

| 대안 | 왜 안 골랐나 |
|---|---|
| MySQL | 충분히 가능한 대안입니다. 이전 프로젝트에서 써 보셨다면 익숙한 쪽을 골라도 됩니다. 팀원 문서가 PostgreSQL이라 맞췄습니다 |
| MongoDB | 문서를 통째로 넣는 DB라 **연결이 강한 데이터에는 불리**하고, 규칙을 DB가 지켜 주는 기능이 약합니다 |
| SQLite | 파일 하나짜리 DB로 연습용에는 편하지만, 여러 사용자가 동시에 쓰는 서비스에는 맞지 않습니다 |

- **상태**: 가안

### 2.4 Redis — 짧게 쓰는 임시 저장소

- **쉬운 설명**: **메모장에 적어 두는 것**과 비슷합니다. 아주 빠르고, 적을 때 **"10분 뒤에 지워 줘"** 하고 시간을 걸어 두면 알아서 사라집니다. 대신 서버가 꺼지면 사라질 수 있어서 **잃어도 괜찮은 값**에 씁니다. (DB는 수첩, Redis는 포스트잇)
- **우리가 쓰는 곳**
  | 용도 | 어떻게 쓰나 |
  |---|---|
  | **이메일 인증번호** (CF-01-14, 15) | "이 이메일의 인증번호는 K7QX9M"을 **10분 뒤 사라지게** 저장. 맞게 입력하면 바로 지움 |
  | **인증 완료 표시** (CF-01-20) | "이 이메일은 인증됨"을 **30분만** 남김 |
  | **재발송 제한** (CF-01-16) | "1분에 한 번", "하루 5번"을 시간이 지나면 풀리는 키로 구현 |
  | 인증번호 틀린 횟수 | 5번 틀리면 번호 폐기 |
  | **조회수 중복 방지** (블로그 관리) | "이 사람이 이 글을 30분 안에 봤다"를 기억해 새로고침으로 조회수가 늘지 않게 함 |
  | 방문자 수 (블로그 관리) | "오늘 이 사람이 이 블로그에 왔다"를 하루 동안 기억 |
- **왜 DB가 아니라 Redis인가**: 이 값들은 **금방 사라져야 하고, 자주 쓰고 지워지며, 잃어도 사용자가 다시 하면 되는** 값입니다. DB에 넣으면 "만료된 것을 지우는 작업"을 따로 만들어야 하지만, Redis는 만료 시간을 걸어 두면 끝입니다.
- **주의**
  - Redis를 쓰면 **설치와 실행이 하나 더 늘어납니다.** (개발 중에는 Docker로 한 번에 띄웁니다)
  - Redis가 꺼져 있으면 **인증번호를 보낼 수 없어서** 가입이 막힙니다. 이때는 "잠시 뒤 다시 시도해 주세요"를 보여 줍니다. ([01-인증-인가.md](상세/01-인증-인가.md)의 '이메일 인증 (가입 전에 인증)')
  - 로그인 자체는 Redis에 의존하지 않습니다. (세션은 PostgreSQL)
- **상태**: 확정 (인증번호 용도). 조회수·방문자 용도는 해당 기능을 만들 때 확정

### 2.5 세션을 어디에 저장할까 — PostgreSQL vs Redis

"로그인 상태를 서버가 기억해야 하니까 Redis"라는 생각은 자연스럽고 **Redis에 세션을 저장하는 방식도 널리 씁니다.** 우리는 지금 두 방법 중 하나를 골랐습니다.

| | **A. PostgreSQL에 저장 (현재 선택)** | B. Redis에 저장 |
|---|---|---|
| 속도 | 보통 (요청마다 DB 조회) | 매우 빠름 |
| 추가 설치 | **없음** (이미 있는 DB) | Redis가 반드시 필요 |
| 만료 처리 | 오래된 세션을 지우는 정리 작업이 필요 | **자동 만료** |
| 서버를 껐다 켜면 | **로그인 유지** (DB에 있으므로) | 설정에 따라 유지 (저장 설정이 필요) |
| Redis가 꺼지면 | 로그인에 **영향 없음** | **모두 로그아웃되거나 로그인 불가** |
| 규모 | 수천 명 정도는 충분 | 더 많은 사용자에 유리 |

- **A를 고른 이유**: 우리 규모에서는 속도 차이를 느낄 수 없고, **Redis가 꺼져도 로그인이 되며**, 7일 유지(CF-02-10)를 추가 설정 없이 지킬 수 있습니다. Redis는 이미 "없어도 서비스가 완전히 멈추지는 않는 값"에만 쓰는 편이 안전합니다.
- **B로 바꾸는 방법**: 서버 설정 한 곳만 바꾸면 됩니다. (Spring Session은 저장소를 바꿔 끼울 수 있게 만들어져 있습니다.) Redis 경험이 목적이라면 B도 충분히 가능합니다.
- **상태**: A 확정. B로 바꿀지는 아래 5장에서 다시 묻습니다.

### 2.6 이미지 저장소 — 올린 사진을 어디에 둘까

사진 파일은 **DB에 넣지 않습니다.** DB에는 "이 글의 사진은 이 주소에 있다"만 적고, 파일은 따로 보관합니다.

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| **서버 디스크** | 서버 컴퓨터의 폴더에 저장 | **가장 단순**, 추가 설치 없음 | 서버가 바뀌면 파일을 옮겨야 함, 서버를 여러 대로 늘리기 어려움 |
| **MinIO** | 내가 직접 띄우는 **파일 보관 서비스** (S3와 같은 방식) | 서버와 파일을 분리, 나중에 AWS S3로 옮기기 쉬움 | **서비스가 하나 더 늘어남**, 설정이 필요 |
| AWS S3 같은 클라우드 | 아마존이 보관해 주는 서비스 | 용량·안정성이 큼 | 계정과 **비용**이 필요, 외부 서비스 규칙의 예외 |

- **MinIO에 대해**: **쓰기로 했습니다(가안).** 파일 저장소(S3 방식)를 배우는 것도 목적입니다. 다만 **2026-04에 공개 저장소가 보관(archived)되어 새 버전과 공식 이미지·실행 파일 배포가 중단**됐습니다. 그래서 **개발용으로 쓰고**, 막히면 서버 디스크로 바꿔 끼울 수 있게 만듭니다. 자세한 이유와 위험은 [04-MinIO-현황과-선택.md](가이드/04-MinIO-현황과-선택.md)에 있습니다.
- **추천**: MinIO 전용 SDK 대신 **S3 표준 방식**(AWS SDK)으로 연결하고, 저장 코드를 `ImageStorage` 인터페이스 하나로 감쌉니다. 배포할 때는 MinIO 포트를 바깥에 열지 않습니다.
- **상태**: **가안** (MinIO, 서버 디스크로 교체 가능)

### 2.7 SMTP — 인증 메일 발송

- **쉬운 설명**: 이메일을 보내는 **우체국 규칙**입니다. 우리 서버가 메일 서비스(Gmail이나 네이버)에 "이 주소로 이 내용을 보내 주세요"라고 맡깁니다.
- **우리가 쓰는 곳**: 인증번호 메일 (CF-01-11)
- **어떻게**: Spring의 메일 기능으로 보내고, **비동기**로 처리해서 가입 화면이 메일 발송을 기다리지 않게 합니다. 개발 중에는 실제 발송 대신 **서버 로그에 인증번호를 출력**해서 메일 한도를 아낍니다.
- **주의**: 개인 메일 계정은 **하루에 보낼 수 있는 양이 제한**되어 있고, Gmail은 앱 비밀번호, 네이버는 메일 설정에서 SMTP 사용을 켜야 합니다. 이 서비스 연동은 "외부 서비스는 쓰지 않는다"는 규칙의 **예외**입니다.
- **상태**: 가안 (발송 계정 **미정**)

### 2.8 비동기 처리와 RabbitMQ

- **쉬운 설명**
  - **비동기**: 오래 걸리는 일을 **"맡겨 놓고 나는 다음 일을 하는 것"**입니다. (식당에서 주문하고 기다리지 않고 진동벨을 받는 것)
  - **RabbitMQ(메시지 큐)**: 맡길 일을 **줄 세워 두는 대기줄 전문 서비스**입니다. 여러 일꾼이 줄에서 하나씩 꺼내 처리하고, 처리하다 실패하면 다시 시도할 수도 있습니다.
- **우리에게 비동기가 필요한 곳을 살펴보면**

| 후보 | 오래 걸리나 | 필요한 도구 |
|---|---|---|
| 인증 메일 발송 | 몇 초 | **Spring 기본 비동기(`@Async`)로 충분** |
| 인기 검색어 계산 | 짧음 | **스케줄러(`@Scheduled`)**로 몇 초마다 |
| 일별 통계 집계 | 짧음 | 스케줄러 (하루 한 번 또는 주기적으로) |
| 미인증 정리 | 이제 필요 없음 (가입 전에 인증하므로) | — |
| 이미지 썸네일 만들기 | 이번에는 안 함 | — |
| AI 호출 (나중) | 길 수 있음 | 필요해지면 그때 검토 |

- **결론**: **지금은 RabbitMQ가 필요 없습니다. 안 씁니다.** 스프링의 기본 기능(`@Async`, `@Scheduled`)으로 충분하고, RabbitMQ를 넣으면 **서비스가 하나 더 늘고, 서버 코드도 두 갈래(보내는 쪽, 받는 쪽)**가 되어 2주 일정에 부담만 커집니다. 말씀하신 대로 비동기가 필요한 부분이 많지 않습니다.
- **언제 도입을 검토하나**: 아래 중 하나가 생길 때입니다.
  1. 일을 **반드시 처리해야 하고, 실패하면 자동으로 다시 시도**해야 할 때 (예: 메일이 꼭 가야 함)
  2. 처리 시간이 길어져서 **서버와 따로 일꾼을 두고 싶을 때** (예: AI 요약)
  3. 서버를 **여러 개로 쪼갠 뒤** 서로 소식을 주고받아야 할 때
- **학습 목적이라면**: 인증 메일 발송을 RabbitMQ로 처리해 보는 것이 가장 작은 적용입니다. 다만 이건 기능이 아니라 **공부를 위한 선택**이라는 점을 구분해 두세요.
- **상태**: **안 씀**

### 2.9 개발·배포 도구

| 도구 | 쉬운 설명 | 쓰는 이유 | 상태 |
|---|---|---|---|
| **Docker Compose** | PostgreSQL, Redis, MinIO 같은 서비스를 **명령 한 줄로 한꺼번에 띄우는** 도구 (사용법: [03-로컬환경-도커컴포즈-사용법.md](가이드/03-로컬환경-도커컴포즈-사용법.md)) | 팀원마다 설치법이 달라 생기는 문제를 줄임. (컴퓨터에 OrbStack이 있는 것으로 보여 바로 쓸 수 있을 가능성이 큼) | 가안 |
| **Flyway** | DB 표의 **변경 이력을 파일로 관리**하는 도구 | "표를 단계적으로 늘리며 만든다"를 안전하게 해 줌. 팀원과 DB 구조를 맞추기도 쉬움 | 가안 (제안) |
| **Nginx** | 서버 앞에 두는 **문지기** | 배포 때 HTTPS와 화면·서버 연결을 정리 | **미정** (배포 환경에 따라) |

## 3. 아키텍처 그림 모음

### A. 서버 안의 구조 (모듈형 단일 서버)

```
 요청 ──▶ [ 보안 필터 ]  세션 번호로 로그인한 회원을 찾는다
              │
              ▼
        [ 컨트롤러 ]    요청을 받고 결과를 돌려준다 (주소별 담당)
              │
              ▼
        [ 서비스 ]      규칙 검사와 처리 (권한, 글자 수, 중복 …)   ← 핵심 규칙은 여기
              │
              ▼
        [ 저장소 ]      DB와 Redis에 읽고 쓴다

 서버는 기능별로 폴더를 나눠 둔다:
 user(회원·인증) / blog(블로그·분류) / post(글) / comment(댓글) / search(검색·인기 검색어) / stats(통계)
 → 나중에 한 부분만 따로 떼어 낼 수 있게 서로는 정해진 입구로만 부른다
```

### B. 로그인과 세션

```
[로그인]
 브라우저 ─(이메일·비밀번호)─▶ 서버
                              ① 이메일로 회원을 찾는다
                              ② 입력한 비밀번호를 해시해서 저장된 값과 비교 (BCrypt)
                              ③ 5회 연속 실패 여부 확인 (잠금)
                              ④ 맞으면 세션을 만들어 PostgreSQL에 저장 (세션 번호 발급)
 브라우저 ◀─(세션 번호를 쿠키로)─ 서버

[이후 모든 요청]
 브라우저 ─(쿠키의 세션 번호)─▶ 서버 ─▶ PostgreSQL 세션 표에서 "누구인지" 확인 ─▶ 처리
 로그아웃 / 비밀번호 변경 = 서버가 해당 세션을 지움 → 번호표 즉시 무효
```

### C. 회원가입과 이메일 인증 (Redis)

```
 ① 닉네임·이메일 입력 ─▶ 서버: 이메일 중복 확인 (PostgreSQL)
 ② [인증번호 받기]     ─▶ 서버: 인증번호 6자리 생성
                              Redis에 "이메일 → 번호" 저장 (10분 뒤 자동 삭제)
                              메일 발송 (비동기, SMTP) ─▶ 사용자 메일함
 ③ 번호 입력 [확인]    ─▶ 서버: Redis의 번호와 비교
                              맞으면: 번호 삭제 + "인증됨" 표시를 Redis에 30분 저장
                              틀리면: 틀린 횟수 +1 (5회면 번호 폐기)
 ④ 비밀번호 입력 [가입하기] ─▶ 서버: "인증됨" 표시가 아직 있는지 확인 (없으면 거절)
                              이메일 중복을 한 번 더 확인
                              비밀번호를 BCrypt로 해시해서 PostgreSQL에 회원 저장
                              블로그를 자동 생성, Redis의 인증됨 표시 삭제
```

### D. 글 수정 요청의 흐름 (세션과 DB가 만나는 곳)

```
 브라우저 ─(세션 쿠키)─▶ 보안 필터: 로그인한 회원을 확인 (세션 표)
                         서비스: ① DB에서 글을 읽는다
                                 ② 글 주인 == 지금 로그인한 회원? (아니면 "존재하지 않는 글")
                                 ③ 제목 1~100자, 본문 필수 같은 규칙 검사
                                 ④ 바뀐 것이 있을 때만 저장 + 수정 시각 갱신
                         DB: 글 표의 해당 줄을 수정 (하나의 트랜잭션)
```

### E. 이미지 업로드 (MinIO 가안, 서버 디스크로 교체 가능)

```
 브라우저 ─(사진 파일)─▶ 서버
                         ① 로그인 확인, 형식(jpg·png·gif·webp)과 용량(5MB) 검사
                         ② 안전한 새 파일 이름을 만든다 (사용자가 준 이름은 쓰지 않음)
                         ③ 파일을 저장소에 저장 (MinIO, 또는 교체한 서버 디스크)
                         ④ DB에 "이 글의 이미지 = 이 주소"를 기록
 브라우저 ◀─(이미지 주소)─ 서버 ──▶ 글 본문에 넣는다
 글 삭제 시: DB 기록과 함께 저장소의 파일도 지운다
```

### F. 조회수와 방문자 집계 (블로그 관리 통계)

```
 글 상세 요청 ─▶ 서버
   본인 글이거나 비공개 글이면 → 세지 않음
   Redis에 "이 사람이 이 글을 30분 안에 봤나" 키가 있나?
        있음 → 조회수 +0 (새로고침 방지)
        없음 → 키를 30분 만료로 저장, 오늘 날짜의 글 조회수 +1
   Redis에 "오늘 이 사람이 이 블로그에 왔나" 키가 있나? (하루 만료)
        없음 → 키 저장, 오늘 날짜의 방문자 +1
 → 숫자는 PostgreSQL의 "일별 통계" 표에 쌓는다 (글마다·날짜마다 한 줄)
 → 블로그 관리의 그래프는 이 표를 읽어 그린다
 (조회가 많아지면: 먼저 Redis에 쌓았다가 주기적으로 DB에 옮기는 방법도 있음)
```

### G. 실시간 인기 검색어

```
 검색 요청 ─▶ 서버: 검색 결과를 돌려주고, 검색어를 "검색 기록" 표에 남긴다
 스케줄러(5초~1분마다) ─▶ 최근 일정 시간의 검색·조회·댓글로 점수를 계산 (검색×3 + 조회×1 + 댓글×5)
                          상위 10개를 메모리(또는 Redis)에 저장
 화면 ─(5초마다 요청)─▶ 서버: 저장해 둔 순위를 돌려준다
 (진짜 "실시간 푸시"는 하지 않고, 화면이 주기적으로 다시 물어본다)
```

### H. 개발 환경 구성

```
 내 컴퓨터
  ├ React 개발 서버 (Vite)          ─ 화면
  ├ Spring Boot 서버               ─ 규칙 처리
  └ Docker Compose로 한 번에 실행
       ├ PostgreSQL
       ├ Redis
       └ MinIO (가안)
 개발 중 메일은 실제로 보내지 않고 서버 로그에 인증번호를 출력
```

## 4. 쓰지 않는 기술과 이유

| 기술 | 쓰지 않는 이유 | 다시 검토할 때 |
|---|---|---|
| **MSA** (서버를 여러 개로 쪼갬) | 개인 구현, 동시 접속자가 적음, 데이터가 강하게 연결되어 쪼개면 오히려 어려움, 2주 일정 | 팀이 여러 개로 나뉘거나 일부 기능만 크게 늘려야 할 때 |
| **JWT (토큰) 인증** | "로그아웃하면 바로 끊김", "다른 기기 끊기" 요구사항을 지키려면 세션이 훨씬 단순함 ([01-인증-인가.md](상세/01-인증-인가.md)의 '쉬운 설명' 참고) | 서버가 여러 개로 나뉘거나 모바일 앱을 붙일 때 |
| **RabbitMQ / Kafka** | 비동기가 필요한 일이 적고, 스프링 기본 기능으로 충분함 (2.8) | 재시도 보장, 일꾼 분리, 서버 분리가 필요할 때 |
| **Elasticsearch** (검색 전용 서버) | 글이 많지 않아 PostgreSQL 검색으로 충분함 | 글이 아주 많아지거나 한국어 검색 품질이 중요해질 때 |
| 외부 소셜 로그인 | 요구사항 제외 (외부 서비스 연동 안 함) | 나중에 확장할 때 |

## 6. 용어 풀이

| 용어 | 쉬운 설명 |
|---|---|
| **서버** | 요청을 받아 규칙을 검사하고 처리해 주는 프로그램 (가게의 점원) |
| **DB (데이터베이스)** | 정보를 표로 정리해 오래 보관하는 곳 (수첩) |
| **Redis** | 빠르고 만료 시간을 걸 수 있는 임시 저장소 (포스트잇) |
| **세션** | 서버가 "이 사람은 로그인한 사람"이라고 적어 둔 명부 |
| **쿠키** | 브라우저가 서버 대신 들고 있는 작은 쪽지 (번호표를 담음) |
| **해시 (BCrypt)** | 비밀번호를 **되돌릴 수 없는** 다른 값으로 바꾸는 것. 운영자도 원문을 알 수 없음 |
| **TTL (만료 시간)** | "이 시간이 지나면 자동으로 지워라" |
| **트랜잭션** | 여러 작업을 **전부 성공하거나 전부 취소**하는 한 묶음 |
| **인덱스** | DB가 빨리 찾도록 만들어 두는 색인 (책의 찾아보기) |
| **제약** | DB가 직접 지키는 규칙 (중복 불가, 비워 둘 수 없음 등) |
| **비동기** | 오래 걸리는 일을 맡겨 놓고 기다리지 않는 것 |
| **스케줄러** | 정해진 시간마다 자동으로 일하는 기능 |
| **메시지 큐 (RabbitMQ)** | 맡길 일을 줄 세워 두고 일꾼이 꺼내 처리하는 서비스 |
| **오브젝트 스토리지 (MinIO, S3)** | 파일을 보관하는 전용 서비스 |
| **마이그레이션 (Flyway)** | DB 표를 바꾼 이력을 파일로 남겨 순서대로 적용하는 것 |
| **컨테이너 (Docker)** | 프로그램을 설치 없이 똑같은 환경으로 실행하는 상자 |
