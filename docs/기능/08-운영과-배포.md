# 08. 운영과 배포

> 코드를 main에 합치면 자동으로 검사하고, 사이트를 끊지 않고 새 버전으로 바꿔 끼워요. 이 문서는 블로그를 쓰는 회원이 아니라 운영하고 개발하는 사람이 할 수 있는 일을 적었어요.
> 동작 원리는 [원리/08-운영과-배포.md](../원리/08-운영과-배포.md)에 있어요.

## 한눈에

- 브랜치는 main(배포), develop(모으는 곳), feature/*(기능 하나)로 나눠요. main에 들어가면 자동 배포돼요.
- PR을 올리면 CI(자동 검사)가 서버 테스트와 화면 검사·테스트·빌드를 돌려요. 브라우저로 핵심 흐름을 끝까지 해 보는 종단(E2E) 테스트도 있어요.
- 배포는 블루-그린 방식이라 사이트가 끊기지 않고, 새 버전이 안 뜨면 옛 버전이 그대로 남아요.
- 바깥에서는 https://sagak.java21.net (HTTPS)으로만 들어올 수 있어요. 앱 포트 8390은 서버 안에서만 열려 있어요(v1.10.1).
- `status` 워크플로로 서버 상태를 확인하고, `CHANGELOG.md`를 고치면 GitHub Release가 저절로 생겨요.
- 비밀값(DB, 메일, 소셜 로그인 키)은 GitHub Secrets에 넣어요. 메일(SMTP)과 소셜 로그인은 키를 넣으면 켜지고, 비우면 꺼져요.
- 시간 맞춰 저절로 도는 일 4개, Redis가 꺼졌을 때의 동작, DB 구조를 바꾸는 규칙(Flyway), 설정 방법, 로컬 개발 환경을 다뤄요.

## 이렇게 써요

### 브랜치 나누기
- 새 기능은 develop에서 브랜치를 따서 만들어요. 이름은 `feature/이름` 꼴을 권하지만, 저장소에는 `trending-24h`, `sticker-shop`처럼 앞말 없이 지은 브랜치도 많아요.
- 기능 브랜치는 PR(변경 제안)로 develop에 합쳐요. 자잘한 수정을 하나씩 배포하지 않고 develop에 모아 둬요.
- 배포하고 싶을 때만 develop을 main으로 합쳐요. main에 들어가는 순간 배포가 시작돼요.
- 급한 수정(hotfix) 브랜치에 대한 규칙은 저장소에 따로 적혀 있지 않아요. `fix/session-cookie`처럼 고칠 것만 담은 브랜치를 만들어 같은 길(PR → develop → main)로 보냈어요.

### PR과 CI(자동 검사)
- PR을 올리면 GitHub Actions의 `ci` 워크플로가 저절로 돌아요. 대상 브랜치가 develop이든 main이든 똑같이 돌아요.
- develop에 합쳐진 뒤에도 한 번 더 돌아요(v1.10.1). 그래야 SonarQube 첫 화면(develop)에 테스트 커버리지가 떠요.
- **backend**: 빈 PostgreSQL 16(`myblog_test` DB)과 Redis 7을 띄우고 `./gradlew test`로 서버 테스트를 모두 돌려요. Java는 21이에요.
- **frontend**: Node 22로 `npm ci`, `npm run lint`(코드 규칙 검사, 경고 0개여야 통과), `npm run typecheck`(타입 검사), `npm test`(vitest), `npm run build`를 차례로 돌려요.
- **SonarQube 품질 게이트**(v1.10.0): backend 작업 끝에 SonarQube Cloud가 코드를 분석해요. 이번에 바뀐 코드에 버그나 보안 취약점이 하나라도 있거나, 테스트 커버리지가 80%보다 낮거나, 중복이 3%를 넘으면 실패해요. PR에 sonarqubecloud 봇이 결과 댓글을 달아요.
- 하나라도 실패하면 빨간 X가 떠요. backend, frontend, SonarCloud Code Analysis가 모두 초록 체크여야 develop과 main에 합칠 수 있어요(브랜치 규칙 "머지 전 검사 필수").
- 테스트가 실패하면 실행 화면 아래 **Artifacts**에 테스트 보고서가 남아요(`backend-test-reports`, `frontend-test-reports`, 14일 보관). 내려받아 어느 테스트가 왜 실패했는지 봐요(다음 버전, 지금은 develop에만 있어요).
- v1.10.2 기준 SonarQube는 신뢰성 · 보안 · 유지보수성이 모두 A, 해결 안 된 이슈 0개, 전체 커버리지 약 90%예요(`CHANGELOG.md`).

### 종단(E2E) 테스트 (다음 버전)
- 실제 서버(화면 + 서버 + PostgreSQL + Redis)를 띄워 두고, Playwright가 Chromium 브라우저로 핵심 흐름 3개를 끝까지 해 봐요. 테스트는 7개예요.
  1. 가입 → 로그인 → 글쓰기 → 글 화면 · 내 블로그 · 메인 최신 글에 보임 (+ 틀린 비밀번호, 로그인 없이 글쓰기 주소)
  2. 다른 회원의 글에 댓글 · 좋아요 → 글쓴이에게도 보임 (+ 손님은 읽기만 되고 좋아요는 안 됨)
  3. 머리말 검색 → 결과 → 글로 이동 (+ 결과 없음)
- 로컬에서 돌리기: 서버를 `MYBLOG_MAIL_MODE=log`로 띄우고(가입 인증번호가 화면에 나와요), 처음 한 번 `npx playwright install chromium`, 그다음 `cd frontend && E2E_BASE_URL=http://localhost:8080 npm run e2e`. 개발 서버로 돌리면 `E2E_BASE_URL=http://localhost:5173`이에요.
- 돌릴 때마다 새 회원을 만들어서 같은 DB에서 여러 번 돌려도 부딪히지 않아요. 운영 DB에서는 돌리지 않아요.
- CI에서는 `e2e` 워크플로가 돌아요. 느려서 PR마다 돌리지 않고, **develop · main에 합쳐진 뒤**에 돌려요. E2E 파일(`frontend/e2e/`, `playwright.config.ts`, `e2e.yml`)을 고친 PR에서만 PR 때도 돌아요. Actions 탭에서 손으로 돌릴 수도 있어요.
- 실패하면 서버 로그 200줄을 찍고, 화면 녹화 · 스크린샷이 든 보고서를 Artifacts `e2e-report`(14일)로 남겨요.
- 테스트를 어떻게 나누고 고르는지는 코드 저장소의 `TESTING.md`에, AI(Claude Code)가 지킬 규칙은 `CLAUDE.md`에 있어요.

### 라이브러리 새 버전 알림(Dependabot) (다음 버전)
- `.github/dependabot.yml`이 라이브러리와 Actions의 새 버전 · 보안 패치를 PR로 알려 줘요. PR은 develop으로 와서, 다른 PR처럼 CI와 품질 게이트를 통과해야 합칠 수 있어요.
- 서버(gradle)와 화면(npm)은 매주 월요일, GitHub Actions는 매달 봐요. 작은 올림(minor · patch)은 한 PR로 묶어요.

### 자동 배포(CD)
- main에 푸시되거나 PR이 합쳐지면 `deploy` 워크플로가 시작돼요. Actions 탭의 deploy에서 "Run workflow"를 눌러 손으로 돌릴 수도 있어요.
- 먼저 `ci`를 한 번 더 돌리고, 통과해야만 배포로 넘어가요.
- 앱 전체(화면 + 서버)를 Docker 이미지 하나로 만들어 압축 파일로 저장하고, 서버의 `~/myblog-deploy`로 보내요. 그다음 서버에서 `deploy/deploy.sh`를 실행해요.
- 배포가 겹치면 앞의 배포를 끝까지 마친 뒤 다음 배포를 시작해요. 도중에 취소하지 않아요.
- 몇 분 뒤 https://sagak.java21.net 에 새 버전이 보여요. 사람이 서버에 들어가 할 일은 없어요.
- **배포 뒤 실제 사이트 확인**(다음 버전): 배포가 끝나면 GitHub 러너가 실제 주소(HTTPS)로 `/`, `/api/topics`, `/api/home`이 200으로 오는지, HSTS 헤더가 있는지 봐요. 5초 간격으로 5번까지 다시 해 보고, 그래도 안 되면 deploy 작업이 실패로 끝나요. 서버 안 확인은 통과했는데 바깥 nginx · 인증서에서 막히는 경우를 잡아요.

### 무중단 배포(블루-그린)를 지켜보면
- deploy 작업의 로그에 `==> 새 서버 띄우기: myblog-green (...), 지금 서버: myblog-blue`처럼 어느 쪽으로 바꾸는지 나와요.
- 성공하면 마지막 줄에 `배포 완료: myblog-green가 ... 손님을 받습니다`가 찍혀요. 다음 배포는 반대 색(blue)으로 가요.
- 새 서버가 정상으로 뜨지 않으면 "옛 서버로 그대로 둡니다"와 함께 새 서버 로그 마지막 80줄을 보여 주고, 워크플로는 실패로 끝나요. 사이트는 옛 버전으로 계속 돌아가요.
- 배포하는 동안 회원의 로그인은 풀리지 않아요. 세션이 Redis에 있기 때문이에요.
- 맨 처음 블루-그린으로 바꾼 한 번만 1~2초 끊겼어요. 예전 방식 컨테이너가 8390을 잡고 있어서 그것을 지우고 nginx를 띄워야 했기 때문이에요. 그 뒤로는 끊기지 않아요.
- 8390을 받는 주소(`PROXY_BIND`)를 바꾼 배포도 한 번 1~2초 끊겨요. 포트 주소는 컨테이너를 다시 만들어야 바뀌기 때문이에요. v1.10.1을 처음 배포할 때가 그랬어요.

### 서버에 무엇이 있나
- **서버 nginx**: 학원 서버 관리자가 관리해요. https://sagak.java21.net 을 HTTPS(Certbot 인증서)로 받아 같은 서버의 `127.0.0.1:8390`으로 넘겨요.
- **nginx 컨테이너 `myblog-proxy`**: 8390 포트로 들어오는 요청을 받아 지금 일하는 서버로 넘겨요. v1.10.1부터 서버 안(`127.0.0.1`)에서만 받아서, `http://공인IP:8390`으로는 열리지 않아요(바깥망에서 확인했어요). 브라우저가 이 사이트를 https로만 열도록 HSTS 헤더도 붙여요.
- **앱 컨테이너 `myblog-blue` / `myblog-green`**: 평소엔 하나만 떠 있어요. 배포하는 동안만 잠깐 둘이 같이 떠요.
- **Redis 컨테이너 `myblog-redis`**: 로그인 세션, 인증번호, 조회수 중복 막기 같은 짧은 기억을 둬요.
- 이 컨테이너들은 모두 도커 네트워크 `myblog-net` 안에서 이름으로 서로를 불러요.
- **PostgreSQL**: 서버 밖에 있는 DB를 써요(Crowfoot에서 받은 DB의 내 스키마). 컨테이너로 띄우지 않아요.
- **`~/myblog-data` 폴더**
  - `images/`: 회원이 올린 사진. 컨테이너 안에서는 `/data/images`로 보여요.
  - `app.env`: 배포 때마다 다시 만드는 앱 설정 파일(DB 주소, Redis 주소 등). 주인만 읽을 수 있어요.
  - `proxy/conf.d/default.conf`: nginx 설정. 지금 손님을 받는 서버 이름이 여기에 적혀 있어요.
- 그래서 바깥 손님은 "서버 nginx(HTTPS) → `myblog-proxy`(127.0.0.1:8390) → `myblog-blue`/`myblog-green`" 길로만 들어와요.

### 비밀값 넣기
- 저장소가 공개라서 비밀번호는 코드에 없어요. GitHub 저장소의 Settings > Secrets에 넣어요.
- 꼭 있어야 하는 Secrets 10개: `SSH_ADDRESS`, `SSH_PORT`, `SSH_ID`, `SSH_PASSWORD`, `DB_ADDRESS`, `DB_PORT`, `DB_NAME`, `DB_SCHEMA`, `DB_USERNAME`, `DB_PASSWORD`.
- 선택 Secrets(넣으면 켜지고, 비우면 꺼져요)
  - 메일(v1.7.1): `SMTP_HOST`, `SMTP_PORT`(비우면 587), `SMTP_USERNAME`, `SMTP_PASSWORD`, `MAIL_FROM`. `SMTP_HOST`가 있어야 실제 메일을 보내요.
  - 소셜 로그인(v1.8.0): `KAKAO_CLIENT_ID`, `KAKAO_CLIENT_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`. CLIENT_ID가 있는 제공자만 켜져요.
- 선택 저장소 변수(Variables) 2개
  - `NOTICE_OWNER_EMAIL`: 공지사항을 쓰는 회원의 이메일이에요. 비우면 공지사항이 빈 화면이에요.
  - `SITE_URL`: 사이트 주소예요. 비우면 `https://sagak.java21.net`이에요. 소셜 로그인 뒤 돌아올 주소에 써요.
- 서버 접속은 SSH 키가 아니라 **아이디와 비밀번호**(`SSH_ID`, `SSH_PASSWORD`)로 해요.
- 서버의 SSH 계정은 docker를 쓸 수 있어야 해요(`sudo usermod -aG docker <계정>`). 안 되면 비밀번호 없는 sudo가 될 때만 sudo로 대신 해요.

### 소셜 로그인 켜기 (v1.8.0)
1. 카카오 디벨로퍼스와 구글 클라우드 콘솔에서 앱(OAuth 클라이언트)을 만들고, client id와 client secret을 받아요.
2. 돌아올 주소(Redirect URI)를 등록해요. `SITE_URL/login/oauth2/code/kakao`, `SITE_URL/login/oauth2/code/google` 꼴이에요. 운영은 `https://sagak.java21.net/login/oauth2/code/kakao`처럼 돼요. 로컬 개발은 `http://localhost:5173/login/oauth2/code/kakao`(구글은 `/google`)예요.
3. 동의 항목: 카카오는 닉네임(`profile_nickname`)과 카카오계정 이메일(`account_email`), 구글은 `openid`, `profile`, `email`이에요. 이메일을 못 받으면 로그인이 안 돼요.
4. GitHub Secrets에 `KAKAO_CLIENT_ID`/`KAKAO_CLIENT_SECRET`, `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`을 넣고 배포해요. 로컬은 `.env`에 같은 이름으로 넣어요.
5. 키를 넣은 제공자의 버튼만 로그인 창에 보여요. 하나도 없으면 소셜 로그인 버튼이 아예 안 보이고, 서버도 소셜 로그인 기능을 켜지 않아요.

### 서버 상태 확인(status)
- Actions 탭에서 `status` 워크플로를 손으로 돌려요. 주소 칸(예: `https://sagak.java21.net`)은 비워도 돼요.
- 보여 주는 것
  - 서버 안: `myblog`가 들어간 컨테이너들의 이름·상태·포트, 서버 안에서 `/api/topics`의 응답 코드, 지금 일하는 색(active), 그 컨테이너의 최근 로그 20줄.
  - 바깥: GitHub 러너에서 `서버주소:8390/api/topics`로 들어가지는지(응답 코드 또는 timeout). v1.10.1부터 8390은 서버 안에서만 열려서 **timeout이 정상**이에요. 응답 코드가 나오면 8390이 바깥에 다시 열렸다는 뜻이니 `PROXY_BIND`를 확인해요.
  - 주소를 넣었으면: 그 주소의 `/`, `/api/topics`, `/api/search?q=a` 응답 코드와 내용 앞부분 150글자.

### 버전과 릴리스
- `CHANGELOG.md` 맨 위에 `## vX.Y.Z 제목` 줄, 날짜, 바뀐 점을 적어요. 필요하면 다음 줄에 `<!-- commit: 커밋 -->`로 어느 커밋에 붙일지 적어요(없으면 지금 커밋).
- main에 합쳐질 때 `CHANGELOG.md`가 바뀌었으면 `release` 워크플로가 돌아, 아직 GitHub Release가 없는 버전을 같은 내용으로 만들어요. 손으로 돌릴 수도 있어요.
- 번호 규칙: 기능 묶음을 내면 가운데 숫자(v1.5.0 → v1.6.0), 작은 수정이면 끝 숫자(v1.6.0 → v1.6.1)를 올려요.
- 지금까지 v1.0.0부터 v1.10.2까지 18개가 있어요(맨 위 v1.10.2가 Latest). 사이트 안 공지사항에 올리는 것은 사람이 따로 해요.

| 1시간마다 (켠 뒤 1분부터) | 글에 쓰이지 않은 채 24시간 지난 사진 지우기 |
| 매일 새벽 4:30 (한국 시간) | 30일 지난 검색 기록 지우기 |
| 매일 새벽 4:40 (한국 시간) | 탈퇴하고 30일 지난 회원 정리(익명화) |

### Redis가 꺼지면
- 회원가입·비밀번호 찾기의 인증번호는 "잠시 뒤 다시 시도해 주세요" 오류가 나요.
- 조회수 중복 막기, 방문자 세기, 댓글 연타 막기는 건너뛰어요. 이때 조회수와 방문자는 늘지 않고, 댓글은 그냥 달려요.
- 로그인 세션이 Redis에 있어서 로그인과 로그인이 필요한 일은 안 돼요. 로그인 없이 글 읽기는 돼요.

### 로컬에서 개발하기
1. `cp .env.example .env` 하고 `DB_PASSWORD` 등을 채워요. `.env`는 Git에 올리지 않아요.
2. `docker compose up -d db redis`로 PostgreSQL 16과 Redis 7을 띄워요. MinIO까지 쓰려면 `docker compose --profile minio up -d`.
3. `cd backend && ./gradlew bootRun`. 서버가 http://localhost:8080 에 뜨고 Flyway가 표를 만들어요. 8080이 쓰이고 있으면 `SERVER_PORT=8081`처럼 바꿔요.
4. `cd frontend && npm install && npm run dev`. 화면이 http://localhost:5173 에 뜨고 `/api` 요청은 8080으로 넘겨요. 서버 주소가 다르면 `MYBLOG_API_TARGET=http://localhost:8081`처럼 줘요.
5. 메일은 기본으로 보내지 않고 서버 로그에 `[메일] to=...`로 인증번호를 찍어요. 그걸 보고 가입하면 돼요. 가입 인증번호는 화면에도 "임시 인증번호"로 보이지만, 비밀번호 찾기 번호는 로그에서만 볼 수 있어요.
6. 소셜 로그인을 해 보려면 `.env`에 `KAKAO_CLIENT_ID` 등을 넣어요. 화면 개발 서버가 `/oauth2`, `/login/oauth2`도 서버로 넘겨 줘요.

### 메일 보내기 방식
- `MYBLOG_MAIL_MODE=log`(기본): 메일을 보내지 않고 서버 로그에 내용을 찍어요.
- `MYBLOG_MAIL_MODE=smtp`: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `MAIL_FROM`으로 실제로 보내요.
- **운영 서버는 Secrets로 정해요(v1.7.1).** Secret `SMTP_HOST`가 있으면 `deploy.sh`가 `app.env`에 `MYBLOG_MAIL_MODE=smtp`와 SMTP 값을 적어 실제 메일을 보내요. 없으면 기본값(log)이에요.
- `smtp` 모드에서는 인증번호를 보낼 때마다 SMTP 서버에 붙어 볼 수 있는지 먼저 확인해요. 붙지 못하면 "메일을 보낼 수 없다"(`MAIL_SEND_FAILED`) 오류가 나요.

## 알아 두면 좋은 것

- **DB 구조 바꾸기는 새 번호 파일로만 해요.** 한 번 실행된 `V숫자__이름.sql`은 절대 고치지 않아요. 바꿀 게 있으면 지금 마지막(V24) 다음 번호(V25)로 새 파일을 더해요. 서버가 켜질 때 아직 안 한 번호만 순서대로 실행돼요.
- **번호가 순서를 어기면 배포가 실패해요.** 운영 DB에 V16이 먼저 들어간 뒤 V14·V15가 오자 Flyway 검증이 실패했어요. 두 파일은 운영에 적용된 적이 없어서 V17·V18로 이름만 바꿨어요. 그래서 V14·V15 번호는 비어 있어요.
- **컬럼 삭제·이름 바꾸기는 두 번에 나눠 배포해요.** 새 서버가 뜨면서 DB 구조를 바꾸는 동안 옛 서버도 같은 DB를 쓰고 있어요. 먼저 새 코드가 옛 컬럼 없이도 돌게 배포하고, 다음 배포에서 컬럼을 지워요.
- **설정 프로필(dev/prod)은 없어요.** 설정은 `application.yml` 하나에 기본값을 두고, 환경변수나 `.env`로 덮어써요. 로컬은 `.env`, 운영은 `deploy.sh`가 만드는 `app.env`를 써요. 테스트만 `application-test.yml`(test 프로필)을 따로 써요.
- **운영 세션 쿠키는 Secure예요(v1.7.1).** `deploy.sh`가 `SESSION_SECURE_COOKIE=true`를 넣어서 로그인 쿠키가 HTTPS로만 오가요. 로컬(http)은 기본값 false라 그대로 로그인돼요.
- **SMTP Secret이 없으면 운영 메일은 log 모드예요.** 실제 회원은 인증번호 메일을 받지 못하고, 가입 인증번호만 화면에 보여요. 비밀번호 찾기 번호는 서버 로그에만 남아서, 회원이 혼자서는 비밀번호를 찾을 수 없어요.
- **`SITE_URL`과 제공자에 등록한 주소가 같아야 해요.** 도메인을 바꾸면 Variable `SITE_URL`과 카카오 · 구글 콘솔의 돌아올 주소를 함께 바꿔요. 다르면 제공자가 "잘못된 redirect URI" 오류를 내요.
- **배포 직후 실시간 인기 검색어가 잠깐 달라질 수 있어요.** 조회 기록 일부를 서버 메모리에 두는데, 새 서버는 빈 상태로 시작해요. 검색 기록은 DB에 있어서 그대로예요.
- **nginx는 프록시만 해요.** 화면(React 빌드 파일)은 Spring 서버가 같이 내려줘요.
- **`PROXY_BIND`는 `deploy.yml`이 넘기지 않아요.** 그래서 배포는 늘 `deploy.sh`의 기본값(`127.0.0.1`)을 써요. 서버 nginx가 넘겨 주는 주소가 바뀌면 이 기본값을 고쳐요. 바꿀 주소로 nginx를 못 띄우면 예전 주소로 되돌려 사이트는 살려 둬요.
- **이미지를 만들 때 설치 스크립트를 돌리지 않아요(v1.10.1).** `Dockerfile`도 CI처럼 `npm ci --ignore-scripts`예요. 외부 패키지가 설치 중에 남의 코드를 실행하지 못하게 막아요.
- **사진은 서버 디스크에 있어요.** 컨테이너를 지워도 `~/myblog-data/images`는 남아요. MinIO는 로컬에서 고를 수 있는 선택 사항이고 운영은 안 써요.
- 배포가 끝나면 쓰지 않는 도커 이미지는 저절로 지워요(`docker image prune`).
- 배포 파일을 받은 뒤 서버의 이미지 압축 파일(`myblog-image.tar.gz`)은 지워요.
